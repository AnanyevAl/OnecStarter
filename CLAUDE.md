# OneCStarter — правила проекта

Программа запуска информационных баз 1С:Предприятие. Python + PySide6, Windows.

## Текущий статус

Ядро v1 реализовано и поставляется: раздел «Базы» (дерево, поиск, запуск с контролем
версии платформы, правки списка, группы, ярлыки), раздел «Настройки» (тема), сборка
PyInstaller + установщик Inno Setup, диагностика старта. Требования —
[docs/requirements.md](docs/requirements.md) (заполнены 30.07.2026), состояние задач —
[docs/tasks.md](docs/tasks.md). Новая функциональность — только через `brainstorming`
и план (раздел «Процесс»).

## Архитектурные инварианты

Нарушение любого из них — повод остановиться и обсудить, а не обойти.

1. **Qt только в `src/onecstarter/ui/`.** Пакеты `domain`, `config`, `platform_1c`, `security`,
   `services` не импортируют `PySide6` ни прямо, ни транзитивно. Логика выбора версии платформы
   должна тестироваться без GUI.
2. **Выбор версии платформы — чистая функция.** Без обращений к ФС и процессам внутри.
   Всё окружение подаётся аргументами. Покрывается табличными тестами.
3. **Форматы 1С читаются и пишутся без потерь.** Неизвестные ключи, порядок и кодировка исходного
   файла сохраняются при записи. Модель = типизированные поля + словарь остального.
   Кодировка определяется по факту, не хардкодится.
4. **Запись в пользовательские файлы — атомарная.** Временный файл в том же каталоге + замена.
   Штатный стартер работает с теми же файлами и может перезаписать их в любой момент.
5. **Секреты — только через `security/`.** Ни в своих файлах, ни в логах, ни в сообщениях об ошибках.

## Достоверность фактов о 1С

Агент не знает предметную область и склонен её домысливать. Поэтому:

- Источники — официальная документация и измерения на реальной машине. **Не статьи и не форумы.**
- Каждый факт о форматах и механике запуска помечается уровнем достоверности:
  проверено / из документации / не проверено.
- Утверждение без метки не попадает ни в скил, ни в `docs/`.
- Не уверен — пометь как непроверенное и предложи эксперимент. Не выдавай догадку за факт.

## Доменные скилы проекта

`.claude/skills/v8i-format/` и `.claude/skills/platform-launch/` — проверенное знание о форматах
1С и запуске платформы. **Читать их перед любой работой с `.v8i`, `1cestart.cfg` или сборкой
командной строки запуска.** Собственные представления о форматах 1С без сверки со скилом не применять.

Результаты экспериментов из `T-02` возвращаются в скилы: подтверждённое повышается до «проверено»,
опровергнутое исправляется. Скил, разошедшийся с реальностью, хуже отсутствующего.

## Фикстуры для тестов

- В `tests/fixtures/` — только обезличенные файлы. Реальные пути к базам, имена организаций
  и имена пользователей в репозиторий не попадают.
- Обезличивание: заменять содержимое `Connect`, имена секций и значения `Folder`; **сохранять
  структуру** — количество секций, наличие секций-групп, дробные `OrderInList`, неполные `Version`,
  исходную кодировку и отсутствие BOM. Фикстура без этих особенностей бесполезна.
- `ID` перегенерировать, уникальность в пределах файла сохранять.
- Обязательный набор краевых случаев: секция-группа без `Connect`, неполная `Version`,
  дробный `OrderInList`, неизвестный ключ, вложенная группа, клиент-серверная и ws-строка соединения.
- Файлы, снятые с рабочей машины и не прошедшие обезличивание, именовать `*.local.v8i` —
  они исключены в `.gitignore`.

## Сборка

- PyInstaller, режим one-dir. Spec-файл — в `build/`, он единственный источник правды о сборке.
- Сборка обязана заканчиваться smoke-тестом собранного экземпляра, а не фактом успешной упаковки.
- Версия проставляется из одного места — `pyproject.toml`.

## Процесс

- Скилы `superpowers` установлены глобально. Ключевые для нас: `brainstorming` перед любой
  новой функциональностью, `test-driven-development` для ядра, `systematic-debugging` при багах,
  `verification-before-completion` перед заявлением о готовности.
- Свои скилы пишем через `writing-skills`, формат не изобретаем. Iron Law: сначала baseline-сценарий
  на субагенте без скила, потом скил, потом проверка.
- Slash-команд у `superpowers` 6.2.0 нет — скилы вызываются по описанию или явной просьбой.
- **Мутационная проверка тестов.** Тест, проверяющий отказ операции или сохранность
  пользовательского файла, обязан падать на сломанной реализации. До того, как считать
  задачу закрытой: временно сломать проверяемое поведение, убедиться, что тест упал
  и на чём именно, откатить эксперимент, записать результат. Тест, зелёный на пустышке,
  хуже отсутствующего — он создаёт ложную уверенность. На табличных тестах чистых функций
  не требуется.
- **План и спека правятся вслед за находкой.** Если ревью нашло дефект в коде, который
  план предписывал дословно, — ошибка в плане, и править надо оба. Если находка вскрыла,
  что правило спеки неисполнимо, — переписывается правило, а не подгоняется код под текст.
  Документ, разошедшийся с кодом, врёт следующему исполнителю.

## Команды

```powershell
uv sync              # окружение
uv run pytest        # тесты
uv run ruff check .  # линт
uv run mypy          # типы
```

`mypy` в режиме `strict` для всего, кроме `onecstarter.ui.*`.

## Границы

- `temp/` — материалы заказчика (документация ИТС, снятые с машины файлы). В репозиторий не идут,
  распространению не подлежат. Читать можно, копировать содержимое в `docs/` — нет.
- В `tests/fixtures/` попадают только обезличенные файлы: реальные пути к базам и их имена
  не должны оказаться в репозитории.
- Не запускать процессы 1С без явной просьбы. Запуск клиента на рабочей базе — действие
  с последствиями.
