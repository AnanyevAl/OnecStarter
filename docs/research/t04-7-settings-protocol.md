## Подготовка (один раз)

1. **Снимок реестра до всего.** Значение `OneCStarter` не должно существовать —
   если оно есть, это остаток прошлых опытов, и блок А начнётся с ложного факта:

   ```powershell
   reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v OneCStarter
   ```

   Ожидание до начала: `ERROR: The system was unable to find the specified registry key or value`.
   Есть значение — удалить (`reg delete ... /v OneCStarter /f`) и записать, откуда оно взялось.

2. **Резервная копия настроек** (блок В правит их вживую):

   ```powershell
   Copy-Item "$env:APPDATA\OneCStarter\settings.json" "$env:APPDATA\OneCStarter\settings.json.bak-t047" -ErrorAction SilentlyContinue
   ```

   Файла может не быть — это нормально, он создаётся первой правкой настройки.

3. **Чем читать значение Run** (форма записи важна не меньше факта наличия —
   спека §3.2 требует путь в кавычках и аргумент `--autostart`):

   ```powershell
   reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v OneCStarter
   ```

4. Установленный экземпляр и запуск из исходников — разные вещи: тумблер
   автозапуска из исходников **заблокирован** по признаку `sys.frozen`
   (спека §3.3). Весь блок А и шаги В2, В7 — только на установленной версии.

## Блок А — установщик, реестр и деинсталляция (закрывает пункт 1)

Проверяется утверждение спеки §3.5: запись в `[Registry]`
[build/installer.iss](../../build/installer.iss) не создаёт значение при
установке и удаляет его при деинсталляции. Метка на момент слияния вехи —
**[Из документации Inno Setup, не проверено]**.

Сама запись по ходу прогона изменилась дважды, и это часть его результата:
на старте она была `ValueType: string; Flags: dontcreatekey uninsdeletevalue`
(шаг А3 показал, что так создаётся пустое значение), к концу стала
`ValueType: none; Flags: uninsdeletevalue` — `dontcreatekey` снят финальным
ревью ветки как способный отменить регистрацию удаления целиком.

**Утверждение вехи «ISCC.exe на машине разработки нет» устарело** (проверено
20.08.2026 при подготовке протокола): Inno Setup 6.7.3 установлен в
`%LOCALAPPDATA%\Programs\Inno Setup 6`. Шаг А1 поэтому уже выполнен агентом —
компиляция установщика не является ни запуском GUI, ни установкой, и под
запрет вехи не попадает. Остальные шаги блока требуют реальной установки
и деинсталляции: их выполняет заказчик.

**Риск, ради которого блок и существует.** Значение в `Run` пишет само
приложение, а не установщик. Удалит ли `uninsdeletevalue` то, чего установщик
не создавал, — ровно тот вопрос, на который документация читается двояко, а
шаг А6 отвечает однозначно. Провал А6 — не катастрофа вехи, а находка: после
деинсталляции Windows при каждом входе пытается запустить стёртый exe.
Кандидаты на замену перечислены после шага А7 — выбирает заказчик.

### А1. Сборка установщика — **выполнено 20.08.2026**

```powershell
uv run pytest -q; if ($?) { .\build\build.ps1 }
```

Критерий: `ISCC` найден по одному из двух путей (`%LOCALAPPDATA%\Programs\Inno Setup 6`
или `%ProgramFiles(x86)%\Inno Setup 6`), `smoke: OK`, на выходе
`dist\OneCStarter-0.1.0-setup.exe`. Скрипт держит порядок «smoke до артефактов»
сам — вмешиваться не нужно.

**Результат — [Проверено, 20.08.2026, машина разработки]:** 1214 тестов зелёные,
PyInstaller 6.22.1, `smoke: OK`, компилятор Inno Setup 6.7.3, код выхода 0.
Артефакты: `dist\OneCStarter-0.1.0-setup.exe` (33,2 МБ),
`dist\OneCStarter-0.1.0-portable.zip` (48,6 МБ), `dist\OneCStarter` (117,6 МБ).

Существенное для блока: в логе компиляции — строка `Parsing [Registry] section`
без единого предупреждения. Это первая машинная проверка секции за всю веху:
ISCC разбирает список флагов и отвергает несовместимые на этапе компиляции,
то есть пара `dontcreatekey uninsdeletevalue` как минимум **допустима вместе**.
О том, удалит ли `uninsdeletevalue` значение, которое установщик не создавал,
компиляция не говорит ничего — это шаг А6.

Оговорка о размерах: T-04.6 (16.08.2026) записал setup 35 МБ и dist 123 МБ,
сейчас 33,2 и 117,6. Расхождение — смена версий Python/PySide6 в окружении
за четыре дня, не следствие вехи: T-04.7 в состав поставки ничего не добавляла.

### А3. Значение Run после установки — его не должно быть

```powershell
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v OneCStarter
```

Критерий: значения нет. Значение появилось —
установщик включил автозапуск молча, что прямо противоречит §1 спеки
(«автозапуск никогда не включается молча»): остановиться, зафиксировать,
дальше блок А не имеет смысла до правки `installer.iss`.

**Результат — [Проверено, 21.08.2026, машина заказчика]: ОЖИДАНИЕ ОПРОВЕРГНУТО,
дефект найден и исправлен.** После установки в `Run` появилось значение
`OneCStarter` типа `REG_SZ` длиной **0 символов**. Замер:
`(Get-Item $k).GetValueNames()` показал имя в списке, `GetValueKind` — `String`,
данные — пустая строка.

Причина: `ValueType: string` без `ValueData` создаёт пустую строку, а
`dontcreatekey` этому не мешает — **[из документации Inno Setup]** флаг
относится к КЛЮЧУ, а ключ `Run` существует всегда. Веха полагала, что флаг
покрывает и значение; метка «не проверено» стояла именно поэтому и оказалась
не формальностью.

Цена — ложь о состоянии системы: `is_enabled` возвращал `True` на пустой
строке, раздел «Настройки» показывал автозапуск включённым, а выполнять при
входе было нечего. Пользователь, видя «включено», не стал бы включать —
расхождение не вылечилось бы никогда.

Исправлено в тот же день (ветка `fix/2026-08-21-installer-empty-run-value`):
`ValueType: none` в `installer.iss` (запись живёт только ради
`uninsdeletevalue`) плюс `is_enabled` считает включённым лишь непустое
значение — второе нужно и само по себе, для машин, где пустая запись уже
появилась. Спека §3.5 переписана.

**Повторная проверка после правки — [Проверено, 21.08.2026]: значение больше
не создаётся.** Порядок был такой: пустая запись убрана из реестра точечно
(`Remove-ItemProperty` только по имени `OneCStarter`, прочие 17 значений ключа
не тронуты), установщик пересобран с `ValueType: none` (ISCC 6.7.3 принял),
установка повторена поверх. После неё `GetValueNames()` имени `OneCStarter`
не содержит, `unins000.exe` обновлён — то есть деинсталлятор в системе теперь
новый, с исправленной записью.

Материал для шага А6 при этом не потерян: значение туда штатно положит шаг А4
(тумблер в приложении), и А6 проверит ровно то, что и требовалось, — удаляет ли
`uninsdeletevalue` значение, которого установщик не создавал.

### А4. Включение автозапуска из приложения

Запустить установленный `OneCStarter.exe`, раздел «Настройки» → включить
«Запускать при входе в Windows». Затем повторить запрос из А3.

Критерии:

- тумблер **не заблокирован** и не несёт подписи «Доступно в установленной
  версии…» (признак `sys.frozen` виден — спека §3.3);
- значение появилось, тип `REG_SZ`;
- данные **дословно**: `"%LOCALAPPDATA%\Programs\OneCStarter\OneCStarter.exe" --autostart`
  — путь в кавычках, аргумент за закрывающей кавычкой, путь ведёт в каталог
  установки, а не в исходники и не в `dist`.

**Результат — [Проверено, 21.08.2026, машина заказчика]: всё три критерия
выполнены.** Тумблер активен и не несёт подписи про исходники — значит
`sys.frozen` в установленной сборке виден. Значение появилось, тип `REG_SZ`,
длина 79 символов, данные (путь обезличен — в реальном стоит профиль
пользователя):

```text
"%LOCALAPPDATA%\Programs\OneCStarter\OneCStarter.exe" --autostart
```

Сверка с ожиданием `autostart_command(sys.executable)` — совпадение дословное,
символ в символ: кавычки вокруг пути, аргумент за закрывающей кавычкой, путь
ведёт в каталог установки, а не в `dist` и не в исходники.

### А5. Тихий старт настоящим входом в систему

Закрыть приложение, выйти из системы и войти снова (или перезагрузиться).

Критерии (спека §3.4):

- окно **не появляется**;
- значок в трее есть;
- глобальное сочетание поднимает окно с фокусом в поиске;
- в `%APPDATA%\OneCStarter\logs\onecstarter.log` — строка
  `тихий старт: окно скрыто, программа в трее`.

**Результат — [Проверено, 21.08.2026, машина заказчика]: все четыре критерия
выполнены.** В логе появилась строка
`18:26:44,137 INFO onecstarter.startup: тихий старт: окно скрыто, программа
в трее` — до этого лог знал только `окно показано`. Процесс поднялся в 18:26:38
из каталога установки. Окна при входе не было, значок в трее на месте,
`Ctrl+Alt+B` поднимает окно.

Оговорка о способе входа, чтобы запись не обещала лишнего:
`Win32_OperatingSystem.LastBootUpTime` после входа показывал 20.08.2026 14:36,
то есть ядро не перезагружалось. Так выглядит либо выход и вход в систему,
либо быстрый запуск Windows (Fast Startup), при котором время загрузки ядра
не обновляется. **Холодная перезагрузка этим шагом не проверена** — проверено
именно то, что требует спека §3.4: значение из `Run` исполняется при входе
пользователя, и программа стартует в трей без окна.

### А6. Деинсталляция — решающий шаг блока

Закрыть приложение (через меню трея «Выход», не крестиком — при включённом
«закрытии в трей» крестик оставит процесс жить, и деинсталлятор упрётся
в занятые файлы). Удалить: «Параметры → Приложения» или
`%LOCALAPPDATA%\Programs\OneCStarter\unins000.exe`. После — запрос из А3.

Критерии:

- значение `OneCStarter` из `Run` **исчезло**;
- `%APPDATA%\OneCStarter\` (история, избранное, настройки) на месте —
  `[UninstallDelete]` в `installer.iss` затрагивает только служебный каталог сборки и сам `{app}`, до пользовательских данных не дотягивается;
- `%APPDATA%\1C\1CEStart\ibases.v8i` не тронут.

**Результат — [Проверено, 21.08.2026, машина заказчика]: главное утверждение
блока подтверждено.** Значение `OneCStarter` **исчезло** из `Run` после
деинсталляции — то есть `uninsdeletevalue` удаляет значение, которого
установщик не создавал (его записало приложение шагом А4). Именно это стояло
в спеке §3.5 с меткой «[Из документации Inno Setup, не проверено]» с самого
начала вехи; метка снимается.

**Чистота доказательства** (уточнено по находке финального ревью ветки).
Первый цикл шёл поверх прежней установки, а `UninstallLogMode` по умолчанию —
`append`: теоретически сработать могла запись, зарегистрированная ещё сборкой
с `ValueType: string`. Шов снят вторым циклом того же дня: каталог установки
к тому моменту был удалён полностью, установка шла с нуля (лог деинсталляции
создан заново), автозапуск включался заново тумблером в шаге В7 — и значение
снова исчезло после удаления. Значит удаление регистрирует именно запись
с `ValueType: none`.

Прочие 17 значений ключа `Run` целы — чужой автозапуск не тронут. Данные
пользователя на месте: `%APPDATA%\OneCStarter\` с `logs`, `bases.json`,
`settings.json`; `ibases.v8i` цел (16 565 байт). Ярлык из «Пуска» удалён.

**Минорная находка того же шага: оставался скелет пустых каталогов.**
В `%LOCALAPPDATA%\Programs\OneCStarter` после удаления остались шесть пустых
каталогов — `_internal` и внутри него `PySide6`, `shiboken6`, `plugins`,
`platforms`, `styles`. Файлов нет, данных нет, места не занимают. Причина:
`[Files]` с `recursesubdirs` регистрирует файлы, а вложенные каталоги
установщик сам по себе не убирает.

**Закрыто и перепроверено 22.08.2026.** В `installer.iss` добавлена секция
`[UninstallDelete]` (`filesandordirs` для `{app}\_internal`, затем `dirifempty`
для `{app}`), установщик пересобран, программа поставлена и удалена ещё раз:
каталог `%LOCALAPPDATA%\Programs\OneCStarter` **исчез полностью**. Тем же
циклом второй раз подтвердилось удаление значения из `Run` и сохранность
пользовательских данных (`%APPDATA%\OneCStarter` — три элемента на месте).

**Новое наблюдение того же замера, важное для находки В7: метка
`StartupApproved` деинсталляцию переживает.** После полного удаления
программы запись `Explorer\StartupApproved\Run\OneCStarter` осталась в реестре.
Практическое следствие: если пользователь однажды отключил автозапуск через
«Диспетчер задач», то и переустановка не поможет — свежая программа включит
значение в `Run`, а Windows по-прежнему будет считать автозапуск отключённым.
Ни удаление, ни повторная установка следов этого не оставляют. Ещё один довод
за подсказку у тумблера: без неё пользователь не имеет ни одного способа
догадаться, почему автозапуск молчит.

Ошибок Windows не показала, процесса нет, значения в `Run` нет. Проверено
и по третьему следу, которого заказчик видеть не мог: в
`%APPDATA%\OneCStarter\logs\onecstarter.log` после `18:26:45` не появилось
ни строки — то есть программа при входе не стартовала и молча не падала.
Именно этот исход и был целью правки `[Registry]`: после удаления в системе
не остаётся ссылки на стёртый exe.

### Если А6 провалился

Значение осталось в `Run` после деинсталляции — `uninsdeletevalue` не покрывает
значение, созданное не установщиком. Кандидаты, по убыванию предпочтения:

1. `[UninstallRun]` с `reg delete "HKCU\...\Run" /v OneCStarter /f` и флагом
   `runhidden` — прямое удаление, не полагается на учёт записей Inno Setup;
2. Pascal-скрипт `CurUninstallStepChanged` (`usUninstall`) с `RegDeleteValue` —
   тот же эффект, но условиями и логированием управляем мы;
3. добавить к существующей строке флаг `deletevalue` — **отвергнуть, не обсуждая**:
   он удалит значение при **установке**, то есть обновление версии молча
   выключит пользователю автозапуск.

Выбор — решение заказчика; после правки блок А прогоняется заново целиком,
начиная с А1.

## Блок Б — раскладка клавиатуры (закрывает пункт 2 и ставит новый вопрос)

Офскрин-тесты строят `QKeyEvent` с явным `Qt.Key`, минуя нативную трансляцию
скан-кодов: драйвер клавиатуры в них не участвует вовсе. Что физически приходит
в [hotkey_edit.py](../../src/onecstarter/ui/hotkey_edit.py) при русской раскладке,
показывает только железо.

Набор допустимых клавиш узкий намеренно (`services/hotkeys.py`): `A`–`Z`,
`0`–`9`, `F1`–`F12`. Кириллической буквы в нём нет и не будет.

### Б1. Захват сочетания на клавише с латинским эквивалентом

**Шаг переписан 20.08.2026 по находке финального ревью ветки (п. Б-2, Б-3).**
Прежняя редакция называла проверяемой клавишей `Ctrl+Alt+Б` и объявляла
правильным исходом «поле не изменилось». Обе части неверны:

- на клавише позиции `B` в русской раскладке стоит **«И»**, а не «Б»
  (ЙЦУКЕН, нижний ряд `ZXCVBNM` → `ЯЧСМИТЬ`); «Б» живёт на запятой
  и относится к классу шага Б2 — значит прогон 20.08.2026 фактически
  дважды проверил Б2 и ни разу не проверил Б1;
- после правки захвата (`fix/2026-08-20-hotkey-capture-layout`) «поле
  не изменилось» — это **дефект, а не норма**. Оставь таблицу как была,
  и следующий исполнитель запишет регрессию как «задумано».

Русская раскладка активна. В поле «Глобальный вызов окна» (в поле стоит
`Ctrl+Alt+G` — сначала назначьте его на латинице) нажать **Ctrl+Alt+И**,
то есть физическую клавишу позиции `B`.

| Исход | Что видно | Оценка |
| --- | --- | --- |
| а | В поле встало `Ctrl+Alt+B` | **Правильно.** Имя взято у драйвера (`VK_B`, `0x42`) — того же кода, на который подпишется `RegisterHotKey` |
| б | Поле не изменилось, осталось `Ctrl+Alt+G` | **Дефект — регрессия правки.** Ровно то, что чинила ветка `fix/2026-08-20-hotkey-capture-layout` |
| в | Поле опустело или встало что-то третье | **Дефект.** Записать точно, что встало, и сравнить с логом |

**Результат — [Проверено, 20.08.2026, машина заказчика]: исход «а».** Проверено
шагом В3 после правки: при активной русской раскладке `Ctrl+Alt+B` встал в поле,
чего до правки сделать было нельзя. Прогон до правки давал исход «б» — он и стал
находкой.

### Б2. Кириллическая буква без латинского эквивалента по позиции

Там же нажать **Ctrl+Alt+Ё**, **Ctrl+Alt+Ж** и **Ctrl+Alt+Б** (позиции
`` ` ``, `;` и `,` — клавиши, у которых нет буквенного латинского
эквивалента, а значит нет и VK в нашей таблице: драйвер шлёт `VK_OEM_*`).

Критерий: поле не меняется ни в одном случае, уже назначенное сочетание цело.
Принятие любого из них — дефект: сочетание встало бы на экране, а
`RegisterHotKey` подписался бы не на ту клавишу.

**Результат — [Проверено, 20.08.2026, машина заказчика]:** поле не изменилось
ни на `Ё`, ни на `Ж`. **`Б` проверена тем же прогоном** — заказчик нажимал
именно её, полагая (как и текст протокола до правки), что она сидит на клавише
`B`; фактически это третий случай Б2, и он тоже дал отказ.

### Б3. Срабатывает ли назначенное сочетание при русской раскладке

**Этот вопрос веха не задавала ни разу** — ни тесты (живой `RegisterHotKey`
они не трогают), ни эксперимент §7 (синтез `keybd_event` шёл при латинской
раскладке). Между тем русская раскладка у пользователя основная, и если
`Ctrl+Alt+B` при ней не срабатывает, глобальный вызов не работает большую часть
рабочего дня — это дороже обоих пунктов «Непроверенного честно».

Порядок: сочетание `Ctrl+Alt+B` назначено, окно свёрнуто или спрятано в трей.

1. Латинская раскладка — нажать Ctrl+Alt+B. Ожидание: окно поднимается,
   фокус в поиске.
2. Переключиться на русскую, нажать **ту же физическую клавишу** (позиция
   латинской `B`, русская «И»). Записать, поднялось ли окно.
3. Свернуть, вернуться на латинскую, повторить — убедиться, что регистрация
   не потерялась после переключения раскладки.

**Результат — [Проверено, 20.08.2026, машина заказчика]: работает на обеих
раскладках.** `Ctrl+Alt+B` поднимает окно и при активной английской, и при
активной русской раскладке; переключение раскладки регистрацию не теряет.
Глобальный вызов раскладко-независим — то есть VK-код, приходящий от драйвера
для клавиши позиции `B`, при русской раскладке тот же `0x42`, и `RegisterHotKey`
получает ровно то, на что подписан.

Замечание о ходе проверки, важное для следующего исполнителя: **первый ответ
заказчика был «не поднялось» и оказался ошибочным** — его опроверг контрольный
замер той же клавиши на английской раскладке в том же сеансе, без перезапуска
программы. Одиночный отрицательный замер вручную не является фактом: пропущенное
нажатие, окно не в том состоянии, промах по клавише выглядят точно так же, как
дефект. Ручную проверку хоткея ставить только парой «рабочий случай рядом
с проверяемым», иначе протокол зафиксирует несуществующий дефект и следующая
сессия пойдёт чинить работающий код.

## Блок В — прогон четырёх настроек на живой машине

Offscreen-платформа маскирует шрифтозависимое (правило вехи 4b); плюс несколько
поведений принципиально не воспроизводятся в тестах — балун трея, реальный
крестик окна, настоящая занятость сочетания.

Порядок в блоке важен: В1 меняет сочетание, В3 его выключает, В4 возвращает.

### В1. Смена сочетания на лету

«Настройки» → поле сочетания → нажать `Ctrl+Alt+G`. Свернуть окно, нажать
`Ctrl+Alt+G`.

Критерии: окно поднялось с фокусом в поиске; **старое** `Ctrl+Alt+B` больше
не поднимает ничего (старая регистрация снята — спека §4.2); тултип значка
трея — `OneCStarter — Ctrl+Alt+G`; в `settings.json` поле `hotkey` = `Ctrl+Alt+G`.

**Результат — [Проверено, 20.08.2026, машина заказчика]: перерегистрация
работает.** Новое сочетание поднимает окно, старое `Ctrl+Alt+B` не поднимает
ничего — старая регистрация снята, как и предписывает §4.2.

**Побочно найден дефект, которого протокол не предусматривал.** Вернуть
`Ctrl+Alt+B` заказчик не смог: при активной русской раскладке поле захвата
молча не реагировало на нажатие. Это не промах пользователя (трактовка **Б2**,
где нажатие действительно непригодно, сюда не распространяется) — сочетание
существует, допустимо и, по результату Б3, срабатывает при любой раскладке. Захват оказался строже системы: он читал
раскладко-зависимый `QKeyEvent.key()`, а срабатывание живёт на драйверном
`nativeVirtualKey`.

Закрыто в тот же день, ветка `fix/2026-08-20-hotkey-capture-layout`: имя
клавиши берётся из `nativeVirtualKey` через новую чистую функцию
`key_name_for_vk` (`services/hotkeys.py`), `key()` остаётся запасным путём
для событий, собранных программно. Спека §4.1 переписана **до** кода —
её утренняя редакция объявляла нормой ровно то, что прогон опроверг.
Мутационные проверки — `docs/tasks.md`, раздел «Правка захвата сочетания».

Урок для протокола: находка пришла не из шага, который её искал (блок Б,
специально про раскладку, дал «всё по плану»), а из соседнего шага про
совсем другое. Сценарий «верните как было» ценнее проверки «работает ли
новое»: возврат проходит по тем же путям, но в состоянии, которого автор
не предусматривал.

### В2. Занятое сочетание

**`Win+L` для этого не годится — проверено 20.08.2026 и опровергнуто.** Поле
не приняло сочетание вовсе: Windows перехватывает `Win+L` ниже уровня приложения
(экран блокируется), и до `keyPressEvent` нажатие не доходит. Первая редакция
этого шага предлагала `Win+L` как «самый дешёвый источник занятости» — способ
оказался нерабочим, а не просто неудобным.

**Рабочий способ — второй экземпляр программы с изолированным каталогом данных.**
Обе копии иначе делили бы один `settings.json` и одну историю, и прогон портил бы
рабочие данные. Подмена `APPDATA` разводит их полностью — `ibases.v8i`, `bases.json`,
`settings.json` и лог берутся из подменённого каталога (`build_runtime`,
`ui/app.py`), тем же приёмом пользуется `build/smoke.py`.

Подготовка каталога (один раз):

```powershell
New-Item -ItemType Directory -Force "e:\tmp\onecstarter-second\1C\1CEStart" | Out-Null
# ibases.v8i с одной секцией-пустышкой Demo — её и покажет второй экземпляр
```

Запуск — **обязательно одной строкой**: переменная и запуск должны попасть в один
процесс, иначе подмена не доедет и замер окажется недействительным (эта ошибка
случилась в прогоне 20.08.2026 и была поймана только тем, что в изолированном
каталоге не оказалось ни лога, ни `settings.json`):

```powershell
$env:APPDATA="e:\tmp\onecstarter-second"; uv run python -m onecstarter
```

Признак, что изоляция сработала: в списке второго экземпляра **ровно одна база
`Demo`**. Виден обычный полный список — подмена не состоялась, замер недействителен.
Проверка постфактум: в `e:\tmp\onecstarter-second\OneCStarter\logs\onecstarter.log`
обязана появиться строка `окно показано`, а рядом — созданный `settings.json`.

Порядок: первый экземпляр запущен и держит `Ctrl+Alt+B` (после шага В3 хоткей
выключен — назначить заново!), затем стартует второй с тем же сочетанием
по умолчанию. Один запуск закрывает сразу и В2, и В4.

Прежний, отвергнутый вариант шага (оставлен как предостережение): назначить `Win+L`.

Критерии (спека §4.2 — «сохранено, сейчас занято»):

- у поля появилась строка `Сочетание Win+L занято другим приложением`;
- **значение всё равно сохранено** в `settings.json` (проверить файл);
- тултип трея — `OneCStarter — Win+L занято другим приложением`;
- модального окна нет.

**Результат — [Проверено, 20.08.2026, машина заказчика]: занятость видна, оба
шага закрыты.** Второй экземпляр при старте получил отказ регистрации: всплыл
балун трея и у поля в разделе «Настройки» встала строка об отказе. Это закрывает
и В2 (занятое сочетание), и В4 (занято на старте) — балун плюс постоянная строка,
без модального окна, ровно как требует спека §4.3.

**Оговорка о чистоте замера, существенная для доверия к записи.** Изоляция
каталога данных в этом прогоне **не состоялась**: в `e:\tmp\onecstarter-second`
не появилось ни `settings.json`, ни единой строки в логе, тогда как живой
`%APPDATA%\OneCStarter\logs\onecstarter.log` содержит два старта — 22:06:55
и 22:14:51. То есть оба экземпляра работали на общем каталоге данных.

На вывод это не влияет, и вот почему: занятость сочетания создаётся
конкуренцией двух процессов за одну регистрацию `RegisterHotKey`, а не
разделением файлов. Изоляция нужна была лишь для сохранности рабочих данных
(общий `settings.json` у двух писателей — источник путаницы), и её отсутствие
делает прогон грязным, а не недействительным. Признак «одна база `Demo`
в списке», предложенный выше как маркер изоляции, в этом прогоне
не подтверждён — при общем каталоге он и не мог сработать.

Метод для следующего раза уточнён: изоляция каталога — требование гигиены,
а не условие замера; проверять её надо **до** выводов, по наличию строки
`окно показано` в логе изолированного каталога, а не по виду списка баз.

Шаг 3 — единственная проверка, ради которой в коде живёт `showEvent`;

**Результат — [Проверено, 22.08.2026, машина заказчика]: шаги 1 и 2 прошли,
шаг 3 вскрыл третий дефект прогона.** Включение и выключение тумблером
работают: значение в `Run` появляется и исчезает.

Шаг 3 (внешняя правка через «Диспетчер задач») **опроверг ожидание протокола**.
Тумблер остался включённым — но виноват не ресинхронизация, как предполагалось
в скобках прежней редакции. Замеры после «Отключить»:

| Что | Значение |
| --- | --- |
| `Run\OneCStarter` | на месте, 79 символов — Диспетчер его **не удаляет** |
| `Explorer\StartupApproved\Run\OneCStarter` | появилась метка, первый байт `0x01` |
| Диспетчер задач, колонка «Состояние» | «Отключено» |

То есть автозапуск у Windows определяется **парой** значений, а мы читаем
только одно — и потому честно показываем «включено» у мёртвой записи.

**Ловушка проверена отдельным экспериментом и подтверждена:** выключение
и повторное включение тумблером перезаписали значение в `Run`, а метка
осталась `0x01`. Значит после «Отключить» в Диспетчере наш раздел бесполезен —
что бы пользователь ни делал, автозапуск не заработает, а тумблер показывает
включённым.

Кодировку метки использовать не стали. Наблюдения первого байта, собранные
на одной машине:

| Запись | Состояние | Первый байт |
| --- | --- | --- |
| наша, после «Отключить» в Диспетчере | отключено | `0x01` |
| наша, после «Включить» в Диспетчере | включено | `0x00` |
| соседние (13 штук) | включено | `0x02` |
| соседние (5 штук) | отключено | `0x03` |

Правило «младший бит взведён — отключено» согласуется со всеми четырьмя
наблюдениями, и это лучшая имеющаяся гипотеза. Но формат официально
не документирован, а одна машина уже дала **две разные пары** кодов для одних
и тех же состояний (`0x00`/`0x01` у нашей записи против `0x02`/`0x03`
у соседних) — то есть старшие биты несут что-то ещё, чего мы не знаем.
Строить показ состояния на такой основе значило бы врать увереннее, чем
сейчас. Таблица оставлена здесь на случай, если решение когда-нибудь
пересмотрят: тогда начинать надо не с нуля, а с проверки этой гипотезы
на нескольких машинах.

Решение заказчика 22.08.2026 — честный минимум без чтения недокументированного:
постоянная строка под тумблером «Отключённый в „Диспетчере задач“ автозапуск
включается только там же». Подсказка размыкает тупик, расхождение остаётся;
спека §3.1 дополнена, тест `test_autostart_row_warns_about_task_manager`
проверяет текст **на экране**, а не константу.

Побочное наблюдение заказчика: в списке автозагрузки Windows программа
называется «Запуск информационных баз 1С:Предприятие» — это `FileDescription`
из метаданных exe, а не имя `OneCStarter`. Не дефект, но в Диспетчере наша
строка ищется не по тому имени, к которому пользователь привык.

### В8. Тема и сохранность соседних настроек

Сменить тему из меню трея, затем открыть «Настройки».

Критерии: сегмент темы показывает новое значение; три остальные настройки
на месте, значения не сбросились (единый писатель `SettingsStore` —
спека §6.2); в `settings.json` все пять ключей (`schema`, `theme`,
`close_to_tray`, `hotkey`, `recent_limit`).

**Результат — [Проверено, 20.08.2026, машина заказчика]: тема подхватилась,
остальное цело.** Смена темы из трея приводит сегмент раздела к новому значению
и не сбрасывает три другие настройки — то самое, ради чего вводился единый
писатель (`ThemeController.set_mode` до вехи писал `Settings(theme=mode)`,
то есть целый файл из одного поля).

Файл сверен отдельно и после того, как на общем каталоге успели поработать
**два процесса разом** (см. В2/В4): все пять ключей на месте, `schema` равна 1,
значения осмысленные. Атомарная запись двух конкурирующих писателей файл
не порвала — незапланированная, но полезная проверка инварианта 4.
