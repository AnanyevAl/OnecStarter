## Блок А — вывод и окна (можно частично подставными процессами)

### А1. Наследование файлового stdout детьми (T-09.2)

Вопрос: пишут ли дети ragent (`rmngr`/`rphost`/`dbgs`/`dbda`) в файл,
в который перенаправлен stdout ragent; не рвут ли записи друг друга.

Шаги: запуск ragent через `Start-Process -RedirectStandardOutput
e:\tmp\t09\srv1.log -RedirectStandardError e:\tmp\t09\srv1.err`
(окно при этом скрыть `-WindowStyle Hidden`); подождать подъёма дерева;
прочитать файл — есть ли строки «Cluster Manager … started», «Working
Process … started» (их печатают дети — видно на скриншоте заказчика
28.08.2026).

Ожидание [Р]: консольные дети наследуют std-handles родителя по
умолчанию — строки детей окажутся в том же файле.

Результат: **DONE, [Ф] 28.08.2026 — ожидание ОПРОВЕРГНУТО.** Три
конфигурации: (1) DETACHED (наша сборка) — каждый ребёнок открывает
СВОЁ окно и печатает баннер туда; (2) скрытая консоль + редирект —
окон нет, в файле только строка dbgs, баннеров rmngr/rphost нет нигде;
(3) видимая консоль + редирект — окно ragent остаётся ПУСТЫМ
(наблюдение заказчика, повторное через минуты), в файле снова только
dbgs, дерево при этом полное (rmngr+rphost живы). Вывод: **баннеры
rmngr/rphost существуют только в их собственных окнах** — при
унаследованной консоли (видимой или скрытой) они не печатаются ни
в неё, ни в перенаправленный stdout. Захвату файлом/общей консолью
их вывод недоступен; ловится только stdout-канал (dbgs, потенциально
ragent — который молчит и об ошибках, [Ф] T-07 А3/А4). [Р] ConPTY,
скорее всего, так же не даст баннеров — дети наследовали бы
псевдоконсоль, как в конфигурации 3 наследовали настоящую; проверка —
отдельный эксперимент при желании. Оговорка честности: жёсткое
завершение (TerminateProcess) буферы не флашит, поэтому «буферизация»
как объяснение не исключена ТОЛЬКО для конфигурации 2; конфигурация 3
с минутами ожидания и пустым окном закрывает вопрос практически.

Куда: спека §12.5 ПЕРЕСМАТРИВАЕТСЯ — «консоль профиля» не может быть
зеркалом вывода платформы (его почти нет); решение заказчика о судьбе
панели — см. tasks.md T-09.

Дополнение [Ф] 29.08.2026 (ручной чек-лист T-10, собранный exe, HEAD
`a39bf29`, `.superpowers/sdd/2026-08-28-v2-servers-journal/
manual-checklist.md`, «Шаг 2»): в журнал профиля из СОБРАННОГО
приложения (не из этих подставных экспериментов) попали ТРИ баннера
платформы — `Server Agent (debug by http) started`, `Search server
(debug by http) started`, `Debug Server started` — больше, чем один
dbgs, зафиксированный экспериментом выше (профиль с `-debug -http`,
которого не было в конфигурациях А1). rmngr/rphost по-прежнему не
попали ни разу — согласуется с выводом выше. Вывод А1 («баннеры
rmngr/rphost не попадают в файл») подтверждён; список того, что
ловится stdout-каналом при живом профиле, шире одного dbgs и зависит
от флагов `-debug`/`-http` профиля.

## Блок Б — Job Object (агент может подставными, финал — живым ragent)

### Б1. Job kill-on-close убивает подставное дерево (T-09.5а)

Шаги (агент, без 1С): python-процесс, порождающий внука; оба в Job
c `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; закрыть handle Job — оба мертвы.

Результат: **DONE, [Ф] 28.08.2026, агентом.** Родитель в Job, внук
унаследовал Job автоматически; до `CloseHandle` оба живы, после —
оба мертвы («убиты оба — kill-on-close работает на дереве»).
Структуры `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` подтверждены живым
вызовом (`SetInformationJobObject` код успеха).

Куда: `platform_1c` Job-модуль T-10 (интеграционный тест повторит).

### Б2. Живое дерево ragent в Job (T-09.5б, T-09.7)

Вопрос: ragent, запущенный в Job, штатно поднимает детей; дети
(включая dbgs/java) наследуют Job (нет `CREATE_BREAKAWAY`); закрытие
handle Job гасит всё дерево разом; кластер после этого поднимается
(целостность — как [Ф] Б2 T-07).

Шаги: запуск ragent в Job (скрипт подготовит веха), снять дерево,
закрыть Job-handle, снять процессы (пусто), перезапустить на том же
`-d` — тот же `clstid`.

Результат: **DONE, [Ф] 28.08.2026 (скрипт агента, запуск заказчиком).**
ragent в Job поднял ПОЛНОЕ дерево — ragent, conhost, rmngr, dbgs,
rphost, dbda — все дети унаследовали Job (заодно закрыт T-09.7:
breakaway не используется). `CloseHandle(job)` погасил дерево целиком,
выживших нет. Перезапуск на том же каталоге — порт слушается, кластер
цел (согласуется с [Ф] Б2 T-07 о безопасности жёсткого завершения).
Попутно: Касперский НЕ блокирует цепочку python→ragent из терминала
заказчика (в отличие от агентской цепочки).

Куда: §12.4 — гарантия «выход/крах лаунчера гасит серверы» измерена;
Job-модуль T-10 строится по этому скрипту (e:\tmp\t09\b2_job.py —
эталон структур и последовательности).
