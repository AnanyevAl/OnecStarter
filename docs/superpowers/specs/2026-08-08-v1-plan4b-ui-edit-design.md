## 1. Витрина размещения: значок и панель пути

### 1.1. Где живёт расчёт

Новый модуль **`services/connection.py`** — «что показать про размещение записи».
Без Qt (инвариант 1), табличные тесты.

Не в `services/display.py`: тот уже 212 строк и отвечает за *дерево и его строки*.
Разбор строки соединения — другая ось. Два модуля по ~200 строк с ясной границей
лучше одного на 350.

Вырезание учётных данных из URL — **`security/secrets.py`**, рядом с `redact_connect`
(инвариант 5: что является секретом и как он убирается, определено в одном месте).

### 1.2. `strip_url_credentials`

```python
def strip_url_credentials(url: str) -> str | None:
    """Адрес без user:pass@. None — вырезать надёжно не вышло, показывать нельзя."""
```

Разбор через `urllib.parse.urlsplit`, **не своей регуляркой**. Причина конкретная:
у `http://user:pa/ss@host/` наивный поиск `@` до первого `/` не срабатывает
и оставляет `ss@host` в пути. Стандартный парсер режет по RFC; строку с таким
незакодированным паролем и платформа не приняла бы.

Адрес собирается заново из `hostname` (+ порт), после чего — тот же fail-closed
приём, что уже стоит в `redact_connect._leaks_secret`: **если в результате `@`
всё ещё есть, возвращается `None`**. Это ловит `urlsplit("user:pass@host/base")`,
где парсер принимает `user` за схему.

Защитный тест → мутационная проверка обязательна (§9).

**[Ф] обоснование существования правила:** `services/launch.py` уже не пускает URL
веб-базы в сообщение об ошибке — ровно потому, что `ws` может нести учётные данные.
**[Д] непроверенное:** сама форма URL веб-базы из `ws` экспериментально не снята
(T-05.11 опционального блока В не проводился). Вырезание безопасно в любом случае:
если такой формы нет, вырезать будет нечего.

### 1.3. Значок вида размещения

Требование §9 п. 2 спеки 4a. `ConnectKind` уже различает четыре значения.

| Вид | Значок | Тултип |
| --- | --- | --- |
| `FILE` | папка | файловая база |
| `SERVER` | стойка (три полосы) | серверная база |
| `WEB` | круг с меридианом | веб-база |
| `UNKNOWN` | контур пунктиром с «?» | строку соединения не разобрали |

Три решения:

- **[Р] Отдельной колонки не будет.** Значок ставится через `QStandardItem.setIcon`
  в колонке имени: не съедает ширину и не заводит четвёртую колонку без сортировки.
- **[Р] `UNKNOWN` визуально отличается от трёх известных** — требование §9 п. 2
  спеки 4a: «не прочее, а строку соединения не разобрали». Контур пунктиром
  против трёх заполненных.
- **[Р] Группы, секции и неявные узлы значка не получают.** Их отличает структура
  дерева и жирный шрифт; значок у группы конкурировал бы со значком «файловая».

Иконки **рисуются кодом** в `ui/bases/icons.py` из действующей палитры и создаются
внутри `build_model`. Это даром снимает проблему смены темы: модель и так
пересобирается, значит новой запечённой точки не появляется (ср. §2.4).

### 1.4. Панель пути подключения

Под деревом, `QLineEdit` в режиме read-only — даёт выделение и `Ctrl+C` штатно,
без своего кода.

| Что выделено | Что в панели |
| --- | --- |
| `FILE` | значение `File` как есть (`D:\bases\accounting`) |
| `SERVER` | `Srvr="localhost";Ref="INITKZ-802-1870"` — дословно, как штатный стартер |
| `WEB` | адрес из `ws`, `user:pass@` вырезан |
| `WEB`, вырезать не вышло (`None`) | пометка, поле пустое, «Копировать» недоступно |
| `UNKNOWN` | пометка «строка соединения не распознана», поле пустое |
| группа / секция / неявный узел / нет выделения | пусто, меню недоступно |

Меню панели: **«Копировать»** и **«Открыть каталог»** (только `FILE`).

- Один пункт «Копировать», а не два: раз дополнительных параметров нет нигде,
  пункты штатного стартера «Копировать путь» и «Копировать строку соединения»
  для нас сливаются (решение заказчика 07.08.2026, §9 п. 3 спеки 4a).
- Для `WEB` в буфер идёт **очищенный** адрес (решение заказчика 08.08.2026).
  Обоснование: панель отвечает на вопрос «куда подключаемся», а не «чем
  аутентифицируемся»; адрес остаётся рабочим, браузер спросит пароль сам.
  Буфер обмена читается любым процессом и переживает закрытие программы —
  инвариант 5 распространяется на него так же, как на сообщения об ошибках.
- «Открыть каталог» — через `QDesktopServices`. Каталога нет → сообщение, не тишина.

**Границы (решение заказчика 07.08.2026, повторяется как граница):** в панель
не попадают полная строка `Connect`, `Usr`, `Pwd`, `LocaleCode`, `wsp*`, `PPasswd`
и неизвестные ключи. Если полная строка понадобится — это отдельное решение
с отдельным вопросом о секретах.

## 2. Тема, настройки и раздел «Настройки»

### 2.1. `ui/theme.py`: константы → палитра

```python
@dataclass(frozen=True)
class Palette:
    background: str; surface: str; surface_raised: str; border: str
    text: str; text_dim: str; accent: str; problem: str

DARK  = Palette(..., accent="#f2d54c", ...)   # значения 4a без изменений
LIGHT = Palette(..., accent="#7d6200", ...)   # см. правку контраста в §2.2

# Цвета иконки трея — вне палитры намеренно, см. §2.4.
TRAY_GROUND = "#1e1e1e"
TRAY_MARK   = "#f2d54c"

def stylesheet(palette: Palette) -> str: ...
```

`DARK` повторяет константы 4a один в один — **вид тёмной темы не меняется ни
на пиксель**.

**[Р] Поля `accent_fill` не будет.** В первой редакции дизайна акцент разделялся
на «для текста» и «для заливок», где заливкой была иконка трея. После решения §2.4
(иконка от палитры не зависит) у второго поля не остаётся ни одного потребителя,
а поле без потребителя — заготовка на будущее, которое может не наступить.

**[Р] Палитра не хранится в глобальной переменной модуля.** Она передаётся явно:
`BasesView(..., palette=)`, `build_model(..., palette=)`, `placement_icon(kind, palette)`.
Причина не в чистоте: глобалка потребовала бы сброса в каждом UI-тесте, и забытый
сброс дал бы тест, зелёный из-за соседа.

**[Ф] Правка 09.08.2026 (финальное ревью, замечание M15).** В списке выше стояла
`make_icon(palette)` — этой подписи нет ни в коде, ни в остальном тексте спеки:
`make_icon()` палитру не принимает и принимать не должна, ровно по решению §2.4
(иконка трея от палитры не зависит). Документ противоречил сам себе; исправлен
документ, а не код. Перечислены теперь настоящие потребители палитры — те,
что запекают цвет в объект.

### 2.2. Светлая палитра

Решение заказчика 08.08.2026: **затемнённый янтарь для текста, исходный жёлтый
для заливок.**

| Роль | Светлая | Контраст к худшему фону | Тёмная | Контраст к худшему фону |
| --- | --- | --- | --- | --- |
| `background` | `#ffffff` | — | `#161616` | — |
| `surface` | `#f4f4f4` | — | `#1e1e1e` | — |
| `surface_raised` | `#eaeaea` | — | `#262626` | — |
| `border` | `#d0d0d0` | — | `#333333` | — |
| `text` | `#1a1a1a` | 14,5:1 | `#e8e8e8` | 12,4:1 |
| `text_dim` | `#666666` | 4,8:1 | `#9a9a9a` | 5,4:1 |
| `accent` (текст, рамки) | `#7d6200` | 4,8:1 | `#f2d54c` | 10,4:1 |
| `problem` | `#c62828` | 4,7:1 | `#e57373` | 5,1:1 |

Вне палитры, одинаково в обеих темах: `TRAY_GROUND = #1e1e1e`,
`TRAY_MARK = #f2d54c` (§2.4).

Контрасты — расчёт по формуле WCAG 2.1, порог для обычного текста 4,5:1.
Инверсией ролей задача не решалась: `#f2d54c` на белом даёт **1,5:1**, и та же
беда у `#e57373` (3,0:1) и `#9a9a9a` (2,8:1) — перекрашивать пришлось три роли,
а не одну.

**[Ф] Правка 09.08.2026: контраст меряется к каждому из трёх фонов, а не к
`background`.** Колонка этой таблицы называлась «Контраст к `#ffffff`», и значения
подбирались только к белому. Но `background` — не единственная подложка: `surface`
несёт подписи разделов `NavRail`, заголовок таблицы и поле только для чтения,
`surface_raised` — выделенную строку, меню и подсказку. Оба цвета, подобранных
впритык, порога на них не держали: `text_dim` `#767676` давал **4,13:1** на
`surface`, `accent` `#8a6d00` — **4,47:1** там же. Замерено на пикселях
(offscreen `grab()`, светлая палитра), не выведено на бумаге. Оба затемнены
до значений с запасом — `#666666` и `#7d6200`; тёмная палитра порог держала
на всех трёх фонах и не тронута. Сторожит расчёт в
`tests/ui/test_theme.py::test_text_roles_meet_the_contrast_threshold`,
параметризованный по трём фонам.

Правило намеренно шире сегодняшнего употребления (`problem` на `surface` нигде
не рисуется): дефект родился именно оттого, что проверка была уже употребления.

**[Ф] Выделенная строка дерева к этому отношения не имеет.** Отдельно проверено,
что `QBrush` элемента модели на выделении не побеждает: правило
`QTreeView::item:selected { color: text }` красит текст в `text`, приглушённый
цвет туда не доходит вовсе. Замер — offscreen `grab()` + сэмплинг пикселей
во **всех четырёх** стилях Qt (`windows11`, `windowsvista`, `Windows`, `Fusion`);
без выделения кисть применяется точно (`#767676`, `#c62828` пиксель в пиксель),
с выделением во всех стилях приходит `text`. Выделенная строка даёт 14,5:1.
Приглушённый цвет на `surface_raised` остаётся только у значка размещения,
а он — не текст, и его порог 3:1 (WCAG 1.4.11).

### 2.3. `services/settings.py` — без Qt

```python
class ThemeMode(Enum):
    AUTO = "auto"; LIGHT = "light"; DARK = "dark"

@dataclass(frozen=True)
class Settings:
    theme: ThemeMode = ThemeMode.AUTO
```

Файл `%APPDATA%\OneCStarter\settings.json`, схема `{"schema": 1, "theme": "auto"}`.

**[Р] Отдельный файл, а не ключ в `bases.json`.** §10 спеки 4a утверждает, что
в `bases.json` «места под настройки нет» — это неточно: файл уже имеет конверт
`{"schema": 1, "entries": {…}}`, и соседний ключ туда лёг бы. Настоящая причина
другая: **`bases.json` при порче уезжает в `.bad`** (`user_data.py:_move_aside`),
и настройка темы уехала бы вместе с историей запусков, будучи ни при чём.
Разные времена жизни и разная частота записи → разные файлы.

**[Р] Политика отказов намеренно не такая, как у `bases.json`.** `load_user_data`
при недоступном файле поднимает `UserDataUnavailableError` и валит старт: подмена
пустыми данными затёрла бы историю. У настроек цена ошибки другая — теряется выбор
темы. Поэтому:

- файл нечитаем или испорчен → значения по умолчанию, приложение стартует;
- неизвестное значение `theme` → `AUTO` (совместимость вперёд, не порча);
- сохранить не удалось → тема применена в этом сеансе, но не запомнена, и раздел
  «Настройки» показывает строку с причиной. Не модальное окно и не тишина.

Правило одной фразой: **работа с `settings.json` никогда не мешает работе программы.**

### 2.4. Определение системной темы и `ThemeController`

Заказчик выбрал три состояния: **Авто / Светлая / Тёмная, по умолчанию Авто.**

**[Д] не проверено:** системная тема читается через
`QGuiApplication.styleHints().colorScheme()`, смена ловится сигналом
`colorSchemeChanged`. Это лучше чтения `AppsUseLightTheme` из реестра — реестр
не даёт сигнала, пришлось бы опрашивать. **Первым шагом задачи проверить**, что
PySide6 6.10 это отдаёт и что сигнал приходит при смене темы Windows. Если нет —
запасной путь через реестр, и тогда «Авто» применяется при старте, а не на лету.
Догадку за факт не выдаём. `ColorScheme.Unknown` → тёмная, как сейчас.

`ThemeController` (в `ui/`) владеет режимом, вычисляет действующую палитру,
применяет её и сохраняет выбор. Применение — **два действия**:

1. `application.setStyleSheet(theme.stylesheet(palette))`
2. `bases_view.apply_palette(palette)` — кладёт палитру и зовёт `rebuild()`,
   тем самым перекрашивая `QBrush` строк и перерисовывая значки размещения

Вариант «применится после перезапуска» отклонён: платить перезапуском за две
строки нечем.

**[Р] Иконка трея от палитры не зависит — и это ответ на вторую запечённую точку
из §10 спеки 4a, а не забывчивость.** §10 предполагала перерисовку иконки при
смене темы. Так делать нельзя: **панель задач красится системной темой, а не
нашей**, и при явно выбранной (не «Авто») теме они расходятся — светлый значок
оказался бы на тёмной панели или наоборот. Прямая беда обнаружилась при
самопроверке этого дизайна: `make_icon` заливает поле цветом `surface`, в светлой
палитре это `#f4f4f4`, и жёлтый треугольник на нём даёт **1,4:1** — значок пропал
бы с панели. Поэтому иконка рисуется фиксированными `TRAY_GROUND` / `TRAY_MARK`:
тёмное поле с жёлтым треугольником читается и на светлой панели, и на тёмной.

`SettingsView` палитру тоже не получает: его радиокнопки и подписи целиком
красит общий stylesheet, собственных `QBrush` и `QPixmap` у него нет. Палитра
нужна только тем виджетам, которые **запекают цвет в объект**.

Путь `settings.json` собирается в `ui/app.py` — там же, где `bases.json`
и `ibases.v8i`: это единственное место, где `ui` знает про расположение файлов
(§1 спеки 4a).

«Обзор…» — жест экономит один клик. Ценность приёма именно в броске на список.
Разбор — план 4b, «Замечания ручного smoke №2», замечание 1. Дизайн — §3.4 ниже,
реализация — задача 20.

Три решения:

- **[Р] `DefaultVersion` не правится, только показывается.** [Ф] скил `v8i-format`,
  факт 3: точная `Version` побеждает `DefaultVersion`, значит при явном выборе
  версии снимать его не нужно. Пояснение в диалоге показывается только когда он
  действительно решает — при неполной или пустой `Version` ([Ф] T-05.5:
  `DefaultVersion` побеждает маску даже вне её).
- **[Р] Секретные значения не редактируются, а скрываются.** Хранение паролей вне
  v1 (§0 спеки 4a), поэтому поле правки пароля создавало бы способ записать пароль
  в `.v8i` открытым текстом. `PPasswd` добавляется в `security.secrets._SECRET_KEYS` —
  обязательство 2 ревью плана 3 исполняется ровно тем, что значение не показывается.
  Суффиксное правило `endswith("pwd")` его не ловит: `ppasswd` кончается на `sswd`.
  **Шагом задачи** — сверить `reference.md` скила `v8i-format` на другие ключи секции
  с секретами, а не считать `PPasswd` единственным по памяти.
- **[Р] Произвольная правка ключей — вне 4b.** Показываем, не даём править. Общий
  редактор ключей открывает класс порчи, который наши проверки не ловят: [Ф] факт 6
  скила — `Connect` с пробелом вокруг `=` платформа не распознаёт и добивает секцию
  необратимо.

**[Ф] Правка 09.08.2026 по итогам финального ревью (замечания I8 и N3): имя
и размещение обязательны, и «ОК» неактивна, пока они не заполнены.** Пробел
был в спеке, а не только в коде: таблица выше требует валидации только для
имени (`validate_section_name`), про размещение не сказано ничего — и `Ctrl+N`
с одним заполненным именем давал `File="";`, то есть запись с пустым путём
в файле, общем со штатным стартером.

Правило: **«ОК» неактивна, пока пусто хотя бы одно обязательное поле —
имя или поле размещения выбранного вида**, а рядом с кнопкой стоит пояснение,
что именно заполнить. Это тот же принцип, что и у неактивных пунктов меню для
общего списка (§3.2): отказ показывается раньше, до действия, а не сообщением
после клика. Поля размещения — по видам: файловая — «Путь»; серверная —
«Сервер» **и** «Имя базы на сервере» (одного `Srvr` без `Ref` для запуска мало);
веб — «Адрес». Пустым считается и значение из одних пробелов.

**Правило распространилось на имя по итогам ре-ревью (N3).** Первая редакция
закрывала только размещение, потому что имя уже было защищено
`validate_section_name` в `services`. Защита есть, но срабатывает **после**
нажатия «ОК», и внутри одного диалога получалось противоречие: поле пути
запирает кнопку до клика, поле имени — нет. Решение заказчика 09.08.2026
(«отказ показывается до действия») действует на оба поля одинаково.
`services` при этом остаётся вторым, самостоятельным рубежом: методы записи
достижимы напрямую, в обход кнопки.

Два исключения, оба про уже существующую запись, которой пустого размещения
мы не создаём:

- поле, чей фрагмент в `Connect` не нашёлся (нередактируемое, `_init_placement`,
  C3 круга правок 1 задачи 9), «ОК» не запирает — заполнить его нельзя,
  а запись открыта, возможно, ради правки версии или группы;
- у записи вида `UNKNOWN` полей размещения нет вовсе, и требовать нечего.

Оба исключения — только про размещение: имя есть у любой секции по определению
формата, и пустым оно быть не может ни у существующей записи, ни у новой.

Здесь же исполняется обязательство §4 спеки 4a: при `NOT_INSTALLED`/`INVALID_REQUEST`
диалог подсвечивает проблему и **предлагает выбрать установленную версию** —
в 4a были только подсветка и подсказка без возможности исправить.

### 3.2. Удаление

- **Запись** — подтверждение с явным «файлы базы не трогаются».
- **Группа** — до 10 элементов перечисляются именами, больше — количеством; выбор
  «удалить с содержимым» (`RECURSIVE`) или «поднять к родителю» (`PROMOTE`).
  Обязательство 3 блока Б: [Ф] T-05.9 — платформа спрашивает «Удалить группу
  "имя"?» и каскадит молча, быть не хуже недостаточно. Расчёт содержимого —
  чистая функция в `services`, табличные тесты.

**[Ф] Правка 09.08.2026 по итогам финального ревью (замечание I7): решение
«можно ли» принимается один раз, до показа меню, — и для записей тоже.**
Правило завёл круг правок 1 задачи 12, но применили его тогда только к группам
(`_group_menu_for`: три неактивных пункта с пояснением `COMMON_NOTE`). У записи
из общего списка все восемь пунктов оставались включёнными: «Удалить из списка…»
показывала подтверждение и лишь **после** «Да» приносила `ReadOnlySourceError`,
а «Свойства…» открывали полностью редактируемый диалог, чей «ОК» отвергается
тем же способом. Решение заказчика — отказ показывается **раньше, до действия**:
элемент неактивен и объясняет почему.

Неактивны ровно те два пункта, которые пишут в файл списка. Запуск, «Создать
ярлык…» и «В избранное» для записи общего списка остаются рабочими: первые два
в `.v8i` не пишут вовсе, третий пишет только в `bases.json`, к которому источник
записи отношения не имеет. Гасить их значило бы отобрать работающие операции
ради симметрии. Цена решения принята явно: посмотреть прочие ключи записи
общего списка через «Свойства…» теперь нельзя — тот же обмен, что уже сделан
для групп общего списка, где недоступно и «Переименовать группу…».

### 3.3. Группы и перемещение

- Создание, переименование и перемещение — существующие `add_group` / `update_group`
  (каскад `Folder` уже в `services`, T-04.4).
- **drag&drop по группам.** Qt строки сам не двигает: перехватываем drop, зовём
  `update_infobase(key, {"Folder": …})` или `update_group(key, new_folder=…)`,
  пересобираем из `Workspace`. Иначе при отказе операции модель и файл разъедутся.
  Запреты уже в `services` (группа внутрь себя, несуществующий родитель, общий
  список только для чтения); UI добавляет свой — виртуальные ветки «Избранное»,
  «Недавние», «Общие списки» и неявные узлы не цель и не источник.
- **Пустой `Connect=`** отличается от обычной группы проверкой
  `item.is_group and item.connect == ""`: у настоящей группы `connect is None`
  (`V8iSection.connect` возвращает значение ключа, `is_group = not connect`).
  Правится как группа, с предупреждением, что первая перезапись платформой
  вычистит `Version` ([Ф] T-05.6). Обязательство 4 блока Б.

### 3.4. Приём каталога в разделе (задача 20, по итогам smoke №2)

Каталог, перетащенный из Проводника в раздел «Базы», открывает диалог добавления
с заполненными полями: путь, имя по названию каталога, группа по месту броска.
Пользователь подтверждает или отменяет; отмена не меняет ничего.

Решение заказчика 09.08.2026: **диалог, а не создание записи сразу.** Имя каталога
не всегда годится как имя базы — его чаще хочется поправить, а молчаливое создание
записи от случайного броска меняет чужой файл без спроса. Диалог вдобавок
не порождает второго пути создания записи: используются существующие
`InfobaseDialog.for_new` и `Workspace.add_infobase`.

**Группа по месту броска:**

| Куда отпустили | `Folder` новой записи |
| --- | --- |
| строка-группа | путь этой группы |
| строка-база | путь её родителя |
| неявный узел, служебная ветка, пустое место, вне дерева | корень |

Считается переиспользованием `_folder_of_drop`, а не новой логикой: для группы это
`INTO`, для базы — `AFTER`. Служебные ветки и неявный узел не отвергаются, а дают
корень: пользователь целился в список, а не в конкретную ветку, и диалог всё равно
покажет, куда ляжет запись, до подтверждения.

**[Р] Режим `InternalMove` не меняется.** Три обработчика `_BasesTree` работают
по одному правилу: есть каталог — обрабатываем сами, до `super()` не доходим;
нет — зовём `super()`. Барьер задачи 14 остаётся дословно: `super()` по-прежнему
отвергает любое чужое перетаскивание, а мы принимаем ровно одну проверенную форму
(один локальный путь, и он каталог). Отвергнутые варианты: перевод дерева
в `DragDrop` расширяет поверхность приёма до любого чужого drop и рискует
регрессией в логике, прошедшей ревью, мутации и два smoke; приём на родителе
с расчётом на всплытие события опирается на **[Д]**, непроверяемое под offscreen,
и переносит риск в ручной smoke.

**Границы:**

- `dropped_directory(mime) -> str | None` — модульная функция `ui/dialogs/infobase.py`
  вместо статического метода `InfobaseDialog`: знание нужно двоим.
- `BasesView.add_infobase_from_directory(...)` — единственная точка входа: считает
  группу, собирает диалог, зовёт `accept_directory`, подставляет группу.
- `BasesView` получает те же три обработчика тонкой обёрткой — для областей раздела
  вне дерева (панель пути, поля); группа при этом корень.
- Полю поиска приём drop **отключается**: `QLineEdit` по умолчанию вставил бы путь
  каталога текстом в строку поиска.

**Вне объёма:** проверка каталога на признаки базы (кнопка «Обзор…» тоже
не проверяет, расхождение было бы неожиданным); несколько каталогов разом;
создание записи без диалога. Приём на диалоге остаётся как был.

## 4. Порядок записей: `OrderInList`

Очевидное решение «новое значение = среднее между соседями» **у нас не работает
с первого дня**: `edit._apply_add` пишет каждой новой записи `OrderInList=-1`,
значит равные соседи — норма, а не краевой случай, и среднего между ними нет.

Поэтому операция формулируется иначе: **«переставить запись на позицию N внутри
её группы»**. Чистая функция считает по текущему списку значений и целевой позиции
минимальный набор новых значений: обычно одно (есть зазор), иногда — перенумерация
одной группы, когда зазора нет. Применение — новый `ReorderPatch`: один проход
по документу, одна атомарная запись.

**[Р] Перенумерация локальная и только по нужде.** Скил `v8i-format` (факт 5)
запрещает пересчёт **всего файла** в плотную нумерацию — он переписывает файл
и ломает round-trip. Пересчёт одной группы при исчерпании зазора — вынужденный
и редкий; решение записано явно, чтобы следующий читатель не принял его
за нарушение правила.

**[Р] решение заказчика (круг правок 1, задача 15): «зазора нет» — когда все
значения группы совпадают буквально**, а не когда исчерпан зазор в одной
конкретной точке вставки. Более широкое условие (сравнение старого значения
переставляемой записи только с одним соседом) на первой версии правки
переписывало лишние записи на реальных данных заказчика: из шести значений
группы, где вырождены только две записи, переписывались все шесть ради
перестановки одной. Проверка идёт по значению, которое реально попадёт
в файл (после округления `%.15g`), а не по промежуточному `float` — у
соседей вида `60.6814814814813`/`60.6814814814814` (реальные значения
платформы, факт 5) среднее после округления может совпасть текстом с одним
из соседей, хотя как `float` честно лежало строго между ними.

Пользователь переставляет запись двумя способами, оба зовут одну операцию:
drag&drop внутри группы и `Alt+↑` / `Alt+↓` (продукт рассчитан на работу
без мыши — §3 спеки 4a).

Сортировка уже идёт по `OrderInList` (`catalog`: ключ
`(item.order is None, item.order or 0.0)`, стабильная).

## 5. Ярлык `.lnk`

Решение заказчика 08.08.2026: **ярлык указывает на OneCStarter с именем базы**,
файл собираем **своей записью формата MS-SHLLINK**.

Почему не на клиента и не на `1cestart.exe`: ярлык прямо на `1cv8c.exe` запекает
путь к конкретной версии платформы навсегда, ярлык на `1cestart.exe` возвращает
[Ф] факт 7 скила `platform-launch` — несуществующая версия молча заменяется
максимальной. И то и другое возвращает боль А из `requirements.md`, от которой
продукт лечит. Плюс у веб-базы исполняемого файла клиента нет вовсе.

- `config/shell_link.py` — сборка байтов. Ложится к `v8i.py` и `cestart_cfg.py`:
  тот же класс задачи, чужой бинарный формат, побайтовые тесты. Без новых
  зависимостей: `pywin32` дал бы ~10 МБ в сборку и тесты только на Windows.
- `--ib-name "Имя"` в `__main__`: окно не показывается, `Workspace` ищет запись
  по имени с той же диагностикой неуникальности, что и `_reject_ambiguous_name`
  ([Ф] T-05.3: платформа считает дублями имена, различающиеся регистром; поиск
  регистронезависим), ошибки — через `QMessageBox`, потому что консоли
  у `pythonw.exe` нет (§9 п. 4 спеки 4a).
- Пункт меню «Создать ярлык…» → `QFileDialog` с предзаполненным рабочим столом.
  Недопустимые в имени файла символы (`\/:*?"<>|`) заменяются; пустое после
  замены имя — отказ.
- **Цель ярлыка — `sys.executable`.** В собранном виде это `OneCStarter.exe`
  (PyInstaller one-dir), в разработке — `pythonw.exe` из venv, и тогда
  в аргументы добавляется `-m onecstarter`. Разница видна в тесте: цель
  и аргументы считает чистая функция, а не собирает диалог.

**Честный риск.** Собственная запись формата проверяется только ручным smoke:
побайтовый тест сверяется с нашим же эталоном, он ловит регрессию, но не ловит
«Windows такой ярлык не принимает». **Шаг задачи:** заказчик создаёт ярлык
на ту же цель штатным способом, байты сверяются с нашими. Без этой сверки задача
не закрывается.

## 6. Горячие клавиши запуска: F3 / F4 и Shift-варианты

Требование заказчика 08.08.2026 — привычка от штатного стартера. Замечание
распадается на две половины разной готовности, и смешивать их нельзя.

| Клавиша | Действие | Статус |
| --- | --- | --- |
| `F3` | 1С:Предприятие | реализуемо в 4b |
| `F4` | Конфигуратор | реализуемо в 4b |
| `Shift+F3` | 1С:Предприятие с запросом авторизации | **блокировано T-05.13** |
| `Shift+F4` | Конфигуратор с запросом авторизации | **блокировано T-05.13** |

### 6.1. `F3` / `F4` — ложатся на уже работающие пути

- `F3` → `launch(key)` **без** `forced_client`. Это режим, а не клиент: тонкий или
  толстый выбирает `App` секции либо платформа ([Ф] T-02.6). Совпадает с тем, что
  сегодня делает `Enter`.
- `F4` → `launch(key, ClientKind.DESIGNER)`. Совпадает с `Ctrl+3`.
- **[Р] `Ctrl+1` и `Ctrl+2` остаются.** Только они дают явный выбор тонкий/толстый,
  которого у `F3` нет. `Ctrl+3` дублирует `F4` — дубль безвреден и снимает
  необходимость переучиваться тем, кто привык к 4a.
- Конфликтов нет: `F3` в Windows — это `QKeySequence.StandardKey.FindNext`,
  но мы его не занимали, поиск у нас живёт в поле ввода.
- **Веб-база.** `F3` открывает браузер (`launch_infobase` для `WEB` игнорирует
  `forced_client`). `F4` на веб-базе **не делает ничего**: «открыть Конфигуратор»
  и «открылся браузер» — разные вещи, а меню для `WEB` эти пункты и так прячет.
  Молча открыть браузер по `F4` было бы обманом ровно того рода, который задача 8
  плана 4a уже закрыла для `Ctrl+1`/`2`/`3`.

**Порядок с §7 важен.** Пункты меню получают эти сочетания, а меню сейчас рисует
подсказку табуляцией в тексте. Если диагностика §7 покажет, что причина скомканного
показа — именно табуляция, переход на `QAction.setShortcut()` обязан идти **до**
добавления `F3`/`F4`, иначе новые пункты приедут с тем же дефектом.

### 6.2. `Shift+F3` / `Shift+F4` — механизма нет, есть гипотеза

> **Решение заказчика 09.08.2026: задача 16 снята из v1 и перенесена в v2.**
> Основание — шаг 0 эксперимента T-05.13, проведённый без запуска 1С (§14):
> в рабочем списке 58 записей баз, из них со строкой соединения, несущей `Usr`, —
> **ноль**, несущей пароль — **ноль**. Игнорировать нечего: предмета, ради которого
> писалась вся гипотеза ниже, на машине заказчика не существует. Остаётся `WA=1`
> (у всех 58 секций), но заказчик подтвердил, что ни одна база не входит по учётной
> записи Windows, — значит `WA=1` инертен и у `Shift+F3` не было бы наблюдаемого
> эффекта ни на одной базе.
>
> Реализовывать по неподтверждённой гипотезе механизм, который негде проверить
> и чей эффект никто не увидит, хуже, чем не реализовывать: он остался бы навсегда
> непроверенным кодом в пути запуска. Разбор ниже сохранён целиком — он понадобится
> в v2, когда появится база с настроенной ОС-аутентификацией или с сохранённым
> паролем.

Формулировка заказчика: «с запросом авторизации, то есть игнорируются параметры
логина и пароля». **[Ф] наблюдение заказчика** — так ведёт себя штатный стартер
на его машине.

**Чего нет:** ключа «проигнорируй сохранённые учётные данные». Справочник
`platform-launch` просмотрен целиком: `/N`, `/P`, `/WA±`, `/WSN`, `/WSP`,
`/ModifyPassword`, `/SAOnRestart`, `/OIDA±`, `/AccessToken` — ни один этого
не делает. `Usr` и `Pwd` — фрагменты **строки соединения** (справочник: «Та же
утечка через argv, что и `/N` `/P`»), и при запуске по `/IBName` платформа читает
их из секции сама.

**[Д] гипотеза, подлежащая проверке:** запускать по `/IBConnectionString` строкой,
из которой вырезаны `Usr` и `Pwd`, плюс `/WA-`.

Опоры — измеренные:

- [Ф] T-05.1 — наша форма `/IBConnectionString` верна (значение прижато, кавычки
  удвоены), путь с пробелом работает;
- [Ф] T-05.1 — запуск по строке соединения **не меняет** `ibases.v8i`;
- [Ф] T-02.7 — `WA=1` платформа отрабатывает сама, **читая его из `.v8i`
  по `/IBName`**; значит при запуске по строке секция не участвует вовсе.

Дыры — тоже измеренные, и они ровно в нужном месте:

- [Ф] T-02.7 сравнивал `/WA+`, `/WA-` и отсутствие ключа **только на базе, где

  с настроенной ОС-аутентификацией не проверен: это открытый T-05.12;

**Почему не «сделать и посмотреть».** Второй путь запуска — правка
`services/launch.py` и `domain/launch.py`, то есть модели запуска, а не слоя UI.

выбрасывается ветка запуска вместе с тестами, а не один замер.

**Решение заказчика 08.08.2026:** провести эксперимент T-05.13 до написания кода.

### 6.3. T-05.13 — что снимаем

**Шаг 0 запуска 1С не требует:** посчитать в `ibases.v8i` фрагменты `Usr`/`Pwd`
в строках соединения и ключи `WA`. Заказчик 08.08.2026 не уверен, что такие базы
у него есть. Если их нет — `F3` и `Shift+F3` на этой машине неразличимы, и
эксперимент требует завести тестовую базу: одну с сохранённым паролем, одну
с настроенной ОС-аутентификацией. Без этого шага остальные замеры бессмысленны.

Матрица: (`/IBName` | `/IBConnectionString` без `Usr`/`Pwd`) × (без `/WA` | `/WA-`)
× (база с сохранённым `Pwd` | база с `WA=1`). Фиксируется по каждому запуску:
появился ли диалог авторизации, под кем вошли, изменился ли `ibases.v8i`.

Исходы:

- **гипотеза подтверждается** → Shift-варианты реализуются вторым путём запуска
  в `domain/launch.py`; обычные `F3`/`F4` остаются на `/IBName` — там работает
  диагностика неуникального имени ([Ф] T-05.3) и чтение `WA` платформой;
- **гипотеза опровергается** → Shift-варианты **не реализуются как-нибудь**.
  Записывается [Ф]-результат, решение принимается отдельно: честный отказ
  с объяснением либо новый кандидат механизма.

В обоих случаях результат возвращается в скил `platform-launch` (подтверждённое
повышается до [Ф], опровергнутое исправляется) и заодно закрывает T-05.12.

   `_target_of_drop`»: строка с ключом привязки, которую он не находит, отвергается
   курсором целиком. Строки без ключа (неявный узел, заголовок ветки, строка
   ошибки) курсором по-прежнему не отвергаются — у них сообщения с подсказкой.

### Шаг 0 T-05.13 выполнен 09.08.2026 — постановка задачи 16 изменилась

Инвентаризация рабочего списка (58 записей баз): строк соединения с `Usr` — **0**,
с паролем (`Pwd`/`SPwd`/`wsp`/…) — **0**, секций с ключом `WA` — **58**, у всех
значение `1`.

Сохранённых учётных данных нет ни в одной базе, значит у `Shift+F3` в исходной
формулировке «проигнорируй сохранённые `Usr`/`Pwd`» на этой машине нет предмета.
Остаётся единственный механизм — `WA=1`. Матрица из восьми запусков (§6.3)
схлопывается до двух: `/WA-` против отсутствия ключа, и только на базе, где
ОС-аутентификация действительно срабатывает. По [Ф] T-02.7 остальные сочетания
уже сняты.

Заказчик подтвердил 09.08.2026: **ни одна база не входит по учётной записи
Windows без запроса логина.** Значит `WA=1` инертен, наблюдаемого эффекта
у `Shift+F3` не было бы ни на одной базе, и проверить механизм негде.

**Решение: задача 16 снята из v1 и перенесена в v2** (§6.2). Гейт, поставленный
08.08.2026 решением 8, сработал ровно так, как задумывался: гипотеза не дошла
до кода. Эксперименты T-05.12 и T-05.13 переезжают в v2 вместе с ней — ставить
их не на чем.
