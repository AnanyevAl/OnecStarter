# v3.1.1 — импорт выбранных проектов через CLI EDT: дизайн

Решения заказчика 16.09.2026, сессия brainstorming. Базовая точка — вершина ветки v3.1
`09c1b72` (3.1.0 собрана, ждёт ручного smoke). Версия вехи — `3.1.1`; ветка
`feat/2026-09-16-v311`. Цветовая схема (спека v3.2) остаётся следующей вехой и подтянет
3.1.1 после слияния.

Повод — замечание при проверке 3.1.0: запись EDT с пустой рабочей областью и каталогом
проекта, в котором лежит клон репозитория (`src/<имя>/.project`, десятки проектов).
Диалог «Импортировать проект (CLI EDT)» ничего не знает о записи: поле каталога пустое,
одна команда — один каталог. Заказчик хочет то же, что мастер импорта самой EDT: каталог
подставлен, найденные проекты перечислены с флажками, импортируются отмеченные.

## §1. Решения заказчика

| Вопрос | Решение |
| --- | --- |
| Веха | Отдельная, `3.1.1`, после выпуска 3.1.0; цвета — v3.2 |
| Несколько проектов за раз | **A**: один сеанс CLI на все отмеченные — скрипт `-file` с JDK через `-ini-file` (по итогам Э12: список Gogo не принят, очередь не нужна) |
| Автоподстановка | «Каталог» = `project_dir` записи, сканирование при открытии |
| Список | Флажки, как в `validate`; уже привязанные — сняты и недоступны |
| Что не делаем | Имя из `.project`, вложенные проекты, правка `project_dir` записи из диалога, сортировка по типу проекта, «скрыть привязанные» |

Почему один сеанс: 30 проектов по одному — ≈25 минут (факт 1); мастер EDT делает это
за минуту, потому что Eclipse уже запущен. Э12 (17.09.2026) подтвердил скрипт `-file`.

## §2. Поиск проектов

`domain/edt_cli.py`:

```python
@dataclass(frozen=True)
class ProjectCandidate:
    path: str          # абсолютный путь каталога проекта, как на диске
    relative: str      # путь относительно корня через "/"; корень-проект — имя его каталога
    in_workspace: bool = False


def mark_in_workspace(
    candidates: Sequence[ProjectCandidate], entries: Sequence[WorkspaceEntry]
) -> list[ProjectCandidate]:
    """`in_workspace=True`, если `workspace_key(path)` совпал с путём любой записи реестра
    (и без `.project` тоже — привязка есть)."""
```

`services/edt_cli.py` (ФС через инъекцию — по образцу `workspace_entries`):

```python
SCAN_MAX_DEPTH = 3


def scan_projects(
    root: str,
    *,
    max_depth: int = SCAN_MAX_DEPTH,
    listdir: Callable[[str], list[str]] = os.listdir,
    is_dir: Callable[[str], bool] = os.path.isdir,
    is_file: Callable[[str], bool] = os.path.isfile,
) -> list[ProjectCandidate]:
```

Правило (факт 9): каталог с `.project` — кандидат, внутрь не заходим; иначе — в подкаталоги.
Ограничения наши: подкаталоги с именем на точку (`.git`, `.metadata`, `.settings`)
пропускаются; глубина: корень — уровень 0, проверяются каталоги уровней 0…`max_depth`
включительно (`root/src/cf` — уровень 2, запас один; ошибочно выбранный `E:\` целиком не
обходится); `OSError` на подкаталоге —
подкаталог пропускается, на корне — пустой список. Результат отсортирован по `relative`
без учёта регистра. Корень, в котором лежит `.project`, — единственный кандидат с
`relative` = имя каталога корня.

## §3. Диалог `ui/edt/cli_import_dialog.py::CliImportDialog`

Заголовок «Импортировать проекты (CLI EDT)». Конструктор:

```python
CliImportDialog(
    project_dir: str,                       # project_dir записи, может быть ""
    entries: Sequence[WorkspaceEntry],      # реестр рабочей области записи
    *,
    scan: Callable[[str], list[ProjectCandidate]] = scan_projects,
    is_dir: Callable[[str], bool] = os.path.isdir,
    choose_directory: Callable[[], str] = browse_for_directory,
    parent: QWidget | None = None,
)
```

Вызывающий код — `EdtView.cli_import`: `project.project_dir`,
`workspace_entries(project.workspace)`.

**Режим «Проекты EDT в каталоге»** (бывший «Существующий проект EDT»):

- Поле «Каталог» = `project_dir`; пусто — placeholder «каталог с проектами EDT, например
  клон репозитория». Кнопка «Обзор…» как сейчас.
- Сканирование — `mark_in_workspace(scan(root), entries)` — при открытии (если поле
  непустое), после «Обзор…» и по `editingFinished` поля — только если текст изменился с
  последнего сканирования (после Enter флаг изменённости поля остаётся, повторный
  `editingFinished` при уходе фокуса не должен сбрасывать снятые флажки). Не по
  `textChanged`: обход трёх уровней от `E:\` не мгновенный. Enter в поле — только
  сканирование, диалог не принимается (иначе ОК-по-умолчанию запустил бы импорт списка,
  которого пользователь не видел).
- Список `QListWidget` с флажками (приём `CliValidateDialog`): текст — `relative`,
  подсказка — `path`. `in_workspace` — флажок снят, элемент недоступен
  (без `ItemIsEnabled` и `ItemIsUserCheckable`), текст с суффиксом
  « — уже в рабочей области». Остальные — отмечены.
- Кнопки «Выбрать всё» / «Снять всё» — только доступные элементы.
- Строка состояния под списком: «Найдено N, уже в рабочей области M»;
  «Проектов не найдено: каталог с .project ищется до 3 уровней» (список пуст,
  каталог есть); «Каталог не существует» (`scan` вернул пусто и `is_dir(root)` — ложь);
  пустое поле — строка состояния пуста, список пуст.
- ОК доступен при хотя бы одном отмеченном; иначе строка ошибки «Не выбран ни один проект».
- `form()` → `ImportForm(existing_project_dirs=tuple(отмеченные path в порядке списка))`.

**Режим «Файлы конфигурации XML»** — без изменений (поля, проверки, `--build`).

`ImportForm.existing_project_dir: str` → `existing_project_dirs: tuple[str, ...] = ()`.

## §4. Команды и выполнение

### §4.1. Домен

`cli_import_args(form) -> str` → `cli_import_commands(form) -> list[str]`:
режим каталога — по одной `import --project '<путь>'` на элемент `existing_project_dirs`
в его порядке; режим XML — одна команда, как сейчас (те же проверки, те же тексты
ошибок; «Выберите один вариант импорта…» при заполненных обоих режимах остаётся).
Пустой `existing_project_dirs` при пустом XML — «Укажите каталог проекта или каталог
файлов конфигурации» (как сейчас). Порядок не сортируем (факт 10 — [Ф] Э6, на успех
не влияет).

```python
def build_cli_script_command(
    exe: Path, workspace: str, script: Path, ini: Path,
    installation_vm_args: str, project_vm_args: str,
) -> LaunchCommand:
    """`-data "<ws>" -ini-file "<ini>" -vmargs <args> -file "<скрипт>"` ([Ф] Э12)."""


def cli_ini_text(installation_ini: str, jvm_dir: Path) -> str:
    """Свой ini для `-ini-file`: строки `1cedt.ini` установки без `-Dosgi.debug…` и без
    прежних `-vm`/<путь>, плюс `-vm` и `<bin JDK>` перед `-vmargs` ([Ф] Э12)."""
```

`build_cli_script_command`: `-vmargs` собирается как у `build_cli_command`
(`installation_vm_args`, `-Djava.library.path=`, `project_vm_args`; пустые части
опускаются) — список никогда не пуст, иначе обёртка приняла бы `-file` за аргумент JVM.
`-ini-file` и `-vmargs` — **до** `-file` (грамматика обёртки, факт 6). `cli_ini_text` —
чистая: текст ini на входе, текст на выходе, LF; нет `-vmargs` в исходном ini —
`-vm`/путь дописываются в конец.

### §4.2. Один сеанс — скрипт `-file` с JDK через `-ini-file`

`services/edt_cli.py::EdtCli.start_script(project_id, label, commands: Sequence[str]) -> CliRun`:

- те же `unavailable_reason` и `EdtError`, что у `start`; проверка — **до** записи файлов
  (живая команда на этой записи читает свой скрипт);
- ini — `<logs_dir>/<project_id>.ini`: `cli_ini_text(<установка>/1cedt.ini, effective_jvm)`;
  `1cedt.ini` читается через инъекцию `read_text` (тесты без диска); `OSError` чтения —
  `EdtError` «Не удалось прочитать 1cedt.ini установки: …»;
- скрипт — `<logs_dir>/<project_id>.cli`: по строке на команду, UTF-8 без BOM, LF ([Ф] Э12);
  оба файла наши, не пользовательские — обычная запись, перезаписываются каждым запуском,
  остаются рядом с журналом для диагностики; `OSError` записи — `EdtError` «Не удалось
  записать скрипт CLI: …»;
- журнал: `▶ <label>: скрипт <имя файла>, команд: N`, затем каждая команда строкой,
  затем командная строка (тот же порядок «события до spawn», что в `start`);
- дальше — `wrap_console_utf8`, Job, `_runs`, `mark_cli_busy`, `finish`/`interrupt` без
  изменений.

`EdtView.cli_import`: одна команда — `start` с `-command` (как сейчас, [Ф] Э6); две и
больше — `start_script`. Метка консоли — «Импортировать (проектов: N)» при N ≥ 2
(числительное не склоняется), «Импортировать» при одной. Пункт меню — «Импортировать
проекты…». Итог — код завершения: 0 — все привязаны; 204 — скрипт остановился на первой
неудавшейся команде, её текст — в журнале (stdout, факт 7), привязанные до неё остаются;
после `finish` — `rebuild()`, повторное открытие диалога показывает новые привязки.

### §4.3. Отклонено по итогам Э12

- Список Gogo `import --project ['a' 'b']` — код 204 (факт 5).
- `;` между командами в одном `-command` — код 204 (факт 6): обёртка отдаёт хвост как одну
  команду.
- Очередь команд по одной — не нужна: скрипт работает; остаётся мысленный резерв на случай,
  если другая версия EDT не примет `-ini-file` (тогда — новый эксперимент, не молчаливый
  откат).

## §5. Ошибки

| Случай | Поведение |
| --- | --- |
| Каталог не существует | Строка состояния «Каталог не существует», список пуст, ОК недоступен |

## §8. Границы

- Не трогаем: XML-импорт, `validate`, `build`, `project`, реестр EDT Start, запуск GUI EDT,
  форматы `.location`/`.project`.
- Не делаем: чтение имени из `.project` (в списке — каталог относительно корня: это то, что
  выбирает пользователь; имя из `.project` появится в EDT после импорта, факт 2), поиск вложенных
  проектов, правку `project_dir` записи из диалога, сортировку по типу проекта, «скрыть
  привязанные», параллельные сеансы CLI на одной записи.
