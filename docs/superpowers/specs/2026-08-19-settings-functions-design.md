# Функции настроек — дизайн вехи

Целевой вид — [assets/2026-08-08-v1-plan4b-mockup.html](assets/2026-08-08-v1-plan4b-mockup.html),
раздел «Раздел „Настройки“» (закреплён заказчиком 15.08.2026). Все поведенческие
решения этой спеки утверждены заказчиком на брейншторме 19.08.2026, дизайн
целиком утверждён в тот же день.

Точка отсчёта — `master@49fb2c4`. Важное расхождение с ранними вводными:
трей с меню (`ui/tray.py`), безусловное «закрытие в трей» (`ui/shell.py`)
и глобальный хоткей Ctrl+Alt+B (`ui/hotkey.py`, `RegisterHotKey`) **уже
реализованы и поставляются в v1**. Веха делает существующие поведения
настраиваемыми и добавляет одну новую механику — автозапуск.

## §1. Объём

Четыре настройки, порядок групп раздела — по мокапу:

| Группа | Настройка | Дефолт |
| --- | --- | --- |
| ВНЕШНИЙ ВИД | Тема — **уже реализована (T-06), не трогается** | — |
| ОКНО И ЗАПУСК | Закрытие окна сворачивает в трей | включено |
| ОКНО И ЗАПУСК | Запускать при входе в Windows | выключено |
| ГОРЯЧИЕ КЛАВИШИ | Глобальный вызов окна | Ctrl+Alt+B, включён |
| СПИСОК БАЗ | Записей в «Недавних» | 10 |

Ни один дефолт не меняет поведение работающей программы у текущих
пользователей; автозапуск никогда не включается молча.

**Не входит** (решение заказчика 19.08.2026): расширение меню трея
(запуск клиентов Ctrl+1/2/3, Ctrl+D избранное из мокапа — отдельная веха);
хвосты из вводной сессии (`.lnk` `0x35`/`0x36`, отложенные кандидаты
ревью 18.08).

## §2. Закрытие в трей

Настройка меняет **ровно одно** — поведение крестика:

- Включено: крестик прячет окно, программа живёт в трее (текущее поведение).
- Выключено: крестик завершает программу; глобальный вызов после этого
  не работает потому, что процесса нет, — это и есть подпись мокапа
  «глобальный вызов перестаёт работать».

Иконка трея — постоянный атрибут работающей программы: показывается всегда,
независимо от настройки (решение заказчика 19.08.2026). Быстрый запуск
избранного и смена темы из трея работают при любом значении настройки.

Трей недоступен (`isSystemTrayAvailable() == False`) — настройка ведёт себя
как выключенная: крестик завершает программу. Это текущее поведение
(`window.close_to_tray = tray is not None`), оно сохраняется; настройка
добавляется конъюнкцией: `close_to_tray = настройка AND трей доступен`.

## §3. Автозапуск при входе в Windows

### 3.1. Источник истины — реестр, не settings.json

Флаг автозапуска в `settings.json` **не хранится**. Истина — значение
в реестре; тумблер раздела показывает фактическое состояние реестра
на момент показа. Два источника истины разошлись бы при переустановке
или ручной правке реестра, и тумблер врал бы либо файлу, либо системе.

### 3.2. Механика

Значение `OneCStarter` в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`,
тип `REG_SZ`, данные — `"<полный путь к OneCStarter.exe>" --autostart`.
Путь — `sys.executable` работающего собранного экземпляра (в frozen-сборке
это путь exe): включает тумблер тот экземпляр, который и должен запускаться.

Метки достоверности:

- **[Проверено, 19.08.2026, машина заказчика]** Чтение реального ключа
  `HKCU\...\Run` (16 значений): все — `REG_SZ`; и «путь + аргументы»,
  и «голый путь» встречаются; путь берётся в кавычки, когда за ним идут
  аргументы. Имена сторонних программ здесь не приводятся: репозиторий
  публичный, состав автозапуска машины заказчика — приватное (правило
  аудита приватного, леджер `.superpowers/`). Наш случай требует кавычек:
  за путём идёт `--autostart`, а сам путь содержит пробелы
  (`...\Programs\OneCStarter\...`).
- **[Из документации Microsoft]** Значения `HKCU\...\Run` исполняются
  при входе пользователя в систему.
- **[Из документации Microsoft]** Запись в `HKEY_CURRENT_USER` прав
  администратора не требует; установка у нас per-user
  (`{localappdata}\Programs\OneCStarter`, `build/installer.iss`).
  Метка добавлена 19.08.2026 по находке ревью Task 3: утверждение стояло
  без неё, а код модуля цитировал его наравне с соседним помеченным —
  правило достоверности не терпит утверждений без источника.

### 3.3. Только в собранной версии

Из исходников настройка заблокирована с подписью мокапа («ссылка в реестре
протухнет»): признак — `sys.frozen`. Сам `sys.frozen` читается тонкой
функцией на границе, а в чистый модуль автозапуска признак и путь к exe
подаются аргументами — иначе модуль нельзя проверить обоими способами
на одной машине (тест «из исходников тумблер заблокирован» на собранной
версии стал бы зелёным по совпадению окружения, как было с offscreen
и определением системной темы).

- **[Проверено, 19.08.2026]** При запуске из исходников `sys.frozen`
  отсутствует (замер: `getattr(sys, "frozen", False) == False`).
- **[Проверено, 20.08.2026]** В собранном exe `sys.frozen == True`:
  `run_smoke` (`src/onecstarter/ui/app.py`) пишет в лог явную строку
  `smoke: frozen=<значение>`, а `build/smoke.py` (задача 10) проверяет,
  что записано именно `smoke: frozen=True`. Проверено сборкой
  `build/build.ps1 -SkipInstaller` (PyInstaller 6.22.1, `smoke: OK`,
  код выхода 0) и повторным ручным запуском
  `OneCStarterc.exe --smoke <каталог>` с подменённым `APPDATA` —
  в логе присутствует строка `smoke: frozen=True`.

### 3.4. Тихий старт

Аргумент `--autostart`: программа стартует в трей, окно не показывается —
смысл автозапуска в том, чтобы хоткей и запуск из трея были доступны сразу,
а не в окне при каждом входе (решение заказчика 19.08.2026). Трей
недоступен — показать окно: невидимый процесс без трея недопустим.

### 3.5. Деинсталляция

Uninstaller Inno Setup удаляет значение `OneCStarter` из Run: запись
в `[Registry]` с флагами `dontcreatekey uninsdeletevalue` (значение не
создаётся при установке, удаляется при удалении).

- **[Проверено, 20.08.2026, машина разработки]** Секция компилируется:
  ISCC 6.7.3 разобрал её (`Parsing [Registry] section`) без
  предупреждений, установщик собран (`dist\OneCStarter-0.1.0-setup.exe`,
  33,2 МБ, код выхода 0). Утверждение вехи «на машине разработки Inno Setup
  нет» устарело — он установлен, компиляция выполнима агентом.
- **[Из документации Inno Setup, не проверено]** Само поведение
  `uninsdeletevalue` по отношению к значению, которое установщик **не
  создавал** (его пишет приложение при включении тумблера), компиляцией
  не проверяется. Прогон установки → включения → деинсталляции — блок А
  протокола [t04-7-settings-protocol.md](../../research/t04-7-settings-protocol.md);
  там же кандидаты на замену, если флаг не покроет этот случай.

### 3.6. Отказы

Запись/удаление значения реестра не удалось (`OSError`) — тумблер
возвращается к фактическому состоянию реестра, у строки показывается
сообщение об ошибке. Молча «сделать вид, что включилось» нельзя.

Чтение реестра не удалось — состояние неизвестно, и показывать «выключено»
как факт нельзя: тумблер выключен и **заблокирован**, у строки — причина.
Разница с §3.3 только в подписи: там «доступно в установленной версии»,
здесь — текст ошибки.

## §4. Глобальный вызов окна

### 4.1. Настройка сочетания

Сочетание редактируется; правило допустимости — как в мокапе, «только
с модификатором»: обязателен хотя бы один из Ctrl, Alt, Win; Shift
допускается только вдобавок к ним. Пустое значение = хоткей выключен,
регистрация не выполняется (решение заказчика 19.08.2026: глобальный
хоткей, который нельзя выключить, враждебен к чужим программам).

Хранение — строка в `settings.json` (`"Ctrl+Alt+B"`, `""` — выключен).
Разбор и форматирование «строка ↔ (модификаторы, VK)» — чистая функция
в `services`, без Qt и без обращений к системе, покрывается табличными
тестами (инвариант 2 по духу: вся логика допустимости — в чистой части).

Форма строки: разбор терпим к порядку модификаторов, регистру и пробелам
вокруг `+`; запись всегда канонична — `Ctrl+Alt+Shift+Win` в этом порядке,
затем клавиша. Иначе одно и то же сочетание попадёт в файл двумя
написаниями, и сравнение «изменилось ли» начнёт врать.

Win-сочетания правило допускает, но многие из них система держит за собой;
это видно отказом `RegisterHotKey` и обрабатывается как занятое (§4.3),
отдельного запрета в чистой функции не требуется.

**Раскладка клавиатуры на срабатывание не влияет. [Проверено, 20.08.2026,
машина заказчика]**: `Ctrl+Alt+B` поднимает окно и при активной английской,
и при активной русской раскладке, переключение раскладки регистрацию не
теряет. Механика: `RegisterHotKey` подписывается на VK-код, а VK для
буквенных клавиш определяется позицией клавиши, не текущей раскладкой, —
драйвер шлёт `0x42` для клавиши позиции `B` в обеих.

**Захват сочетания обязан быть раскладко-независимым — как и срабатывание.**
Правка 20.08.2026 по находке блока В протокола, решение заказчика того же дня.

Первая редакция этого абзаца (утром 20.08.2026) объявила нормой то, что
`Ctrl+Alt+Б` при русской раскладке не меняет поля: «непригодное нажатие —
промах пользователя». Прогон блока В опроверг трактовку в тот же час.
Заказчик, сменив сочетание на `Ctrl+Alt+G`, **не смог вернуть `Ctrl+Alt+B`**,
не переключив раскладку: поле молча не реагировало на осмысленное действие.
Промахом это не было — пользователь нажимал ровно то сочетание, которое
система принимает и которое, по результату Б3 выше, прекрасно срабатывает
при русской раскладке. UI оказался строже системы, и молча.

Причина: `spec_from_event` (`ui/hotkey_edit.py`) строила имя клавиши из
`event.key()`, а он раскладко-зависим — при русской раскладке отдаёт
кириллический код. Требование: имя клавиши берётся из
`event.nativeVirtualKey()` — фактического кода от драйвера, того самого,
на который подписывается `RegisterHotKey`, — и уже он переводится в имя
чистой функцией `key_name_for_vk` в `services/hotkeys.py` (обратная сторона
существующей таблицы `_VK_BY_KEY`, одно место истины на оба направления).
`event.key()` остаётся запасным путём: `nativeVirtualKey` равен `0`, когда
события синтезированы, а не пришли от драйвера, и терять на этом работающий
захват нельзя.

Кириллическая клавиша, у которой нет позиционного эквивалента в таблице
(`Ё`, `Ж`, `Э`), по-прежнему не принимается и по-прежнему не стирает
назначенного — вот это действительно промах, и трактовка для него верна.
Абзац добавлен по
итогам блока Б протокола
[t04-7-settings-protocol.md](../../research/t04-7-settings-protocol.md):
веха этот вопрос не задавала ни разу, хотя русская раскладка у пользователя
основная, и отказ означал бы неработающий вызов большую часть рабочего дня.

**Добавлено 20.08.2026, находка финального ревью ветки, п. 3.** Ровно одно
сочетание запрещено в самом разборе, а не оставлено на отказ регистрации:
`Alt+F4` при модификаторах **ровно** `Alt` (то есть без `Ctrl`/`Shift`/`Win`
в довесок — `Ctrl+Alt+F4` и `Alt+Shift+F4` разбор принимает как обычно).
Причина, по которой довод предыдущего абзаца («занятость видна отказом
`RegisterHotKey`») здесь не работает: Alt+F4 — сочетание, которое система
перехватывает как «закрыть активное окно», но регистрации `RegisterHotKey`
это не мешает — она успешно проходит, и назначив его пользователь отбирает
закрытие окон у всей Windows на время работы программы, вместо честного
«занято другим приложением». Решение заказчика 20.08.2026: запретить это
сочетание безусловно.

**[Из документации Microsoft, не проверено]**: факт «`RegisterHotKey` не
отклоняет `Alt+F4`» экспериментально не проверялся и проверяться не будет —
запрет ставится разбором заранее, а не полагается на отказ регистрации.

### 4.2. Смена на лету

`GlobalHotkey` получает перерегистрацию: `Unregister` старого + `Register`
нового. **[Проверено, 19.08.2026, эксперимент §7 на машине заказчика]**:
перерегистрация в одном процессе работает, освобождение мгновенно (то же
сочетание сразу берётся другой регистрацией), доставка `WM_HOTKEY` после
rebind подтверждена синтезом нажатий; занятость сочетания определяется
отказом `RegisterHotKey`. Базовая механика проверена и кодом v1 в поставке.

Занятое сочетание при смене: ошибка показывается сразу у поля, **но выбор
сохраняется в файл** с честным статусом «сохранено, сейчас занято» —
чтобы можно было назначить сочетание, которое освободится после закрытия
конфликтующей программы (решение заказчика 19.08.2026, утверждено явно).
Старая регистрация при этом снимается: действует то, что в файле, — до
освобождения сочетания хоткей фактически не работает, статус говорит об
этом прямо. Держать втихую старое сочетание при новом в файле — ложь
о состоянии.

### 4.3. Занято на старте

Сохранённое сочетание занято другим приложением при старте (включая тихий
автозапуск): **балун трея** (`QSystemTrayIcon.showMessage`) + постоянный
статус у поля в разделе «Настройки» + тултип трея (текущее поведение
тултипа сохраняется). Модального окна нет. **[Проверено, 19.08.2026,
эксперимент §7]**: `supportsMessages() == True`, балун показан на экране
Windows 11, визуально подтверждён заказчиком.

### 4.4. Поведение вызова

Хоткей поднимает окно с фокусом в поиске (`show_and_focus_search`,
текущее поведение) — из трея, из свёрнутого, из-под других окон.
При завершённой программе вызова нет: процесс мёртв, регистрация снята.

### 4.5. Кривое значение в файле

Непарсибельная строка сочетания — не порча файла: мягко в дефолт
`Ctrl+Alt+B` (по образцу `_theme_of`). Пустая строка — валидное
значение «выключен», не дефолт.

## §5. Записей в «Недавних»

Константа `RECENT_LIMIT` уходит из `services/display.py`: лимит подаётся
аргументом сборки леса из настроек. `0` — ветка «Недавние» не строится
(код уже пропускает пустую ветку — поведение совпадает с подписью мокапа).
UI — числовое поле со стрелками (spinbox) в границах 0–50. История запусков
в `bases.json` не трогается — настройка меняет только показ.

Чтение файла при вне-диапазонном значении — **исправлено 20.08.2026,
находка финального ревью ветки, п. 4 (решение заказчика 20.08.2026),
асимметрично, не «мягко в дефолт» для обеих границ**:

- значение больше `RECENT_MAX` (50) — обрезается до `RECENT_MAX`:
  пользователь явно хотел «много», это осмысленный ввод, не порча файла;
- значение меньше `RECENT_MIN` (0), то есть отрицательное, — мягко в дефолт
  10, а **не** в `RECENT_MIN`/`0`. Обоснование: `0` — валидный осознанный
  выбор «не показывать ветку „Недавние" вовсе» (см. абзац выше), и молча
  подставить его из битого отрицательного значения значило бы сделать
  за пользователя видимое изменение поведения, которого он не выбирал.
  `0`, прочитанный из файла как есть, остаётся `0` — путать «значение вне
  диапазона» с «пользователь явно выбрал ноль» нельзя;
- не-целое значение и `bool` — по-прежнему дефолт 10 (без изменений).

Первая редакция этого параграфа говорила «значение вне диапазона — мягко
в дефолт 10» для обеих границ разом; ревью нашло расхождение с кодом
(`max(RECENT_MIN, min(RECENT_MAX, value))` резал `-3` в `0`, а не в
дефолт) и заказчик решил в пользу асимметрии, а не в пользу буквы прежней
спеки — обоснование выше объясняет, почему симметричное правило было
неверным по существу, не только текстуально.

## §6. Хранение и единый писатель

### 6.1. Схема

`SCHEMA_VERSION` остаётся `1` (решение заказчика 19.08.2026). Новые поля
`Settings`: `close_to_tray: bool = True`, `hotkey: str = "Ctrl+Alt+B"`,
`recent_limit: int = 10`. Отсутствующее поле — дефолт; кривое значение —
мягко в дефолт поля. Старый файл читается без миграции; старая версия
программы новый файл не ломает (читает `theme`, незнакомые ключи игнорирует).

Задокументированный компромисс: старая версия при сохранении перезапишет
файл без новых полей — они вернутся к дефолтам. Мягкая политика settings
это допускает (цена — забытые настройки, не данные о базах). Bump схемы
был бы строго хуже: старая версия увезла бы файл в `.bad` и потеряла
даже тему.

### 6.2. SettingsStore

Сейчас `ThemeController.set_mode` пишет `Settings(theme=mode)` — целый
файл из одного поля; с четырьмя полями это затирание чужих настроек.
Вводится единый владелец — `SettingsStore` (слой ui: QObject с сигналом
`changed`; чтение/запись остаются чистыми функциями `services/settings.py`):

- держит текущий `Settings`, единственный писатель файла;
- `update(<поле>)` → `dataclasses.replace` + атомарная запись целиком + сигнал;
- `last_save_error` переезжает из `ThemeController` сюда; раздел «Настройки»
  показывает его как сегодня.

`ThemeController` рефакторится: тему меняет через store, применение
стилей и следование системной теме — без изменений. Автозапуск через
store не ходит (§3.1).

## §8. Тестирование

- **Табличные тесты чистых функций**: разбор/форматирование сочетания
  (валидные, без модификатора, только Shift, пусто, мусор); формирование
  данных значения Run (пути с пробелами — кавычки); чтение новых полей
  (отсутствуют, кривые, вне диапазона); цикл load→save не теряет поля.
- **Мутационная проверка** обязательна для защитных тестов (правило
  проекта). Первые кандидаты:
  - «смена темы не затирает остальные поля» — ломается возвратом
    `Settings(theme=mode)` в писателя;
  - «автозапуск не включается без явного действия» — ломается записью
    в реестр при старте;
  - «выключенный хоткей не регистрируется» — ломается безусловной
    регистрацией.
- **Реестр в тестах — только инъекция** функций чтения/записи/удаления;
  живой HKCU тесты не трогают (по образцу инъекции user32 в `hotkey.py`).
- **UI offscreen**: ряды раздела по группам мокапа, spinbox в границах,
  статусы ошибок; сторожа геометрии — на сравнении элементов, не констант
  (правило 5 вводной). Помнить: offscreen маскирует шрифтозависимое.
- **Smoke сборки** дополняется проверкой `sys.frozen` (§3.3).

## §9. Расхождение с мокапом, принятое сознательно

Мокап рисует двухпозиционные переключатели-«тумблеры» (switch). В Qt такого
виджета нет, и рисовать свой пришлось бы вручную — с собственным
`paintEvent`, палитрой и сторожами геометрии. Решение заказчика
19.08.2026: в этой вехе — штатный `QCheckBox`, красится общим stylesheet;
собственный переключатель — отдельной задачей после того, как поведение
всех четырёх настроек работает.

Записано здесь, а не оставлено в переписке: следующий исполнитель, сверив
раздел с мокапом, иначе примет флажок за недоделку и «починит» его,
не зная, что расхождение осознанное.
