# T-12. Job Object на профиль — дизайн (29.08.2026)

Пересмотр §12.4 спеки [v2 «Серверы»](2026-08-26-v2-servers-design.md)
по находкам 5–6 ручного чек-листа T-10 (29.08.2026, [tasks.md](../../tasks.md)
§ T-10). Веха идёт после слияния ветки T-08/T-10 в `master`, отдельной
веткой; план — `writing-plans` по этой спеке. Номер T-11 занят бэклогом
косметики (tasks.md), поэтому T-12.

Метки достоверности: **[Ф]** — измерено на реальной машине,
**[Д]** — из документации, **[Р]** — рассуждение.

## §1. Что сломано и почему

Ручной чек-лист 29.08.2026 (протокол — `.superpowers/sdd/2026-08-28-v2-servers-journal/manual-checklist.md`,
итог — tasks.md § T-10) показал два дефекта одного корня:

- **Находка 5.** Пользователь снял `ragent` из Диспетчера задач; дети
  (`rmngr`, `rphost`, `dbgs`) пережили его, держат порты 1541 и 1550.
  «Запустить» породил новый `ragent`, под которым поднялись только
  `java` и `dbda`; карточка показала «работает», красная строка о сиротах
  исчезла. Сервер выглядит здоровым и не принимает соединений. [Ф]
- **Находка 6.** «Погасить» бьёт только `rmngr`, найденный по `-regport`
  (T-08 §6: сироты = менеджеры). `rphost` и `dbgs` — не дети `rmngr`,
  а братья (дети мёртвого `ragent`); `dbgs` по командной строке
  (`--port=1550`, без `-d`) с профилем не сопоставить. [Ф]

Корень: T-08 управляет процессами через **сопоставление по командной
строке** и `TerminateProcess` по снимку. Это работает для `ragent`
и `rmngr`, но не для всего дерева, и требует гонки «снимок → убийство»
со сверкой `create_time` (§6.2). При этом с T-10 у лаунчера уже есть
механизм, который знает всё дерево без сопоставления, — Job Object,
только он один на весь лаунчер и умеет лишь «умереть вместе с ним».

## §2. Решения заказчика (29.08.2026)

1. **Job Object на каждый запуск профиля** вместо одного на лаунчер.
   «Остановить»/«Погасить» = закрыть хендл Job — ОС гасит всё дерево.
2. **«Запустить» при остатках прошлого дерева в Job профиля** — гасим
   остатки сами (событие в журнал) и запускаем. Намерение пользователя
   очевидно, остатки — только порождённое нами (в Job чужого нет).
3. **Удаление работающего профиля = остановка**: диалог «Сервер работает
   — остановить и удалить профиль?», согласие закрывает Job и удаляет.
   Решение 8 §2 исходной спеки («сервер продолжает работать и становится
   чужим») **отменяется**.
4. **Чужой `ragent`, совпавший с профилем по каталогу** (запущен не
   лаунчером — из `srv.sh`, PowerShell), — **только показ**, как служба
   (решение 6): статус «работает (запущен не лаунчером)», кнопки
   неактивны. Решение 5 §2 исходной спеки («совпавший — управляем»)
   **отменяется**. Управляем только тем, что запустили сами.

## §3. Модель: Job на запуск профиля

- `ServersWorkspace` держит `dict[profile_id, Job]` живых Job и
  `dict[profile_id, pid]` порождённых `ragent`. Job создаётся фабрикой
  на каждый `start()`; `spawn_server` кладёт в него `ragent` сразу после
  `Popen`, до рождения детей ([Ф] T-10 задача 1: Job не поглощает уже
  существующих потомков).
- **Истина о наших процессах — у ОС:** `Job.pids()` через
  `QueryInformationJobObject(JobObjectBasicProcessIdList)`. [Ф] 29.08.2026
  (проба на python-процессах с внуком, kill-on-close): список содержит
  всё дерево, включая скрытых посредников (`conhost`, venv-лаунчер);
  после убийства родителя извне остатки остаются в Job и видны
  в списке; `CloseHandle` гасит все остатки; пустой Job даёт
  `(0, ())`. Буфер списка растёт при `ERROR_MORE_DATA` [Д].
- `stop()` = `close()` Job профиля → kill-on-close ([Ф] Б2 T-09 на живом
  дереве `ragent`, [Ф] 29.08 на остатках). Ни сопоставления по argv,
  ни гонки PID, ни `children()`.
- `start()`: проверки → **занятые порты** (§4) → остатки в Job →
  `close()` (отказ `close` — отказ запуска, ДО ротации) → новый Job →
  ротация журнала → событие `погашены остатки прошлого запуска: PID …` →
  `запуск: …` → spawn → `порождён PID`. Событие гашения — ПОСЛЕ ротации
  (правка вслед за находкой задачи 3 плана, 30.08.2026): ротация
  переименовывает текущий журнал в `.1.log`, и записанное до неё событие
  уехало бы в журнал ПРОШЛОГО запуска, тогда как §10 п.3 требует видеть
  `погашены остатки…` и следом штатный старт в одном текущем журнале.
- «Погасить» = `stop()` для Job без живого `ragent`.
- Выход и крах лаунчера — все Job kill-on-close, кода нет (§12.4
  сохраняется: каждый Job умирает с процессом).
- `running_count()` и `log_shutdown()` — по профилям с непустым Job:
  закрывает долг T-10 «вопрос о выходе считает чужие процессы».
- Скан процессов (psutil) остаётся — для чужих серверов (§3.3 исходной
  спеки), статуса «работает (не лаунчером)» и занятых портов.

## §4. Состояния карточки, порты, UI

| Состояние | Признак | Кнопки |
| --- | --- | --- |
| **работает · PID N** | порождённый PID есть в `job.pids()` | «Остановить» |
| **остановлен · остатки прошлого запуска: PID …** (красным) | Job не пуст, `ragent` в нём нет | «Запустить» (гасит остатки сам), «Погасить» |
| **работает (запущен не лаунчером)** | Job пуст, скан нашёл совпавший по каталогу `ragent` | все неактивны; подсказка как у «службы» |
| **остановлен** | Job пуст, в скане ничего | «Запустить» |

**Чужие держатели портов.** Процесс из скана, не входящий ни в один наш
Job, с `-regport` или `-port` профиля (`rmngr`/`ragent`, включая сирот
чужого дерева) — красная строка «порт регистрации N занят PID … (запущен
не лаунчером)»; `start()` **отказывает** с этим текстом (`ServerError`,
событие `отказ запуска: …`). Гасить чужое нельзя (решение 4), а запуск
поверх даёт полумёртвый сервер (находка 5). Реализация — существующее
сопоставление сирот T-08 (`orphan_managers`), переименованное по смыслу
в «держатели портов». **Ограничение [Р]:** чужой `dbgs` на 1550 по
командной строке не опознать — новый запуск будет без отладочного
сервера, карточка этого не покажет; журнал покажет отсутствие баннера
`Debug Server started` ([Ф] 29.08: три баннера при здоровом старте).

**§8 подтверждающий скан** остаётся: если на первом снимке после старта
порождённый PID уже не в Job — `сервер завершился сразу после запуска`
(тот же текст в диалоге и журнале, T-10); остатки, если есть,
показываются как остатки.

**Удаление работающего профиля**: диалог через `ask_confirmation`
(«Нет» по умолчанию), согласие → `stop()` → удаление. Отказ — ничего
не меняется.

**Подтверждение выхода** — по `running_count()` (§3).

**Обнаружение остатков** — на снимке монитора (раз в 5 с, как сейчас):
переход «ragent был в Job → его нет, Job не пуст» пишется в журнал один
раз: `ragent завершился извне; остатки дерева: PID …`.

## §5. Архитектура по слоям

**platform_1c/job.py.** `ServerJob`: `assign()` (есть), `pids() ->
tuple[int, ...]`, `close()` (идемпотентный `CloseHandle`, после него
`pids() == ()`), `is_empty()`. `NullJob`: `pids() == ()`, `close()` no-op.
Протокол `Job` расширяется этими методами; `spawn_server` принимает `Job`
(закрывает долг T-10 «закрытая уния вместо протокола»). Гигиена ctypes:
`argtypes`/`restype` у всех функций, один `WinDLL` на модуль
(долг T-10). Ошибки WinAPI → `JobError` с кодом `GetLastError`.

**services/servers.py.** Конструктор: `job_factory: Callable[[], Job]`
вместо запечённого в `server_spawn` Job; `server_spawn` получает Job
аргументом: `Callable[[LaunchCommand, Path, Job], int]`. Удаляются
`stop_orphans`, `_terminate_or_raise`, `ServerStopError`, параметр
`process_control`. `JobError` из `pids()`/`close()` → `ServerError`
с текстом (как для `assign`).

**platform_1c/process_control.py** — удаляется целиком
(`ProcessControl`, `PsutilControl`, `NullControl`) вместе с тестами;
`app.py`/`run_smoke` теряют `process_control`. Скан (`process_scan.py`)
остаётся.

**domain/server_match.py.** `ServerStatus` получает `job_pids:
tuple[int, ...]` и `spawned_pid: int | None`; `orphan_managers` →
`port_holders` (чужие процессы с портами профиля, не из наших Job —
фильтр по множеству PID всех наших Job подаётся аргументом, функция
остаётся чистой).

**ui/servers/view.py.** Таблица состояний §4; диалог удаления
работающего профиля; «Погасить» → `stop()`; красная строка держателей
портов. Панель журнала и выделение — без изменений.

**ui/app.py.** `job_factory=ServerJob` в проде, `NullJob` в `run_smoke`
(защитный тест `test_run_smoke_uses_null_job` переориентируется на
фабрику).

## §6. Журнал профиля — события T-12

Добавляются: `погашены остатки прошлого запуска: PID …`;
`ragent завершился извне; остатки дерева: PID …`;
`отказ запуска: порт регистрации N занят PID … (запущен не лаунчером)`.
Остаются: `запуск`, `порождён PID`, `работает · PID`, `остановка по
команде пользователя` (теперь — закрытие Job), `выход лаунчера…`,
`отказ запуска`, `ротация журнала не удалась`. Удаляется: `гашение
сирот: PID …` (заменено остатками) и `отказ остановки: …` (отказа
`TerminateProcess` больше нет; отказ `CloseHandle` → `отказ остановки:
<JobError>` сохраняется как текст, но источник другой).

## §7. Обработка ошибок

- `JobError` (создание Job, `assign`, `pids`, `close`) → `ServerError`
  с кодом ОС; `assign` при отказе по-прежнему убивает порождённый
  процесс (T-10).
- `start()` при чужом держателе порта — отказ ДО ротации и spawn
  (журнал прошлого запуска не трогается).
- `stop()` на пустом Job — `ServerError` «нечего останавливать»; кнопка
  в этом состоянии и так неактивна.
- Удаление профиля: отказ пользователя в диалоге — no-op; `ServerError`
  из `stop()` — показывается, профиль не удаляется.
- Чужой `ragent` — никаких действий, только показ; отказа прав больше
  нет как класса ошибки.

## §9. Тестирование

- **platform_1c**: `pids()`/`close()`/`is_empty()` на настоящих python-
  процессах с внуком (образец — проба 29.08): список содержит родителя
  и внука; после `kill` родителя внук в списке; `close()` гасит остатки;
  `pids()` пустого Job — `()`. Мутационная проверка обязательна
  (`close()` без `CloseHandle`; `pids()` возвращает `()` всегда).
- **services** (фейк `FakeJob` с управляемым списком PID): защитные —
  `stop()` закрывает Job именно этого профиля (второй профиль жив);
  `start()` при остатках закрывает старый Job ДО spawn и пишет событие;
  `start()` при чужом держателе порта не зовёт `server_spawn` и не
  ротирует журнал; `running_count()` не считает чужой совпавший `ragent`;
  `log_shutdown()` пишет только профилям с непустым Job.
- **ui**: таблица состояний §4 (4 строки); удаление работающего профиля
  без согласия не останавливает и не удаляет (защитный); «Погасить»
  зовёт `stop()`; красная строка держателей портов; `run_smoke` —
  `NullJob` через фабрику (защитный).
- **Мутации** — независимым агентом по протоколу CLAUDE.md, после
  финального ревью ветки.

## §10. Живая проверка (ручной чек-лист T-12)

1. Запуск профиля → «работает · PID»; `pids()` карточки совпадают с
   деревом в Диспетчере.
2. Снять `ragent` из Диспетчера → карточка «остатки прошлого запуска:
   PID …» + событие в журнале → «Погасить» → в Диспетчере нет ни одного
   процесса дерева (включая `dbgs`, `java`).
3. Снять `ragent` → сразу «Запустить» → в журнале `погашены остатки…`,
   затем штатный старт с тремя баннерами (`Debug Server started` —
   признак, что порт 1550 освободился).
4. `ragent` того же каталога из `srv.sh` → «работает (запущен не
   лаунчером)», кнопки неактивны; профиль с теми же портами → красная
   строка держателя, «Запустить» отказывает.
5. Удаление работающего профиля → вопрос → «Да» → дерево мертво,
   профиль удалён.
6. Выход при работающем чужом `ragent` и без наших — без вопроса;
   чужой жив после выхода.
