# Дизайн — операции над группами и дедупликация источников

> Утверждён 04.08.2026 в сессии brainstorming.
> Закрывает долги плана 3: пункты 1 и 3 раздела 10
> [дизайна плана 3](2026-08-03-v1-plan3-services-design.md).
> Факты о формате `.v8i` не дублируются — скил `v8i-format`.
> Метки достоверности: **[Ф]** проверено экспериментом, **[Д]** из документации,
> **[Р]** наше решение, **[не проверено]** требует эксперимента.

## 0. Почему это отдельная работа

План 3 закрылся с двумя долгами: каскадное переименование секции-группы и политика
дедупликации записи, попавшей и в пользовательский список, и в общий. При разборе кода
выяснилось, что долгов не два, а что группы в `services` реализованы наполовину:
читаются и собираются в дерево, но не создаются, не удаляются осмысленно и не перемещаются.

Что нашлось при разборе:

| Где | Что происходит |
| --- | --- |
| `edit._rename` | Переименование группы запрещено — единственное, что было закрыто |
| `edit._apply_update` | Смена `Folder` у секции-группы проходит без проверок: собственный путь группы меняется, потомки продолжают ссылаться на старый и высыпаются в корень как orphan. Та же мина, другой вход |
| `workspace.remove_infobase` | Удаление секции-группы оставляет потомков сиротами |
| `workspace.add_infobase` | Всегда пишет `Connect`, то есть всегда создаёт базу. Создать группу нельзя ни одним вызовом |

Запрет переименования дыру не закрыл: перемещение групп drag&drop заявлено в
[дизайне v1, §2](2026-07-30-v1-core-design.md), и первый же вызов `update_infobase`
с новым `Folder` разрушил бы дерево пользователя молча.

Переименование и перемещение — не две операции, а одна: **меняется собственный путь
группы, потомкам надо переписать префикс `Folder`**.

## 1. Границы

Входит:

- модуль арифметики путей групп — единый источник правды о том, кто чей потомок;
- создание группы;
- каскадное обновление пути группы (переименование и/или перемещение);
- удаление группы с явной политикой для потомков;
- дедупликация пользовательского и общего списков;
- закрытие лазеек, через которые группу сегодня можно испортить операциями над базой.

Не входит:

- UI — подтверждения, меню, показ пометок;
- эксперименты на реальной платформе;
- политика запуска и `_reject_ambiguous_name`;
- дедупликация записей с разными `ID`. Если админ положил в общий список ту же базу
  под другим `ID`, ключи привязки разойдутся и запись останется двойной. Это неотличимо
  от двух настоящих разных баз, и угадывать здесь нечего.

## 2. Модуль путей — `services/paths.py`

Чистые функции, без ФС и без Qt:

| Функция | Смысл |
| --- | --- |
| `normalize_folder(folder)` | `/` для корня, иначе строка без обрамляющих слэшей |
| `group_path(folder, name)` | собственный путь группы: путь родителя + `/` + имя **[Ф]** T-02.3 |
| `is_inside(path, ancestor)` | посегментно: равно предку или начинается с `ancestor + "/"` |
| `retarget(path, old_ancestor, new_ancestor)` | заменить префикс-предка; вне поддерева вернуть как есть |
| `render_folder(path)` | записать путь в файл с ведущим слэшем: `/` и `/Клиенты/Розница` |

**[Р]** Записываем `Folder` в той же форме, что и платформа — с ведущим слэшем **[Ф]**
(мастер стартера, эксперимент T-02.3). Внутреннее представление слэша не несёт, но своя
форма записи в одном файле рядом со штатной — непроверенный риск на ровном месте.

**[Р]** Посегментность обязательна. `Клиенты` и `КлиентыVIP` совпадают как префиксы строк,
но потомками друг другу не приходятся: наивный `startswith` при переименовании `Клиенты`
утащил бы за собой всю ветку `КлиентыVIP`.

**[Р]** Знание о путях существует ровно в одном экземпляре. Сегодня оно приватно
в `catalog._group_path` и `catalog._normalized_folder`, а каскаду нужно то же самое.
Копия в `edit.py` гарантированно разъедется с оригиналом: дерево будет считать потомком
одно, каскад другое, и сироты появятся не от ошибки в алгоритме, а от рассинхронизации
двух реализаций. `catalog` переходит на общий модуль — чистый рефактор, поведение
`build_tree` не меняется, существующие тесты его и держат.

**[Р]** Сравнение путей остаётся точным по регистру, как сегодня. Как штатный стартер
сопоставляет `Folder` с именем секции-группы — **[не проверено]**. Ошибка в любую сторону
даёт расхождение с платформой: при регистронезависимом сравнении мы покажем потомком то,
что платформа считает сиротой, при точном — наоборот. Сохраняем нынешнюю семантику
и уносим вопрос в эксперименты (§7).

## 3. Операции над группами

### 3.1. Форма патча

`SectionPatch` не расширяем. Группам — свой тип в `services/groups.py`:

```python
class GroupPatchKind(Enum):   CREATE | RETARGET | REMOVE
class GroupRemoval(Enum):     PROMOTE | RECURSIVE

@dataclass(frozen=True)
class GroupPatch:
    kind: GroupPatchKind
    target_key: str | None = None
    name: str | None = None
    new_name: str | None = None
    new_folder: str | None = None
    removal: GroupRemoval | None = None
```

**[Р]** Отдельный тип вместо новых значений `PatchKind`: иначе `SectionPatch` обрастает
полями, осмысленными только для одного вида, и становится представимым `ADD` с политикой
удаления. Невалидные состояния должны быть непредставимы типом.

`apply_patch` в `edit.py` становится диспетчером по типу патча. `writer.write_patch`
не меняется вовсе — цикл переигрывания при внешнем изменении, разрешение конфликтов,
политика кодировки и атомарность достаются каскаду даром.

Обёртка `key_of_section(section)` переезжает в `model.py`: сейчас `edit._key_of` приватна,
а нужна обоим модулям.

### 3.2. Отвергнутая альтернатива: список патчей

Рассматривался `write_patches(path, [patch, ...])`, где вызывающий сам собирает патчи
на каждого потомка. **Отвергнуто:** список целей пришлось бы вычислять до чтения свежего
файла, а цикл в `writer` переигрывает патч на свежем состоянии. Стартер добавил базу
в переименовываемую группу между нашими попытками — она не попадёт в устаревший список
и осиротеет. Это ровно тот класс ошибок, от которого защищает нынешний дизайн записи.

Отсюда требование: **каскад вычисляется внутри применения патча, по тому документу,
в который патч сейчас применяется.**

### 3.3. CREATE — `Workspace.add_group(name, folder=None) -> str`

Секция без `Connect` **[Ф]** (признак группы — отсутствие `Connect`).
Состав ключей: `ID`, `OrderInList=-1`, `Folder`, `External=0`.

**[Ф]** мастер штатного стартера пишет группе `ID`, `OrderInList=-1`, `Folder`,
`OrderInTree`, `External=0`.

**[Р]** `OrderInTree` не пишем. Осмысленное значение неизвестно (наблюдалось `16640`),
а выдуманное число расставляет группы в дереве наугад. **[Ф]** при канонической перезаписи
платформа `OrderInTree` пересчитывает сама и **[Ф]** неизвестные ключи не удаляет — отсюда
вывод, что отсутствие ключа безвредно. Это **[Р]**, а не факт; проверяется экспериментом (§7).

**[Р]** `Folder` пишется всегда, включая корень (`Folder=/`) — так делает мастер **[Ф]**.

Возвращает ключ привязки созданной группы (`id:<uuid>`).

Валидация — по таблице §5.

### 3.4. RETARGET — `Workspace.update_group(key, *, new_name=None, new_folder=None) -> str`

Переименование и перемещение одной операцией. Алгоритм выполняется в момент применения
к свежему документу:

1. Найти секцию по ключу привязки. Не группа → `InvalidRequestError`; нет → `TargetGoneError`.
2. `old = group_path(folder, name)` секции;
   `new = group_path(new_folder ?? folder, new_name ?? name)`.
3. `new == old` → no-op, `applied=True`: запрошенное состояние достигнуто.
4. Проверки отказа — §5.
5. Переписать заголовок секции (если менялось имя) и её `Folder` (если менялся родитель).
6. Одним проходом по **всем** секциям документа: у секции, чей `Folder` `is_inside(old)`,
   `Folder = retarget(folder, old, new)`.

Шаг 6 не требует рекурсии: прямые дети, вложенные группы и их содержимое несут в `Folder`
полный путь, начинающийся с `old`, и чинятся одной посегментной заменой префикса.

**Ключи привязки потомков не меняются.** `binding_key` строится из `ID` либо из хеша
`Connect` и имени; `Folder` в него не входит. Избранное и история запусков остаются
на местах — это отдельное тестируемое свойство, а не следствие удачи.

Возвращается фактический ключ группы после применения. Он меняется только при отсутствии
у секции `ID` — суррогат зависит от имени. Существующий механизм `rekey_from`
в `Workspace._write` это отрабатывает; наших данных у групп нет, перевешивание безвредно.

### 3.5. REMOVE — `Workspace.remove_group(key, removal)`

Аргумент политики обязателен, значения по умолчанию нет: удалить дерево баз
по невнимательности вызывающего нельзя.

- **`PROMOTE`** — потомки поднимаются к родителю удаляемой группы. Реализация — тот же
  посегментный `retarget`, где предком назначается родитель. Относительная структура
  подгрупп сохраняется. Затем секция группы удаляется.
- **`RECURSIVE`** — удаляются секция группы и все секции, чей путь `is_inside` её пути.

**[Р]** При `PROMOTE` проверяется коллизия: если у родителя уже есть группа с именем
поднимаемой подгруппы — отказ. Без проверки операция своими руками создала бы задвоенный
путь, который `RETARGET` запрещает.

**[Р]** Наши данные удалённых баз в `bases.json` не чистятся — как и сегодня при
`remove_infobase`. Побочный эффект полезен: база, удалённая по ошибке и возвращённая
с тем же `ID`, получает свою историю обратно.

Возвращает `bool` — была ли цель найдена, как `remove_infobase`.

### 3.6. Закрытие лазеек

| Вызов на секции-группе | Сейчас | Станет |
| --- | --- | --- |
| `update_infobase(key, {"Folder": ...})` | молча ломает дерево | `InvalidRequestError` |
| `update_infobase(key, new_name=...)` | `InvalidRequestError` в `_rename` | то же, единым правилом на границе |
| `remove_infobase(key)` | оставляет сирот | `InvalidRequestError`: нужен `remove_group` с политикой |

**[Р]** Вид секции проверяется при применении патча к свежему документу, а не по модели
координатора. Модель могла устареть, и вид секции мог смениться извне: **[Ф]** T-02.9 —
база, у которой платформа перестала распознавать `Connect`, деградирует до группы.
Решение о том, группа перед нами или база, обязано приниматься по тем байтам,
в которые мы сейчас пишем.

Дополнительно: при добавлении записи базы и при смене её `Folder` проверяется
существование целевой группы. Сегодня туда можно записать любой путь и получить сироту —
и на добавлении, и на правке одинаково.

`add_infobase` в остальном не меняется: она всегда пишет `Connect`, то есть всегда
создаёт базу.

## 4. Дедупликация источников

**[Р]** Запись, пришедшая и из пользовательского списка, и из общего с тем же ключом
привязки, показывается один раз. Выигрывает пользовательская: её данные лежат в файле,
который мы вправе править, и именно её правки увидит пользователь.

`InfobaseItem` получает поле `in_common_list: bool = False`. Заменять `source` набором
источников не нужно: `source` отвечает на вопрос «откуда взяты данные записи и можно ли
её править», и это по-прежнему ровно один источник.

Чистая функция в `catalog`:

```python
def dedupe(user_items, common_items) -> list[InfobaseItem]
```

Ключи пользовательских записей индексируются; запись из общего списка с совпавшим ключом
отбрасывается, а соответствующая пользовательская получает `in_common_list=True`.
Остальные записи общих списков проходят как есть. Порядок сохраняется: пользовательские,
затем общие — как сейчас в `Workspace._rebuild`.

**[Р]** Общие списки сводятся по ключу целиком, а не пофайлово. `CommonInfoBases`
объединяется со всех уровней `1cestart.cfg` **[Д]**, и одна база встречается в нескольких
файлах; уникальность `ID` **[Ф]** есть свойство файла, а не набора. Совпадение ключа
внутри одного файла сводится тем же правилом: там это либо патология формата, либо две
секции с одинаковыми именем и `Connect` — вторая запись не несёт информации, а источник
доступен только для чтения, и чинить пользователю в нём нечего. Выигрывает встреченная
раньше, то есть общий список более раннего уровня.

Первая редакция этого раздела обещала «дубли внутри одного источника не трогаем».
Обещание оказалось неисполнимым: `load_common_items` схлопывает файлы в один список
до дедупликации, и происхождение записи там уже не восстановить. Восстанавливать его
пофайловыми пачками — сложность ради поведения, которое показывает одинаковую запись
дважды.

**[Р]** Пользовательский список не сводится никогда. Он редактируемый, и дубль в нём
пользователь обязан увидеть, чтобы убрать.

`tree()` не меняется: дерево строится по пользовательскому списку, пометка живёт на записи.

Побочный эффект на `_reject_ambiguous_name`: сегодня та же база из двух источников уже
не считается соперником (фильтр `other.key != item.key`), но после дедупликации ветка
«часть записей пришла из общего списка» будет срабатывать только на настоящих разных базах.
Логика не меняется, тесты уточняются.

## 5. Отказы

Все — потомки `ServicesError`; иерархия уже есть.

| Условие | Исключение |
| --- | --- |
| Цель операции над группой — не группа | `InvalidRequestError` |
| Цель операции над базой — группа | `InvalidRequestError` |
| Цели с таким ключом в документе нет — при `UPDATE` записи базы и `RETARGET` группы | `TargetGoneError` |
| Цели с таким ключом в документе нет — при удалении | не ошибка: `applied=False`, как у `remove_infobase`. Пользователь хотел, чтобы группы не было, — её нет |
| Цель из общего списка | `ReadOnlySourceError` (существующий `_reject_common`) |
| Пустое имя группы или `/` в имени | `InvalidRequestError` |
| Целевого родителя не существует | `InvalidRequestError` |
| Путь занят другой группой — при создании, `RETARGET` и подъёме в `PROMOTE` | `InvalidRequestError` |
| Перемещение группы внутрь себя или своего потомка | `InvalidRequestError` |

Имена и пути групп секретами не являются и в сообщения идут. Ключи привязки — нет,
как и сейчас: суррогат несёт хеш строки соединения (инвариант 5 `CLAUDE.md`).

**[Р]** Коллизия путей отвергается, а не сливается молча. Две группы с одинаковым путём
ломают дерево уже сегодня: `build_tree` держит потомков в словаре по пути, и обе группы
получат один и тот же список детей — потомки отрисуются дважды.

## 6. Тестирование

TDD, `mypy --strict`, `ruff`, `pytest` — как в планах 1–3.

- **`paths.py`** — табличные тесты: корень и его записи (`/`, пустая строка, `/Клиенты`),
  посегментность (`Клиенты` против `КлиентыVIP`), `retarget` внутри и снаружи поддерева.
  Случай `КлиентыVIP` покрывается инлайновыми байтами, а не общей фикстурой: добавление
  секции в фикстуру ломает ожидания существующих тестов.
- **Каскад** — на фикстуре `tests/fixtures/anonymized.v8i`, где уже есть вложенность
  (`Клиенты` → `Розница` → база) и сирота. Переименовать верхнюю группу, проверить `Folder`
  потомков на всех уровнях; убедиться, что ключи привязки потомков не изменились,
  а избранное и история остались на местах. Новая фикстура не нужна.
- **Переигрывание при конфликте** — подменить файл между чтением и записью, добавив базу
  в переименовываемую группу: новая база обязана получить новый `Folder`. Этот тест
  и есть доказательство, что каскад считается по свежему документу, а не по устаревшему
  списку целей (§3.2).
- **Удаление** — `PROMOTE` (потомки у родителя, относительная структура цела),
  `RECURSIVE` (внутри удалено, снаружи цело), коллизия имён при подъёме.
- **Отказы** — по таблице §5, включая закрытые лазейки §3.6.
- **Дедупликация** — табличные: совпадение по `id:`, совпадение по суррогату, запись только
  в общем списке, только в пользовательском, выставление `in_common_list`.
- **Инвариант 1** — существующий тест в подпроцессе покрывает новые модули автоматически.

## 8. Состав работ

Ориентировочно шесть-восемь задач: `paths.py` и перевод `catalog` на него; `groups.py`
с тремя операциями; диспетчер в `edit.py` и `key_of_section` в `model.py`; методы
координатора; закрытие лазеек; дедупликация и поле модели. Детальная разбивка — в плане,
через `writing-plans`.

## 9. Отступления реализации от этого дизайна

Зафиксированы по итогам ревью, которые нашли в исходных формулировках реальные дефекты,
вскрывшиеся по ходу исполнения плана. Актуально то, что в разделах выше, а не
первоначальный текст.

| Что | Почему |
| --- | --- |
| Правило дедупликации развёрнуто: было «дубли внутри одного источника не трогаем», стало «общие списки сводятся по ключу целиком» (§4) | `load_common_items` схлопывает файлы общих списков в один плоский список до дедупликации — происхождение записи там уже не восстановить. Различение пофайловыми пачками — сложность ради поведения, которое показывает одинаковую запись дважды из источника только для чтения |
| Защита формата от перевода строки перенесена в `config` | Вне границ §1: общий фикс формата, не специфичный для групп и дедупликации. Подробности — в плане, раздел задачи 5 |
