## 3. Перестройка старта (подход 2)

### 3.1. Три доказанных источника зависания до окна

| Источник | Свидетельство |
| --- | --- |
| Чтение exe платформы (`executable_arch`, `open("rb")` × 7) | **[Ф] инцидент 15.08.2026**: `build_runtime` повис до показа окна на минуты; по прогретому кэшу антивируса тот же скан — 0,3 с. Причина «антивирус синхронно сканирует при открытии» — **гипотеза, не доказана**; наш дефект — не антивирус, а неограниченная работа с ФС до окна |
| Корни `InstalledLocation` из `1cestart.cfg` | Могут указывать на сетевой путь; `is_dir()`/`iterdir()` на мёртвой шаре ждёт SMB-таймаут. **Не воспроизводилось**, выведено из формата cfg |
| Общие списки (`CommonInfoBases`) | Читаются в конструкторе `Workspace` (`_reload`); в организациях лежат на сетевых шарах. **Не воспроизводилось**, выведено из формата cfg |

### 3.2. Разделение

**Синхронно до показа окна** (локальные малые файлы, миллисекунды): чтение двух
`1cestart.cfg`, правила версий, `ibases.v8i`, `bases.json`. Окно показывается сразу
с деревом пользовательских баз — как сейчас в норме.

**В фоне, двумя независимыми задачами** (зависание одной не топит вторую):

- обнаружение платформ — `find_installations` (скан корней + чтение exe);
- чтение общих списков.

### 3.3. Границы слоёв (инвариант 1)

Фоновые функции — чистые, без Qt, возвращают данные. Потоки, сигналы
и прогресс-диалог живут в `ui`. `Workspace` мутируется **только из главного
потока**: результат фона доставляется сигналом, главный поток вызывает
`set_installations(...)` / `apply_common_lists(...)` и перестраивает модель.

Изменения `Workspace`:

- конструктор не выполняет ни одного обращения к сетевым путям и exe.
  Готовый список установок передавать в конструктор можно (тесты,
  `run_launch` после обнаружения); `None` означает «ещё не известны» —
  это состояние отличается от «известно, что установок нет» (§3.4);
- чтение общих списков отделяется от применения: чтение (эффект, в фоне)
  возвращает данные, применение (чистое, в главном потоке) кладёт их
  в состояние. Следствие, найденное при планировании: сегодня `_rebuild`
  перечитывает общие списки с диска **при каждой перестройке** (любая
  операция со списком), то есть сетевые чтения происходят не только
  на старте. После перестройки общие списки — снимок, обновляемый только
  `apply_common_lists`; фоновая задача старта — единственный его источник.
  Слежения за изменением общих списков не было и не появляется;
- `reload_if_changed` не меняется.

### 3.4. Состояние «установки ещё не известны»

Пустой список установок и «обнаружение не завершено» — **разные состояния**,
и выводить второе из первого нельзя: до готовности колонка версии показывала бы
ложь «нет установленных версий». Признак готовности передаётся в расчёт колонки
явным аргументом:

- до готовности — колонка версии показывает «…», без подсветки проблемы;
- попытка запуска до готовности — вежливый отказ «Обнаружение платформ ещё
  не завершено», а не «нет установленных версий»;
- раздел общих списков появляется по готовности своей задачи.

В норме (тёплый кэш, ~0,3 с) пользователь этих состояний не успевает увидеть.

### 3.5. Путь `--ib-name` (ярлыки, окна нет)

Та же фоновая работа + `QProgressDialog` с кнопкой отмены; диалог показывается,
только если обнаружение не уложилось в ~0,5 с. Отмена обязана завершать процесс
даже при потоке, заблокированном в `open()`: убить поток Python нельзя,
поэтому фоновые потоки — демоны, выход — явный. Это проверяется тестом
на уровне «отмена ведёт к завершению, не дожидаясь фона».

Кэш установок для мгновенных ярлыков (подход 3) — **вне объёма**; добавляется
позже поверх, если ярлыки окажутся медленными на практике.

## 4. Видимость ошибок

### 4.1. Лог

`%APPDATA%\OneCStarter\logs\onecstarter.log`, `RotatingFileHandler` (3 × 512 КБ).
Фазы старта пишутся с таймстампами и длительностями: «обнаружение начато /
закончено за N мс, найдено K установок», «общие списки: M записей», «окно показано».
По последней строке лога видно, на какой фазе висим.

**Содержимое лога** (инвариант 5 плюс сценарий «приложите лог к issue»):
ни строк соединения, ни имён и путей баз, ни имён пользователей, ни путей
установок платформы (`InstalledLocation` может нести имя сервера организации).
Разрешены: счётчики, длительности, номера версий платформы, пути к **нашим**
файлам (`%APPDATA%\OneCStarter\...`). Правило охраняется тестом.

### 4.2. Перехват в `__main__`

Порядок в `main()` до любого импорта `ui`:

1. настроить лог (только stdlib, падать тут нечему; отказ создания лога
   не валит запуск — приложение важнее лога);
2. `faulthandler.enable()` в `logs/crash.log` — ловит падения нативного кода Qt;
3. всё остальное — внутри `try/except`: traceback в лог + системное окно
   `MessageBoxW` через `ctypes` (работает без Qt и без консоли —
   [из документации Windows]) с путём к логу, код выхода 1.

Это закрывает «`ModuleNotFoundError` ушёл в никуда» (§9 п. 4 спеки 4a):
отказ на импорте `ui` происходит уже под перехватом.

### 4.3. Консольный exe

Вторая точка входа той же сборки — `OneCStarterc.exe` (console). Тот же код;
при наличии консоли (`sys.stderr` не `None`) лог дублируется в stderr.
Сценарий диагностики для issues: «запустите консольный exe, пришлите вывод».

## 5. Сборка

- **`build/onecstarter.spec`** — единственный источник правды (правило `CLAUDE.md`):
  one-dir, один `Analysis`, два exe (`OneCStarter.exe` windowed,
  `OneCStarterc.exe` console), общий `COLLECT`.
- **Версия** читается spec-файлом из `pyproject.toml` (`tomllib`) — единственное
  место (правило `CLAUDE.md`); из неё же генерируется версионный ресурс Windows
  (свойства файла exe).
- **Иконка** `build/onecstarter.ico` генерируется скриптом `build/make_icon.py`
  из кодовой графики приложения (Qt offscreen, кадры 16–256 px, PNG-кадры внутри
  `.ico` — поддерживаются с Windows Vista [из документации]); без логотипа 1С
  (граница бренда из требований). Результат коммитится; замена — в любой момент.
- **`build/build.ps1`** — оркестратор: очистка → PyInstaller → **smoke** → zip →
  Inno Setup → отчёт (размеры каталога/zip/инсталлятора, версия). Ненулевой код
  любого шага прерывает сборку: требование «сборка заканчивается smoke-тестом»
  зашито в порядок, а не в дисциплину.
- **Smoke собранного экземпляра**: `OneCStarterc.exe --smoke` под offscreen
  с подменённым `APPDATA` (временный каталог — живые данные не трогаются,
  процессы 1С не порождаются): поднять рантайм, показать окно, создать ярлык
  на собранный exe **нашим кодом** (исполняется ветка `frozen=True` — закрывает
  шаг 8 задачи 17, долг №7), завершиться кодом 0. Скрипт smoke проверяет код
  выхода, цель ярлыка штатным читателем `.lnk` (WScript.Shell) и появление
  лог-файла с фазой «окно показано» в подменённом `APPDATA`.
- `.gitignore`: негации `build/` расширяются — сейчас выживает только `*.spec`,
  нужны `.iss`, `.ps1`, `make_icon.py`, `.ico`.

## 6. Установщик

`build/installer.iss`, Inno Setup 6 (**наличие на машине сборки не проверено** —
установка входит в план):

- per-user: `PrivilegesRequired=lowest`, без прав администратора,
  в `{localappdata}\Programs\OneCStarter`; ярлык в Пуске; деинсталлятор;
  русский + английский интерфейс; `AppId` фиксируется один раз;
- версию передаёт оркестратор (`/D`);
- деинсталляция **не трогает** `%APPDATA%\OneCStarter` (история, избранное,
  настройки) и `ibases.v8i` — «удаление ничего не теряет» из требований;
- артефакты не подписаны: сертификата нет, SmartScreen предупредит при первом
  запуске — честная строка в README, не дефект. Подпись — отдельное решение
  с деньгами, вне объёма.

## 7. Публикация

Порядок: вся работа — на ветке плана, слияние в `master`, и только затем
свежий корень из финального дерева.

1. **На ветке плана** (уходит в `master` обычным порядком):
   `.gitattributes` (`* text=auto`; `tests/fixtures/** -text` — фикстурам
   байтовая точность; `*.lnk binary`) + `git add --renormalize .` — закрывает
   долг №5 (CRLF); `LICENSE` MIT; `README.md` — русский основной, короткая
   EN-шапка: что это, скриншот, установка, сборка из исходников, границы,
   строка про SmartScreen; версия `0.1.0` в `pyproject.toml`; правки `ci.yml`
   по факту первого живого прогона.
2. **Свежий корень**: из дерева финального `master` создаётся один корневой
   коммит «OneCStarter 0.1.0»; `master` переставляется на него. Старая история —
   локальная ветка `archive/pre-publish-history`, **не пушится никогда**
   (в ней SID, коммит `4121853`). Дальнейшая работа — поверх нового корня,
   история снова одна. `.superpowers/` в git не входит и не публикуется.
3. **Аудит дерева перед push** — отдельный шаг с чек-листом по всему дереву,
   не по памяти: SID (`S-1-5-21`), имена машин, MAC, серийники томов, сетевые
   пути (`\\`), реальные имена баз и организаций; авторство корневого коммита
   (имя и email публикуются — подтвердить осознанно).
4. **GitHub**: создание репозитория (имя и аккаунт — решение заказчика,
   понадобится его участие либо авторизованный `gh`), push `master`,
   тег `v0.1.0`, Release с двумя артефактами и заметками на русском.

## 8. Тестирование

- Чистые функции (признак готовности в расчёте колонки версии) — табличные
  тесты; мутационная проверка на них не требуется (правило `CLAUDE.md`).
- `Workspace` (конструктор без сетевых чтений и exe, `set_installations`,
  `apply_common_lists`) — юнит-тесты; «конструктор не читает общие списки» —
  сторожевой тест с мутационной проверкой.
- UI-состояния «до готовности» — pytest-qt; сторожа геометрии и показа строятся
  на сравнении элементов, а не на замере против константы (урок
  `test_rail_buttons_fill_the_rail_regardless_of_label_width`).
- Защитные тесты — отказ запуска до готовности, изоляция smoke по `APPDATA`,
  отсутствие запретного в логе, завершение по отмене прогресса — проходят
  **мутационную проверку; мутацию ставит не автор теста** (правило 1 вводной).
- Smoke собранного экземпляра — исполняется каждой сборкой (`build.ps1`),
  не только вручную.
- Ручные контрольные точки заказчика: установка из инсталлятора на рабочей
  машине и запуск глазами, **включая холодный старт с непрогретым кэшем
  антивируса** — прямой тест инцидента 15.08; ярлык из установленного
  приложения на реальную базу — запуск 1С только с явного согласия.

## 9. Риски

| Риск | Смягчение |
| --- | --- |
| Антивирусы метят PyInstaller-exe как подозрительный (известная боль) | one-dir менее подозрителен, чем one-file; блокировка на машине заказчика исследуется, не обходится; Nuitka — запасной вариант (требования §6) |
| SmartScreen без подписи предупреждает | Строка в README; подпись — вне объёма |
| Qt-тесты на github-runner | `QT_QPA_PLATFORM=offscreen` в `ci.yml`, если первый прогон упадёт |
| Размер дистрибутива (PySide6, ~100+ МБ) | Отчёт сборки фиксирует размер; неиспользуемые Qt-модули в сборку не пускаются; охота на мегабайты не открывается |
| Свежий корень: потеря публичной истории решений | Осознанное решение заказчика (№3, §2); спеки и tasks.md публикуются в дереве и несут контекст |
