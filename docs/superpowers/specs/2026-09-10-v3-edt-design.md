## §0. Что здесь считается фактом

Проект не имел знания об EDT ни в скилах, ни в `temp/`: справочники ИТС в `temp/`
описывают платформу, не EDT. Всё знание вехи снято с рабочей машины заказчика
10.09.2026 и помечено уровнем достоверности. Легенда — как во всём проекте:
**[Ф]** проверено на реальной машине, **[Д]** из документации, **[?]** не проверено,
**[Р]** наше решение.

## §1. Решения заказчика

Каждый вопрос предъявлялся с вариантами и ценой; здесь — исход.

| Вопрос | Решение | Цена, признанная заказчиком |
| --- | --- | --- |
| Источник правды для списка проектов | **Свой реестр** в `%APPDATA%\OneCStarter\`, EDT Start — только импорт. В `projects.json` не пишем никогда | Два списка расходятся; проекты, заведённые в EDT Start позже, попадают к нам только импортом |

## §2. Модель и хранение

### Запись

```python
@dataclass(frozen=True)
class EdtProject:
    id: str            # uuid, ключ привязки
    name: str          # метка в списке
    workspace: str     # путь для -data; обязателен
    project_dir: str   # каталог для редакторов; "" — редакторы получают workspace
    edt_version: str   # точно как в имени каталога установки: "2025.2.6+4"
    jvm_dir: str       # каталог bin JDK; "" — JVM установки
    vm_args: str       # аргументы JVM записи; "" — действуют 1cedt.ini и установка
    group_id: str | None
```

### Группы и порядок

Группы — отдельный список `{id, name, parent_id}`; `parent_id: null` — корень.
Порядок записей и групп среди соседей — порядок в массиве файла. `OrderInList`,
каскадной перезаписи `Folder`, переигрывания патча на свежем файле — нет: формат
наш, штатный стартер его не трогает.

### Файл `%APPDATA%\OneCStarter\edt.json`

```json
{
  "schema": 1,
  "groups": [
    {"id": "g-1", "name": "2025", "parent_id": null}
  ],
  "projects": [
    {
      "id": "p-1",
      "name": "Розница (2025)",
      "workspace": "D:\\edt\\2025\\retail",
      "project_dir": "D:\\edt\\2025\\retail\\retail",
      "edt_version": "2025.2.6+4",
      "jvm_dir": "",
      "vm_args": "-Xmx8192m",
      "group_id": "g-1"
    }
  ]
}
```

Чтение/запись — по образцу `services/server_store.py`: атомарная запись
(`config/atomic.py`), повреждённый файл переносится в `.bad` с сообщением
пользователю, не сумели перенести — раздел недоступен с причиной (пустой список
затёр бы то, что пользователь мог достать из файла). Неизвестные ключи не
сохраняются: совместимость с чужим стартером здесь не нужна.

### Три уровня настроек запуска

| Уровень EDT Start | У нас | Где живёт |
| --- | --- | --- |
| Программа → Запуск | `edt_jvm_dir` (пусто = автоподбор; рядом версия из `release`), `edt_default_max_heap_mb = 8192`, `edt_default_language = ""` — умолчания для **новых записей** | `Settings`, группа «EDT» |
| Среда разработки (карандаш у версии) | `EdtInstallation` — `jvm_dir` и `vm_args` из `products.json` вживую при каждом обновлении, не только при импорте: правка в EDT Start подхватывается | Снимок обнаружения, не хранится |
| Проект | `EdtProject.jvm_dir`, `EdtProject.vm_args` | `edt.json` |

### `vm_args` — одна строка, два фасада

Хранится только строка. В диалоге записи она разложена на три поля чистой
функцией `split_vm_args(text) -> (max_heap_mb | None, language | None, rest)`:

- память — токен `-Xmx<N>(k|m|g)`, показывается в МБ; несколько токенов — берётся
  последний, при сборке остаётся один;
- язык — токен `-Duser.language=<код>`; список в диалоге: «По умолчанию» (токена нет),
  «Русский» (`ru`), «English» (`en`);
- прочее — остальные токены в исходном порядке.

`join_vm_args(max_heap_mb, language, rest)` собирает обратно: `rest`, затем `-Xmx`,
затем `-Duser.language`. Разбор — `shlex`-подобный с учётом кавычек Windows; токен,
который не удалось разобрать, остаётся в «прочем» как есть. Это то же, что
«Отредактировать как параметры Java VM…» у EDT Start, без второго источника правды.

### Версия — точное совпадение

Никакой «ближайшей подходящей», как у платформы: workspace привязан к версии EDT,
открытие другой версией запускает миграцию `.metadata`. Версия не установлена —
запись видна и помечена, «Открыть в EDT» недоступен с объяснением; редакторы
и Проводник работают.

## §3. Установки EDT и запуск

### Обнаружение — `platform_1c/edt_discovery.py`

Только чтение диска. Корни: `%ProgramFiles%\1C\1CE\components`,
`%LOCALAPPDATA%\1C\1cedtstart\installations`, плюс каталоги `location` из
`products.json`, где бы они ни лежали. Установка — каталог по маске
`1c-edt-<версия>-x86_64` с `1cedt.exe` внутри; версия — из имени каталога.
Из `1cedt.ini` читаются `-vm` (следующая строка после него) и
`-Dosgi.requiredJavaVersion=<N>`; ini нечитаем — установка есть, `required_java = 17`,
`-vm` нет.

```python
@dataclass(frozen=True)
class EdtInstallation:
    version: str          # "2025.2.6+4"
    exe: Path
    jvm_dir: Path | None  # подобранный каталог bin; None — не найден
    vm_args: str          # args продукта из products.json; "" — продукта там нет
    required_java: int
    jvm_source: str       # "products.json" | "1cedt.ini" | "settings" | "auto" | "" — для показа
```

### Подбор JDK — чистая функция над снимком

По порядку, первый существующий на диске:

1. `jvmPath` продукта из `products.json` (URL `file:///…` → путь, `%20` раскрыт,
   завершающий слэш снят);
2. `-vm` из `1cedt.ini` (файл `javaw.exe` → его каталог);
3. `edt_jvm_dir` из настроек;
4. самый старший каталог `axiom-jdk-full-*` или `*jdk*` в корнях обнаружения, чья
   версия из `release` (`JAVA_VERSION`) ≥ `required_java`;
5. `None` — «JDK не найден»: где искали и что требуется.

Существование пути проверяется снаружи чистой функции: ей подаётся множество
существующих кандидатов.

### Командная строка — `domain/edt.py::build_edt_command`

Чистая функция `(project, installation) -> LaunchCommand`:

```
<exe> -data <workspace> -vm <project.jvm_dir или installation.jvm_dir>
      --launcher.appendVmargs -vmargs <installation.vm_args> -Djava.library.path= <project.vm_args>
```

Дословно повторяет снятую с процесса **[Ф]**, включая `-Djava.library.path=`
(EDT Start ставит его всегда, у 2025/2026 он и в ini). Пустые `vm_args` дают
`-vmargs -Djava.library.path=` — допустимо. `jvm_dir` нет ни у записи, ни
у установки — отказ до запуска (§8).

### Запуск

Существующий `platform_1c/process.spawn` — отсоединённый процесс, без ожидания:
EDT живёт дольше нас. Рабочий каталог — каталог `1cedt.exe`.

## §4. Статус «запущен» и активация окна

### Сопоставление процесса с записью — `domain/edt.py::running_workspaces`

Вход — `ProcessScanner.snapshot({"1cedt.exe"})` (есть, psutil, единственное место)
и список записей. В `argv` ищется `-data` и следующий элемент; путь нормализуется
без обращения к диску (`os.path.normcase(os.path.normpath(...))`) и сравнивается
с так же нормализованным `workspace`. `argv is None` (нет доступа) — процесс
пропускается. Результат — `{workspace_key: pid}`.

### Опрос

Тот же фоновый монитор, что у серверов (`ui/servers/monitor.py`, `QTimer` 5 с,
снимок в потоке-демоне): второй экземпляр с именем процесса `1cedt.exe` и своим
сопоставлением; общий снимок на оба раздела — только если монитор серверов
параметризуется без правки его поведения. Точка статуса в дереве, `F5` — принудительно.

### Повтор — `platform_1c/window_activate.py`

Единственный Win32-модуль вехи, ctypes без новых зависимостей:
`EnumWindows` → окно с `GetWindowThreadProcessId == pid`, видимое, верхнего уровня,
с непустым заголовком → `ShowWindow(SW_RESTORE)`, если свёрнуто →
`SetForegroundWindow`. Windows разрешает перехват фокуса процессу, у которого
фокус сейчас, — у нас, пользователь только что кликнул **[?]** (эксперимент 2).
Окно не нашлось (splash ещё не сменился главным окном) — молча ничего: ложное
«не запущен» хуже отсутствия реакции. Функция принимает PID и возвращает
`bool`; в `domain` не попадает.

## §5. Редакторы

### Поиск — `platform_1c/editors.py`, приоритет — чистая функция

| Редактор | Настройка | PATH | Известные каталоги |
| --- | --- | --- | --- |
| VS Code | `editor_vscode` | `code.cmd`, `code` | `%LOCALAPPDATA%\Programs\Microsoft VS Code\bin\code.cmd` **[Ф]**; `%ProgramFiles%\Microsoft VS Code\bin\code.cmd` **[?]** системная установка |
| Antigravity | `editor_antigravity` | `antigravity-ide.cmd`, `antigravity-ide` | `%LOCALAPPDATA%\Programs\Antigravity IDE\bin\antigravity-ide.cmd` **[Ф]** |

Приоритет: настройка непуста — только она; пуста — PATH, затем известные каталоги.
Настройка указывает на несуществующий файл — редактор «не найден», автопоиск
не подменяет явное указание молча: в Настройках рядом с полем видно и что нашлось
автоматически, и что указанный путь не существует.

### Вызов

`[cli, <каталог>]` отсоединённым процессом через `process.spawn`; каталог —
`project_dir`, пустой — `workspace`. Оба лаунчера `.cmd` — зона известных проблем
с кавычками **[?]** (эксперимент 3). Если эксперимент покажет отказ — вызов
через `cmd.exe /c` с явным экранированием, решение фиксируется в скиле.

### Меню

Редактор не найден — пункт неактивен с подсказкой «не найден, укажите путь
в Настройках». Найден, `project_dir` пуст — пункт активен, открывается workspace.
«Открыть в Проводнике» — `os.startfile(каталог)`, тот же выбор каталога; выручает
с третьим редактором.

## §6. Импорт из EDT Start

### Чтение — `platform_1c/edtstart_registry.py`

Только чтение `products.json` и `projects.json`. Разбор терпимый: неизвестные
ключи игнорируются; запись без `location` или `productId` пропускается со счётчиком
«пропущено N»; `jvmPath` — URL → путь. Файла нет или JSON битый — «EDT Start
не найден / реестр не читается», импорт недоступен с причиной, раздел работает.

```python
@dataclass(frozen=True)
class EdtStartProduct:
    id: str
    version: str      # installedVersion.label
    exe: Path
    jvm_dir: Path | None
    args: tuple[str, ...]

@dataclass(frozen=True)
class EdtStartProject:
    id: str
    label: str
    workspace: Path
    product_id: str
    args: tuple[str, ...]
    jvm_dir: Path | None   # [?] ключ jvmPath, эксперимент 4
```

### Дифф — `domain/edt.py::import_candidates`

Чистая: кандидат — проект EDT Start, чей нормализованный `workspace` не совпадает
с `workspace` ни одной нашей записи. Повтор ничего не дублирует. Отображение:
`label → name`, `location → workspace`, `product.version → edt_version`,
`" ".join(args) → vm_args`, `jvm_dir → jvm_dir`, `project_dir = ""`.
`productId` без продукта → кандидат помечен «версия неизвестна», `edt_version = ""`,
запись сразу требует правки. `args` продукта в запись **не копируются** — они
остаются на уровне установки и читаются вживую (§2).

### Диалог

Список кандидатов с галочками (все отмечены): имя, workspace, версия. Отмеченные
добавляются в корень. Список записей пуст, реестр EDT Start есть — над деревом
баннер «Список пуст. Импортировать из EDT Start?» с кнопкой; состояния у баннера
нет, он исчезает с первой записью.

## §7. Интерфейс

Раздел **«EDT»** на рейле между «Серверы» и «Настройки», значок — в `rail_icons`.

**Дерево**: группы и записи, фильтр по набору текста как у баз; колонки — имя,
версия EDT (не установлена — подсветка как у баз), точка статуса. Enter и двойной

**Контекстное меню**: Открыть в EDT · Открыть в VS Code · Открыть в Antigravity ·
Открыть в Проводнике · — · Добавить… · Изменить… · Удалить · — · Создать группу ·
Переименовать группу · Удалить группу · — · Импорт из EDT Start… Удаление записи
и группы — с подтверждением; удаление группы с содержимым переносит содержимое
к родителю (единственный вариант, выбора нет — записей мало, каскадное удаление
не нужно).

**Дополнение 10.09.2026** — после «Открыть в Проводнике» подменю **CLI**:
Пересобрать проекты · Импортировать проект… · Проверить проекты… · Информация
по проектам (§14).
Подменю неактивно для записи со статусом «запущен» (подсказка «закройте EDT:
workspace занят») и для записи с выполняющейся командой; «Открыть в EDT» неактивен,
пока команда выполняется.

**Перетаскивание**: внутри дерева — порядок и группа; каталог из Проводника —
диалог добавления с предзаполненным `workspace`.

**Диалог записи**: имя · workspace (обзор) · каталог проекта (обзор, необязателен) ·
версия EDT (список установленных; текущее значение записи, если не установлено,
остаётся в списке с пометкой) · JVM (обзор; пусто — «JVM установки: <путь, версия>») ·
память, МБ (редактируемый список 2048/4096/8192/12288/16384; пусто — без `-Xmx`) ·
язык · прочие параметры JVM. Новая запись предзаполняется из настроек §2.
Проверки до сохранения: имя и workspace непусты; workspace — абсолютный путь.

**Настройки**, группа «EDT»: JVM по умолчанию (обзор; рядом версия из `release`
и что подобрано автоматически), память по умолчанию, язык по умолчанию, путь к VS Code,
путь к Antigravity (рядом — что нашлось автоматически).

## §9. Тесты и мутационная проверка

**Табличные (чистые функции)**: `build_edt_command` (JVM записи / установки,
`vm_args` пустые / заполненные на обоих уровнях); подбор JDK по цепочке (каждый шаг
и промах всех); разбор `1cedt.ini` (с `-vm`, без, нечитаемый); `split_vm_args` /
`join_vm_args` (повтор `-Xmx`, единицы `k/m/g`, кавычки, неразбираемый токен,
roundtrip); `running_workspaces` (регистр, слэши, `argv is None`, `-data` последним
элементом без значения); `import_candidates` (идемпотентность, неизвестный продукт,
пропуск записей без ключей); приоритет поиска редактора.

**CLI (дополнение 10.09.2026)** — табличные: `build_cli_command` (порядок
`-command` до `-vmargs`, свойства кодировки, JVM записи/установки), `quote_cli_arg`
(пробел, кириллица, одинарная кавычка внутри), сборка строк `build --yes`, `project`,
`import` по обоим вариантам диалога (каждое необязательное поле — свой ряд),
`validate` (один путь, несколько, файл с пробелом в имени); перечень проектов
workspace из снимка каталога (подкаталог без `.project` пропущен, `project_dir`
вне workspace добавлен, внутри — не задвоен); исход процесса → событие журнала
(код, прерывание). Мутационная проверка: «команда
на занятом workspace не запускается» — убрать проверку статуса, тест падает на
вызове `spawn`; «второй запуск на той же записи отклонён» — то же.

**Хранилище**: roundtrip `edt.json`, `.bad`, недоступный перенос.

**UI**: pytest-qt по образцу `ui/servers`: дерево строится из файла, фильтр,
контекстное меню по состоянию (версия не установлена, редактор не найден, запущен),
диалог записи собирает `vm_args` из фасадов, импорт добавляет только отмеченное.

**Мутационная проверка** (CLAUDE.md, «Процесс») обязательна для:
`.bad` — сломать перенос, тест должен упасть на пропаже данных; идемпотентность
импорта — убрать фильтр по существующим, тест падает на дубле; отказ запуска
без JDK — убрать проверку, тест падает на вызове `spawn`; «повтор не плодит второй
процесс» — убрать ветку активации, тест падает на втором `spawn`.

**Фикстуры** — обезличенные `products.json` / `projects.json` с сохранением структуры:
продукт, которого нет на диске; проект без `args`; проект с `jvmPath`; `location`
с кириллицей и пробелом; продукт с `jvmPath` в виде `file:///` с `%20`.
Реальные метки и пути заказчика в репозиторий не попадают.

## §14. CLI EDT — дополнение заказчика 10.09.2026

Факты — §0-Д, решения — §1 (последние пять строк).

### 14.1. Ограничение, задающее форму

CLI — headless-Eclipse на том же `-data`. Workspace, открытый в EDT, для него
занят (**[Д]** `WORKSPACE_IN_USE`), и наоборот: пока идёт команда, EDT на этот
workspace не откроется. Отсюда два правила интерфейса, оба — на статусе из §4:

- подменю CLI неактивно для записи «запущен» (подсказка «закройте EDT: workspace занят»);
- «Открыть в EDT» и подменю CLI неактивны для записи с выполняющейся командой.

Честная область применения — сборка, импорт и проверка **до** открытия workspace
и для workspace, с которыми не работают прямо сейчас. Это уже, чем «ПКМ → пересобрать»
на текущем проекте, и заказчик это принял (§1).

### 14.2. Пункты и команды

| Пункт | Команда в `-command` | Диалог |
| --- | --- | --- |
| Пересобрать проекты | `build --yes` — все проекты workspace | Нет; подтверждение до запуска: «Пересобрать все проекты workspace <имя>? Это займёт время» |
| Импортировать проект… | Переключатель «Существующий проект EDT»: `import --project '<каталог>'`. «Файлы конфигурации XML»: `import --configuration-files '<каталог XML>'` + `--project '<каталог>'` **или** `--project-name '<имя>'` + необязательные `--base-project-name '<имя>'`, `--version <8.3.x>`, `--build` | Да: каталог проекта; каталог XML; каталог **или** имя нового проекта (взаимоисключающие); базовый проект (для расширений и внешних обработок); версия платформы; галочка «Собрать после импорта» |

### 14.3. Командная строка — `domain/edt_cli.py::build_cli_command`

```
<каталог установки>\1cedtcli.exe -data <workspace> -command "<команда>"
    -vm <jvm записи или установки> --launcher.appendVmargs
    -vmargs <vm_args установки> -Djava.library.path= <vm_args записи>
    -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8
    -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8
```

`-command` стоит до `-vmargs` (**[?]** эксперимент 6). JVM и память — те же, что
для EDT (§3): сборка большой конфигурации без `-Xmx` записи упрётся в `-Xmx4096m`
из ini. Свойства кодировки — обе пары, для JDK 17 и для 19+ (**[?]** эксперимент 6);
не подействуют — панель всё равно читает с `errors="replace"`. `1cedtcli.exe` в каталоге
установки отсутствует — подменю неактивно (§8).

### 14.4. Выполнение — `services/edt_cli.py`

- **Порождение** — `platform_1c/server_spawn.py::spawn_server` как есть: stdout и
  stderr ребёнка — в файл журнала хендлом `FILE_APPEND_DATA`, процесс — в `Job`
  (`platform_1c/job.py`), окно консоли не создаётся. `spawn_server` дополняется
  возвратом хендла процесса; серверы этим не пользуются, их поведение не меняется.
- **Журнал** — `%APPDATA%\OneCStarter\edt-journal\<id записи>.log`, ротация
  «текущий → прошлый» на каждый запуск (`server_journal.rotate_journal`); наши
  события — `append_event`: старт с полной командной строкой, завершение с кодом,
  прерывание. Два писателя одного файла — тот приём, что у серверов (докстринг
  `server_journal.py`).
- **Код завершения** — поток-демон ждёт хендл (`WaitForSingleObject`), читает
  `GetExitCodeProcess`, результат в UI сигналом Qt — тот же приём, что у фоновых
  проверок доступности. Число — в событие журнала и в заголовок консоли; имя кода —
  после эксперимента 7 по таблице в скиле.
- **Одна команда на запись**; на разных записях — параллельно, без лимита:
  workspace разные, а память — забота пользователя, как при двух открытых EDT.
- **Прервать** — кнопка в консоли, подтверждение «Прервать <команда>? Сборка
  останется незавершённой, EDT пересоберёт при следующем открытии» (**[?]**
  поведение Eclipse при убитой сборке), затем `TerminateJobObject` через `Job`.
- **Выход из программы** с живой командой — тот же вопрос, что у серверов
  («прервать N команд и выйти?»); молчаливого убийства нет.

### 14.5. Консоль — `ui/edt/console_panel.py`

Обёртка над `ui/servers/journal_panel.py::JournalPanel` (используется как есть,
тот же tail файла и та же палитра) с заголовком-кнопкой и состоянием свёрнуто/раскрыто:

- под деревом, **свёрнута по умолчанию** — виден только заголовок;
- **раскрывается автоматически при запуске команды** и переключается на журнал
  этой записи; свёрнутая вручную — остаётся свёрнутой до следующего запуска;
- заголовок: «Консоль ▾ · <запись> · <команда> · выполняется / завершено, код N /
  прервано»; кнопки «Прервать» (пока выполняется), «Открыть журнал» (файл
  в системном редакторе) и «Открыть результат» (только после `validate` с кодом 0
  и существующим TSV);
- выбор другой записи в дереве переключает содержимое на её журнал (прошлый запуск
  тоже читается), **не раскрывая** панель;
- состояние свёрнуто/раскрыто не сохраняется между сеансами.
