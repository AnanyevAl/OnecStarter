## §1. Обнаружение установок EDT вне Program Files

### §1.0. Повод и корень проблемы

Пользователь: EDT ставится не обязательно в Program Files, каталог выбирает сам
пользователь; у него установка лежит в
`C:\Users\<user>\AppData\Local\1C\1cedtstart\installations\1C_EDT 2026.1\1cedt`.
Просьба — искать установки и там, и дать задать каталог вручную в настройках.

Первая половина просьбы уже реализована и не работает. Второй корень
(`%LOCALAPPDATA%\1C\1cedtstart\installations`) в `platform_1c/edt_discovery.py::default_roots`
стоит с вехи v3. Мешают ему **три независимых дефекта**, и чинить нужно все три —
каждый в одиночку способен спрятать установку:

1. **`product.version` из `products.json` не используется вовсе.**
   `discover_edt` добавляет установку из реестра в словарь кандидатов, а затем на
   `version_from_dir_name(folder.name)` выбрасывает её, если имя каталога не по маске.
   Установка, версию которой знает сам EDT Start, теряется.
   Это худший из трёх: ответ у нас на руках, и мы его игнорируем.
2. **Версия берётся только из имени каталога** — маска `^1c-edt-(<версия>)-x86_64$`.
   Каталог `1C_EDT 2026.1` её не проходит, а имя каталога выбирает пользователь.
3. **Скан идёт на глубину 1.** В пользовательском корне `1cedt.exe` лежит уровнем ниже.

### §1.1. Цепочка определения версии

`discover_edt` перестаёт спрашивать версию у имени каталога и спрашивает её по цепочке.
Первый непустой ответ выигрывает:

| № | Источник | Достоверность |
| --- | --- | --- |
| 1 | `products.json`: `installedVersion.label` продукта, найденного по нормализованному пути `1cedt.exe` | **[Ф]** |
| 2 | `<установка>\configuration\config.ini`: `product.version` и `eclipse.buildId` | **[Ф]** |
| 3 | Имя каталога по маске `1c-edt-<версия>-x86_64` | **[Ф]** |
| 4 | Ничего не дало — установка **не показывается** | **[Р]** |

Реестр первым, а не диск: `installedVersion.label` — это ровно та строка, которую
пользователь видит в 1C:EDT Start, и совпадение метки с именем каталога **[Ф]** означает,
что порядок 1↔3 нынешнее поведение не меняет.

**Отказ показывать установку без версии — решение заказчика 25.09.2026.** Версия здесь не
украшение: `EdtProject.edt_version` (`domain/edt.py`) — ключ привязки записи проекта к
установке. Установка без версии эту привязку ломает, а подстановка имени каталога вместо
версии сделала бы привязку зависимой от имени каталога, которое пользователь волен
переименовать. Реальные установки покрыты шагами 1–3; выпасть может только битый каталог,
и про него надо не гадать, а сказать вслух — §1.4.

### §1.2. Склейка версии из `config.ini`

Новая **чистая** функция `domain/edt.py::version_from_config_ini(text: str) -> str | None`.
Инвариант 2 соблюдён: ни ФС, ни процессов внутри, на вход — текст, покрытие табличными
тестами.

Правило склейки:

- `product.version=X.Y.Z` и `eclipse.buildId=X.Y.Z.B` (тот же префикс, ровно один лишний
  компонент) → `X.Y.Z+B`;
- `product.version` есть, `eclipse.buildId` отсутствует, не разбирается или префикс не
  совпал → `X.Y.Z` без `+B`;
- `product.version` нет → `None`.

Порядок строк в файле произвольный **[Ф]**: в 2026.1.2+2 `product.version` идёт раньше
`eclipse.buildId`, в 2026.2.1+3 — позже. Формат — Java properties; читаем только эти два
ключа, остальное игнорируем, как `parse_ini`.

Осторожность в правиле префикса намеренная: `+B` — часть метки, которой пользователь
различает сборки, и приклеить к версии чужое число хуже, чем не приклеить своё.
Расхождение префикса на снятых установках не наблюдалось **[Ф]**, ветка существует как
страховка и покрывается табличным тестом.

### §1.3. Скан корней: глубина у каждого своя

Один обход ищет и установки, и JDK, и **останавливается на обоих видах листьев**:

- каталог с `1cedt.exe` — установка, внутрь (`plugins`, `features`, `p2`) не заходим;
- каталог с файлом `release` и подкаталогом `bin` — JDK, внутрь не заходим.

Отсечение ветки JDK — не микрооптимизация: без него глубина 3 на `components` стоит
48,6 мс и 246 каталогов вместо 23,1 мс и 63 **[Ф]**. Заодно оно убирает нынешний
`_auto_jdks` как отдельный проход по тем же корням.

Глубина считается от корня: уровень 0 — сам корень, 1 — его подкаталоги, 2 — их
подкаталоги. **Уровень 0 проверяется тоже** — это не мелочь, а страховка §1.5: путь,
указанный прямо на каталог установки, работает независимо от того, угадали мы глубину
или нет.

Глубина задаётся **у каждого корня отдельно**, а не одна на всех:

| Корень | Глубина | Почему |
| --- | --- | --- |
| `%ProgramFiles%\1C\1CE\components` | 2 | Управляется установщиком 1С, раскладка проверена **[Ф]**: exe на уровне 1. Уровень запаса стоит 1,9 мс; глубина 3 стоила бы 23,1 мс — в 38 раз дороже уровня 1 без единого известного случая, который бы это окупил |
| `%LOCALAPPDATA%\1C\1cedtstart\installations` | 3 | Раскладка неизвестна и проверить её нечем (§1.5). Корень узкий: EDT Start кладёт туда по каталогу на версию, и глубина 3 против 2 стоит **+0,04 мс** **[Ф]** |
| Ручной каталог из настроек | 3 | Форму задаёт пользователь — та же неизвестность и та же узость |

Асимметрия здесь — не частный случай ради одного пользователя, а прямое следствие того,
кто владеет каталогом: у корня установщика раскладка известна, у корней, которые лепит
человек, — нет. Веха 3.2.1 занималась замираниями интерфейса на холодном сервере, и
платить 23 мс на каждом обнаружении за догадку о раскладке чужого каталога здесь нечем.

Тип корня — `EdtRoot(path, max_depth)`; `default_roots` возвращает список таких пар.

### §1.4. Настройка и диагностика

**Настройка.** Новый ключ `edt_installations_root: str = ""` в `services/settings.py`,
рядом с `edt_jvm_dir`/`edt_schemes_dir`. Пустая строка — только корни по умолчанию;
заданный каталог **добавляется** к ним, не заменяет их, и сканируется тем же
`find_installations` с глубиной 3 (§1.3). Дубли схлопываются по нормализованному пути
`exe`, как сейчас, поэтому порядок корней на результат не влияет.

Указать можно **и корень с установками, и сам каталог установки** — уровень 0 обхода
(§1.3) принимает оба. Это главный запасной выход вехи: если раскладка окажется глубже,
чем мы угадали, пользователь всё равно доберётся до своей EDT, указав каталог с
`1cedt.exe` напрямую.

В разделе «Настройки», группа EDT, **первой строкой группы** (до «JDK по умолчанию»):
«Каталог установок EDT» — поле пути и «Обзор…», приёмом `_path_control`, как «Каталог
цветовых схем». Подпись под полем — не статический текст, а результат:
сколько установок найдено. Это ровно та обратная связь, которой сейчас не хватает
пользователю, чтобы понять, почему EDT не видно:

- пусто → «Не задан — ищем в Program Files и `%LOCALAPPDATA%\1C\1cedtstart\installations`»;
- задан, установки есть → «Найдено установок: N»;
- задан, установок нет → «Установок не найдено. Подойдёт и каталог с установками,
  и сам каталог, в котором лежит `1cedt.exe`».

Третья формулировка названа так намеренно: она не просто сообщает о неудаче, а называет
действие, которым пользователь выберется сам.

`EdtNotes` (`services/edt.py`) получает поле `installations`, `_refresh_edt_notes`
обновляет строку после сохранения пути — тем же швом, что у JDK и редакторов.

**Диагностика — обязательная часть вехи, а не украшение.** Раз раскладку у пользователя
проверить нечем (§1.5), лог остаётся единственным способом узнать, угадали мы или нет.
Без него следующее обращение будет таким же пересказом, и веха 3.2.3 начнётся с того же
тупика.

`discover_edt` начинает возвращать `EdtDiscovery` — датакласс с полями `installations`
и `rejected` (пары «каталог, причина»: «нет версии», «нет `1cedt.exe`»). Логирует не
`platform_1c` (ни один модуль этого пакета не логирует — логи живут в `services/`, `ui/`,
`perf`, `diagnostics`), а `ui/app.py::edt_discover`. Производственный вызов `discover_edt`
ровно один, поэтому смена типа возврата стоит дёшево.

В лог при обнаружении идут:

- перечень просканированных корней с их глубиной и числом найденных в каждом установок —
  включая корни, которых на диске нет;
- отброшенные кандидаты с причиной (при непустом `rejected`).

Число найденных корней и установок печатается всегда, а не только при неудаче: «ноль
установок в корне, который существует» — это и есть картина разбираемого случая, и
отличить её от «корня нет вовсе» по логу нужно с первого взгляда.

Строка `smoke: edt=%d` (`run_smoke`) дополняется числом отброшенных.

### §1.5. Раскладка остаётся непроверенной. Риск принят

Раскладка `installations\1C_EDT 2026.1\1cedt\` — **[?]**: это пересказ из сообщения,
а не листинг. На машине разработчика каталог `installations` пуст **[Ф]**, проверить
нечем, и получить листинг с машины пользователя не получится — **решение заказчика
25.09.2026**. Делаем вслепую.

Это меняет не дизайн, а его обоснование. Раз проверить нечем, веха держится не на
угадывании одного числа, а на четырёх независимых способах добраться до установки —
чтобы промах в любом одном не оставил пользователя ни с чем:

| Способ | Работает, когда |
| --- | --- |
| §1.1, шаг 1: версия из `products.json` | Установку поставил сам EDT Start — а именно он владеет каталогом `installations` (`productsRoot` в `preferences.json` **[Ф]**). Наиболее вероятный случай, и он не зависит от глубины вовсе |
| §1.3: глубина 3 на пользовательских корнях | Установка лежит не глубже третьего уровня и её нет в реестре |
| §1.2: версия из `config.ini` | Имя каталога произвольное и в реестре установки нет |
| §1.4: ручной путь **прямо на каталог установки** | Промахнулись все три предыдущих |

Последняя строка — та, ради которой уровень 0 проверяется в §1.3. Она закрывает случай
любой глубины и любой раскладки ценой одного действия пользователя.

**Проверка переносится на живой запуск у пользователя.** Признак успеха — установка
появилась в разделе EDT без правки настроек. Признак промаха — лог обнаружения (§1.4),
где видно, какие корни просканированы и что в них найдено; по нему раскладка
восстанавливается без просьб о листинге. Пока этого не случилось, в `docs/tasks.md` и
в скиле `edt-launch` раскладка остаётся **[?]** со ссылкой на источник «со слов
пользователя» — за проверенную она не выдаётся ни при каком исходе сборки.

Отдельно о том, чего дизайн **не** делает: сканировать глубже третьего уровня или искать
`1cedt.exe` по всему диску. Неопределённость не лечится расширением поиска — она лечится
тем, что у пользователя есть работающий запасной выход, а у нас лог, по которому видно,
что произошло.

## §2. Alt+1…Alt+N по разделам

### §2.1. Поведение

`MainWindow` (`ui/shell.py`) регистрирует `QShortcut` на каждый раздел по его порядковому
месту в рельсе: 1 — «Базы», 2 — «Серверы», 3 — «EDT», 4 — «Настройки». Нумерация идёт
от списка `sections`, а не от жёсткой таблицы: добавление раздела автоматически даёт ему
следующий номер. Разделы после девятого сочетания не получают (`Alt+0` не занимаем).

Контекст — окно (умолчание `Qt.WindowShortcut`): модальные диалоги сочетание не
перехватывают, а мнемоник у кнопок рельсы нет (`setText("Базы")` без `&`), так что
конфликта с автомнемониками Qt не возникает.

Подсказка кнопки рельсы становится «Базы (Alt+1)» — сочетание должно быть видно там, где
на него нажимают, а не только в справочнике.

### §2.2. Справочник в настройках

В `ui/shortcuts.py` — новая таблица `WINDOW_SHORTCUTS` с **одной** строкой:
«Alt+1 … Alt+4» → «Перейти в раздел по порядку в левой панели». В разделе «Настройки»
она показывается в группе «ГОРЯЧИЕ КЛАВИШИ» отдельным блоком «Окно», рядом с блоками
«Базы» и «EDT».

Строка намеренно обобщённая, без перечисления имён разделов: имена живут в `ui/app.py`,
и копия в `ui/shortcuts.py` стала бы второй правдой, расходящейся при первом же
переименовании. Диапазон в подписи (`Alt+1 … Alt+4`) строится из числа разделов, а не
пишется буквой.

### §2.3. Известное ограничение

Глобальный хоткей (`Ctrl+Alt+B` по умолчанию), если пользователь назначит его на
`Alt+<цифра>`, перехватит сочетание системно и до окна оно не дойдёт. Не чиним и не
запрещаем: это свойство `RegisterHotKey`, а не наш дефект, и цена запрета — разбор
пересечений в `HotkeyEdit` ради случая, которого никто не просил. Фиксируется в
`docs/tasks.md` как известное ограничение.

## §3. Расшифровка кодов возврата CLI

### §3.1. Где настоящая дыра

Просьба «нужна не только цифра, но и пояснение» выполнена наполовину и не там, где
пользователь смотрит. Таблица `CLI_STATUS_TEXTS` есть в `ui/edt/console_panel.py`, и шапка
консоли через `state_finished` показывает «завершено, код 202 (рабочая область занята
другим приложением)».

А в **журнал** — файл, который пользователь открывает кнопкой «Открыть журнал» и
присылает в поддержку — `services/edt_cli.py::finish` пишет голое
`■ завершено, код 204`. Шапка живёт до следующего запуска, журнал остаётся.

### §3.2. Одна таблица на оба места

`CLI_STATUS_TEXTS` и функция `status_text(code: int) -> str` переезжают из
`ui/edt/console_panel.py` в `domain/edt_cli.py`. Причина не косметическая: журнал пишет
`services/edt_cli.py`, которому импорт из `ui/` запрещён инвариантом 1. `console_panel`
импортирует `status_text` оттуда же — одна таблица, два потребителя.

Таблица — протокол Э7 (`help --status-codes`, EDT 2026.1.2+2, 13.09.2026,
`docs/research/t17-edt-experiments.md`), целиком **[Ф]**. **Исправлено находкой финального
ревью ветки:** первая редакция этого раздела дополняла таблицу «по документации ИТС», помечая
код 13 и формулу 128+сигнал как **[Д]** со ссылкой на «документация ИТС, скриншот
25.09.2026». Такого скриншота веха не снимала — оба факта с самого начала были частью того
же измерения `help --status-codes`, что и вся остальная таблица (см. правку кода и скила,
коммиты `29cc0c4`, `1c07b8a`, `3c3c856`), а не отдельным источником. Заявленная атрибуция
«документация ИТС, скриншот» для факта, снятого командой на живой машине, — ложная
атрибуция, а не просто заниженная метка:

| Код | Текст | Источник |
| --- | --- | --- |
| 0 | без пояснения | **[Ф]** Э7 |
| 1 | не удалось запустить CLI: не найден `1cedt.ini`, не создан временный файл или рабочая область (либо отказ `cmd.exe`) | Первые две причины — **[Ф]** Э7; третья («отказ `cmd.exe`») — из ДРУГОГО замера, тоже **[Ф]**: предел длины строки `cmd.exe` (`_CMD_MAX_LINE`, ревью 13.09.2026), не документация |
| 13 | 32-разрядная JVM (источник называет это лишь ПРИМЕРОМ кода среды исполнения, не общим правилом «код = разрядность» — текст сужен до измеренного) | **[Ф]** Э7 |
| 200 | общая ошибка, см. журналы рабочей области | **[Ф]** Э7 |
| 201 | файл скрипта не найден | **[Ф]** Э7 |
| 202 | рабочая область занята другим приложением | **[Ф]** Э7 |
| 203 | команда прервана, скорее всего по таймауту | **[Ф]** Э7 |
| 204 | команда прервана исключением, см. журналы рабочей области | **[Ф]** Э7 |
| 205 | таймаут, процесс убит | **[Ф]** Э7 |
| 128 < код < 256 | процесс убит сигналом ОС (сигнал `код − 128`) | **[Ф]** Э7 |
| прочее | код команды или JVM | **[Р]** |

`128+сигнал` — вычисляемая ветка, а не 128 строк в словаре. Оговорка о том, что конкретное
значение зависит от оболочки и среды исполнения, на формулу не влияет: мы называем наиболее
вероятное значение, а не утверждаем единственное.

Хвост «код команды или JVM» для неизвестных кодов — **[Р]**: команда в режиме `-command`
может вернуть своё число, и молчать о том, что число вообще может быть чужим, хуже, чем
сказать это девятью словами. Текст короткий намеренно — он попадает в узкий `QLabel` шапки.

Таблица оговаривается в коде как **неполная по своей природе**: ИТС прямо пишет, что коды
приходят из разных источников и полный перечень невозможен. Актуальный список даёт
`help --status-codes`.

### §3.3. Что меняется на экране

- Журнал: `■ завершено, код 204 (команда прервана исключением, см. журналы рабочей области)`.
- Шапка консоли: как сейчас, но через общую функцию.
- «завершено, код неизвестен» (процесс не дал кода) не трогаем — расшифровывать нечего.

Замер на живом CLI не назначается (решение заказчика 25.09.2026): вся таблица, включая
код 13 и формулу 128+сигнал, уже имеет достоверность **[Ф]** — она снята одним прогоном
`help --status-codes` (протокол Э7, 13.09.2026), а не собрана по частям из разных
источников, которые стоило бы свести заново. Прогон `help --status-codes` занимает
~32 с, поднимает headless-Eclipse и создаёт рабочую область — цена без ожидаемой прибыли,
раз таблица и так уже измерена целиком.

### §3.4. Правка скила

`edt-launch/SKILL.md`, абзац о кодах: у 13 и `128+сигнал` метка достоверности
**исправляется на [Ф]** со ссылкой на протокол Э7 (`docs/research/t17-edt-experiments.md`,
`help --status-codes`, 13.09.2026) — оба факта с самого начала были частью того же
измерения, что и остальная таблица, а не отдельным источником уровня документации.
Запись **[?]** о том, что имена кодов (`WORKSPACE_IN_USE`, …) сопоставлены числам по
смыслу, остаётся: документация ИТС имён не приводит и этот вопрос не закрывает (это
отдельная, легитимно **[Д]**-ИТС оговорка о неполноте таблицы по своей природе — она
не про происхождение 13 и 128+сигнал и находкой не затронута).

## §4. Тестирование

Базовые правила проекта: TDD для ядра, табличные тесты для чистых функций, мутационная
проверка — только там, где тест проверяет отказ операции или сохранность пользовательского
файла.

| Что | Как |
| --- | --- |
| `version_from_config_ini` | Табличные тесты: оба порядка ключей **[Ф]**, отсутствие `buildId`, несовпадение префикса, лишние ключи, пустой текст, мусор |
| Цепочка версии в `discover_edt` | По тесту на каждый шаг: реестр главнее диска; `config.ini` при имени каталога не по маске; маска без реестра и без `config.ini`; отсутствие всех трёх → в `rejected`, не в `installations` |
| `find_installations` | На `tmp_path`: exe уровнями 0 (сам корень — запасной выход §1.5), 1, 2 и 3; при `max_depth=2` уровень 3 **не** находится — граница закреплена тестом; обход не заходит внутрь найденной установки |
| Отсечение JDK в обходе | Каталог с `release` и `bin` — лист: JDK найден, его подкаталоги не перечислены; каталог с `release`, но без `bin` — не JDK, обход продолжается |
| Глубина у каждого корня своя | `default_roots` отдаёт `components` с глубиной 2, `installations` — с 3; ручной корень — с 3 |
| Настройка `edt_installations_root` | Круговой прогон `settings.json`; заданный корень добавляется к умолчаниям; дубль с корнем по умолчанию схлопывается; путь прямо на каталог установки даёт установку |
| Подпись под полем в настройках | Три состояния §1.4 |
| Лог обнаружения | Перечислены все корни с глубиной и числом найденных, включая несуществующий корень; отброшенные — с причиной |
| `Alt+N` | `MainWindow` с N разделами: нажатие переключает раздел и проставляет `checked` кнопке; разделов больше девяти — сочетаний ровно девять; подсказка кнопки содержит сочетание |
| Диапазон в справочнике | Строится из числа разделов (3 раздела → «Alt+1 … Alt+3») |
| `status_text` | Табличные: каждый код таблицы, `137` → сигнал 9, `128` и `256` — граница, `0` — пусто, неизвестный → «код команды или JVM» |
| Журнал `finish` | Строка журнала содержит и код, и расшифровку |

Мутационная проверка в этой вехе **не требуется**: ни одна задача не трогает отказ
операции и не пишет в пользовательские файлы. Записи в `products.json`/`projects.json`
не было и не будет (решение заказчика, спека v3 §1).

## §6. Границы вехи

Не входит:

- ленивое или отложенное обнаружение установок (это веха про поиск, а не про его цену);
- настраиваемый keymap — сочетания остаются зашитыми (решение заказчика 29.08.2026, T-11);
- показ установок без версии в любом виде (§1.1);
- скан глубже третьего уровня и поиск `1cedt.exe` по диску: неопределённость §1.5 лечится
  запасным выходом и логом, а не расширением поиска;
- прогон `help --status-codes` на 2026.2.1+3 (§3.3);
- разбор пересечений глобального хоткея с оконными сочетаниями (§2.3).
