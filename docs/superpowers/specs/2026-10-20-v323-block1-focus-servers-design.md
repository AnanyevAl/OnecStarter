## 2. T-35 — Enter и Tab переводят фокус из поиска в список

### 2.1. Поведение

Одинаково в «Базах» и в разделе EDT. Решения заказчика 20.10.2026 — в таблице и под ней.

| Ситуация | Enter или Tab в поле поиска |
| --- | --- |
| Поиск непустой, что-то найдено | Текущей становится **первая найденная запись**; её группа раскрыта, список прокручен к ней; фокус в списке. **Запуска нет** |
| Поиск пустой (после `strip`) | Фокус переходит в список, текущая строка не меняется. Запуска нет |
| Поиск непустой, ничего не найдено | Фокус остаётся в поле поиска |
| Enter в списке | Запускает текущую строку — как сейчас, не меняется |

- «Первая найденная запись» — первая **база** в «Базах» (обход `_first_base`, как сейчас)
  и первый **проект** в EDT (обход `_first_project`, как сейчас). Группы и виртуальные
  ветки («Недавние», «Избранное») первой записью не бывают: Enter по ним ничего не запускает,
  и второй Enter вёл бы в никуда.
- Первая найденная — **всегда**, даже если выделенная до поиска строка осталась видна.
  Результат не зависит от того, что было выделено раньше.
- Tab ведёт себя ровно как Enter: иначе он приводил бы в список без текущей строки.

**Цена.** Путь «глобальное сочетание → имя → Enter» становится на одно нажатие длиннее.
Это осознанный обмен: заказчик хочет видеть, что запускается.

### 2.2. Устройство

`ui/search_field.py::SearchField` получает сигнал `list_requested`. Его подают Enter
(`returnPressed`) и Tab без модификаторов. Tab перехватывается в `event()` — Qt обрабатывает
его там раньше `keyPressEvent`, — чтобы фокус не ушёл по порядку обхода. Shift+Tab
не перехватывается.

**Переход включается явно** — параметром `list_navigation=True` конструктора; по умолчанию
выключен, сигнал не подаётся, Tab работает как обычно. Находка плана 20.10.2026:
`SearchField` стоит и в диалоге «Цветовая схема…», и безусловный перехват Tab запер бы
там фокус в поле поиска. «Базы» и EDT флаг включают, диалог схемы — нет.

Каждый раздел подключает сигнал к своему методу `_focus_first_match()`:

1. Поиск пустой → `self._tree.setFocus()`, выход.
2. Найти первую запись тем же обходом, что сейчас у `_launch_first_visible`.
3. Не найдено → выход, фокус остаётся в поле.
4. Найдено → `setCurrentIndex`, раскрыть предков, `scrollTo`, `self._tree.setFocus()`.

`_launch_first_visible` в обоих разделах удаляется: запуск из поиска больше не нужен,
а оставленный метод — соблазн подключить его обратно. Обходы `_first_base`
и `_first_project` переиспользуются; если им нужен индекс, а не ключ, — меняется
возвращаемое значение, второй обход не заводится.

Логика клавиш написана один раз (в `SearchField`), выбор «первой записи» — у раздела.
Отвергнуто: фильтр событий в каждом разделе (дублирование) и порядок обхода Qt для Tab
(Tab приводил бы в список без текущей строки).

### 2.3. Справочник сочетаний

## 3. T-36 — выделение добавленной записи

### 3.1. Поведение (решения заказчика 20.10.2026)

- После успешного добавления новая запись становится текущей **в дереве списка** — в ветке
  файла, не в «Недавних» и не в «Избранном», даже если она видна и там. Её группа раскрыта,
  список прокручен к ней, фокус в списке.
- Если активный поиск запись скрыл — поиск **не очищается**, текущей остаётся прежняя
  строка, как сейчас.
- Добавление не удалось (`ServicesError`) — текущая строка прежняя, как сейчас.
- EDT: то же для записи, добавленной вручную (`add_project`, `add_project_from_directory`).
  Импорт (из EDT Start, через CLI) ничего не выделяет.

### 3.2. Устройство

**«Базы».** Все пути добавления сходятся в `_apply_new_infobase` («Добавить базу…»,
`Ctrl+N`, `Insert`, брошенный каталог). Ключ новой записи возвращает
`Workspace.add_infobase`. После завершающего `rebuild()` вызывается новый метод
`_select_in_tree(key) -> bool`: ищет строку записи в ветке файла и, если нашёл, делает её
текущей. Не нашёл — ничего не трогает, остаётся результат `_restore_current`.

Как отличить ветку файла от виртуальных — по тем же маркерам, что использует
`_restore_current` (маркер записи + путь); конкретный признак выбирается в плане по коду
модели, без второго способа различения.

Ошибка сохранения пароля после успешного добавления (`set_credentials`) запись
не отменяет — выделение выполняется и в этом случае.

**EDT.** `add_project` сейчас идёт через `_apply(lambda: ...)`, который результат операции
отбрасывает. `Workspace.add_project` возвращает сохранённую запись с `id`. Нужно получить
этот `id` после `_apply` и выделить проект тем же способом. Как именно — вернуть результат
из `_apply` или отдельная ветка в `add_project` — решается в плане; `_apply` остальных
операций не меняется по поведению.

## 4. T-29 — выпадающий список серверов

### 4.1. Варианты (решения заказчика 20.10.2026)

Чистая функция без Qt (инвариант 1), например `known_servers(items) -> list[str]`
в `services/` или `domain/` — модуль выбирается в плане по соседству:

- источник — все записи раздела «Базы»: `Workspace.items()`, он уже включает общие списки
  (`dedupe(items, common)` в `Workspace._rebuild`);
- значение — фрагмент `Srvr` строки соединения, извлечённый существующим разбором
  (`domain/connect.py`: `parse_connect` + `find_fragment`), без своего парсера;
- пустые и отсутствующие значения отбрасываются;
- дубли — только точные. Регистр не сворачивается: как платформа сравнивает `Srvr`
  без учёта регистра, не измерено (**[?]**);
- список кластера через запятую (`a,b,c`) — один вариант, строка целиком;
- порядок — по алфавиту без учёта регистра (`casefold`).

### 4.2. Поле в диалоге

`ui/dialogs/infobase.py`: поле «Сервер» становится редактируемым `QComboBox`.
`self._server` продолжает указывать на `QLineEdit` — встроенное поле ввода комбобокса
(`combo.lineEdit()`), поэтому чтение, запись, проверка и словарь полей по видам
(`{"Srvr": self._server, …}`) не меняются. В строку формы и в `_kind_row_widgets` идёт
сам комбобокс — по тому же образцу, по которому у пути файловой базы строка формы
и поле значения уже расходятся.

- Политика вставки — без вставки: введённое вручную в список не добавляется.
- Список заполняется при создании диалога из аргумента — диалог Workspace не читает.
  Передают его `_build_add_dialog` и `_build_properties_dialog` раздела «Базы».
- В диалоге свойств поле показывает значение записи как есть, даже если такого варианта
  в списке нет. В диалоге добавления поле пустое.

## 6. Тесты

- **T-28.** Подсказки версии серверной и веб-базы не содержат `[Ф]`, `[Д]`, `[?]` —
  проверка через публичный путь, по которому подсказка попадает в диалог, а не через
  приватную константу.
- **T-29.** Табличный тест функции: общие списки учтены; точные дубли схлопнуты;
  `srv` и `SRV` — два варианта; `a,b,c` — один; пустые отброшены; порядок по алфавиту
  без учёта регистра; файловые и веб-записи не дают вариантов. Диалог: варианты в списке;
  значение записи показано, даже если его нет среди вариантов; ручной ввод доходит
  до строки соединения.
- **T-35**, для каждого раздела: Enter и Tab при найденном / пустом / ничего не найденном
  поиске — текущая строка и владелец фокуса. **Первый Enter не запускает**: запуск
  подменяется, проверяется отсутствие вызова. Enter в списке запускает текущую.
- **T-36.** «Базы»: новая запись видна — она текущая и строка из ветки файла; поиск её
  скрыл — текущая прежняя, поиск не очищен; отказ добавления — текущая прежняя.
  EDT: ручное добавление выделяет проект; импорт — не выделяет.
- Справочник сочетаний — существующий тест соответствия зарегистрированным сочетаниям.

**Мутационная проверка.** По правилу проекта обязательна для тестов отказа и сохранности
файлов; здесь таких нет. Но для теста «первый Enter не запускает» она выполняется: старое
поведение запускало не ту базу, и тест, зелёный на нём, — ложная уверенность. Мутация:
временно подключить запуск обратно к Enter, убедиться, что тест падает, откатить, записать.
