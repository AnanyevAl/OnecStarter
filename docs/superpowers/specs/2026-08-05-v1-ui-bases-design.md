> Утверждён заказчиком 05.08.2026 в сессии brainstorming.
> Детализирует §2 [дизайна v1](2026-07-30-v1-core-design.md) до двух планов реализации.
> Факты о формате и запуске не дублируются — скилы `v8i-format` и `platform-launch`.
> Обязательства блоков А и Б экспериментов T-05 — таблица соответствия в §8.
> Метки достоверности: **[Ф]** проверено экспериментом, **[Р]** наше решение.

## 0. Резка и результат

Два плана, каждый — работающий проверяемый продукт:

- **4a «Просмотр и запуск»** — окно, дерево, поиск, запуск, контроль версии,
  избранное/недавние, трей и глобальный хоткей, показ ошибок, watcher.
  После 4a продукт закрывает боли А и Б целиком — им можно пользоваться каждый день.
- **4b «Правки списка»** — добавление, редактирование, удаление, группы,
  drag&drop, порядок, ярлыки `.lnk`.

Вне объёма обоих:

- **очистка кэша** — блокирована непроведённым экспериментом T-05.10 (блок В);
  вернуться отдельным решением, когда дойдёт очередь;
- хранение паролей (не в v1), редактирование общих списков (не в v1).

Цепочка каждого плана: writing-plans → subagent-driven-development, отдельная ветка,
финальное ревью всей ветки на самой сильной модели.

## 1. Каркас окна (4a)

Одно окно; слева свёрнутая панель навигации с единственным разделом «Базы» — каркас
держит разделы v2–v4 как независимые виджеты. Тёмная тема по мотивам `temp/style/`,
без бренда 1С. Весь Qt — в `onecstarter.ui` (инвариант 1); UI разговаривает только
с `Workspace`, напрямую в `config`/`platform_1c` не лезет — кроме composition root
`ui/app.py`, который собирает `Workspace` из окружения (план 4a, задача 12):
находит установленные версии и cfg-правила и есть единственное место, где `ui`
знает про `config`/`platform_1c` напрямую.

## 2. Дерево (4a)

Qt-модель поверх `Workspace.tree()` и `items()`.

- Виртуальные узлы **Избранное** и **Недавние** — над деревом файла; наполняются
  из наших данных (`favorite`, `last_launched_at`). Отметить/снять избранное —
  уже в 4a: `set_favorite` пишет в наш `bases.json`, не в `.v8i`.
- Ветка **общих списков** — отдельно, только чтение, с объяснением почему.
  Пользовательская запись с `in_common_list` получает пометку. Дубль
  «пользовательская + общая» с `External=1` — штатное состояние после первого
  запуска общей базы ([Ф] T-05.2), дедупликация по `ID` уже в `services`;
  никаких предложений «удалить дубль». Ошибки чтения общих списков
  (`common_errors`) показываются, не глотаются.
- **Висячий `Folder`** ([Р], утверждено 05.08.2026): рисуем **неявный узел-группу,
  как платформа** ([Ф] T-05.7) — дерево совпадает со штатным стартером; база
  в корне вместо привычного места читалась бы как «OneCStarter сломал мой список».
  У узла нет секции и ключа: пометка «группы нет в файле», операции недоступны
  с объяснением. Правка `build_tree` в `services` — без Qt, с табличными тестами.
- Секция с пустым `Connect=` — группа и выглядит группой ([Ф] T-05.6).
- Битая запись не валит приложение: пометка «не разобрано» с текстом
  `parse_error`, байты секции при записи возвращаются как были (дизайн v1, §4).
- Колонки: имя · версия с разрядностью (что фактически запустим) · дата
  последнего запуска.
- После любой операции и любого перечитывания UI берёт свежие `items()`/`tree()`,
  ключи не кеширует — они меняются при дописывании `ID`.

## 3. Поиск и запуск (4a)

- Набор текста фильтрует дерево; сравнение регистронезависимое, casefold — как
  платформа сравнивает имена баз ([Ф] T-05.3). Совпавшая запись показывается
  вместе со своей группой.
- Enter — запуск в режиме по умолчанию (`launch` без `forced_client`); отдельные
  действия: тонкий, толстый, конфигуратор, для веб-баз — браузер (контекстное
  меню + хоткеи).
- Глобальный хоткей поднимает окно с фокусом в строке поиска; трей — сворачивание
  и запуск избранного из меню. Целевая метрика: любая из 50+ баз — ≤5 нажатий
  без мыши.
- Диагностика **до** запуска — наша, потому что платформа молчит:
  - неуникальное имя — готовый `LaunchError` из `_reject_ambiguous_name`
    ([Ф] T-05.3: ненайденное имя платформа встречает окном выбора, дубли —
    отказом клиента);
  - исчезнувшая из файла запись — `UnknownItemError` после внешней правки:
    предложение обновить список, не трассировка.
- Ошибка запуска — сообщение с фактической командной строкой без секретов
  и кнопкой «скопировать» (дизайн v1, §4). Все `ServicesError` и потомки
  показываются человеческим текстом; трассировка — только для действительно
  неожиданных исключений.

## 4. Контроль версии: правка `resolve_version` (4a, домен)

[Р], утверждено 05.08.2026 — **гибрид**: платформа там, где её поведение
детерминировано, своё — против тихой подмены (боль А):

- `DefaultVersion` установлен, но вне маски → **побеждает**, как у платформы
  ([Ф] T-05.5): снимается проверка `starts_with` для установленного значения.
  Это явное значение штатного ключа, не тихая подмена — расходиться здесь
  значит спорить с платформой без выигрыша.
- `DefaultVersion` задан, но не установлен → для нашего выбора игнорируется,
  работает максимум по маске; тихий максимум-вообще ([Ф] T-05.5)
  не воспроизводим.
- Поле `fallback` («что молча запустил бы штатный стартер») всегда считается
  по платформенным правилам ([Ф] T-05.5, T-02.8) — отдельной логикой,
  не копией нашего выбора. Иначе подсказка в UI врёт.

UI: колонка версии показывает наш выбор; `version != fallback` → подсказка
«штатный стартер запустил бы X»; `NOT_INSTALLED`/`INVALID_REQUEST` → подсветка
проблемы до запуска, предложение выбрать установленную версию (выбор версии —
правка свойств записи, план 4b; в 4a — подсветка и подсказка). Табличные тесты
на оба снятых случая T-05.5 — обязательство 2 блока А.

## 5. Сосуществование со штатным стартером (4a)

`QFileSystemWatcher` живёт в `ui` (инвариант 1) и дёргает
`Workspace.reload_if_changed()`. Обязан переживать **полную перезапись файла**
(атомарная замена удаляет и создаёт путь): после срабатывания путь
переподписывается. Триггер — не только внешний стартер: наш собственный запуск
общей базы материализует её секцию полной канонической перезаписью ([Ф] T-05.2).
Дребезг гасится: несколько событий подряд — одно перечитывание.

## 6. Правки списка (4b)

> **Детализировано и уточнено** в [дизайне плана 4b](2026-08-08-v1-plan4b-ui-edit-design.md)
> (08.08.2026). При расхождении побеждает он: он написан после ручного smoke 4a.
> Здесь остаётся исходная постановка объёма.

- **Добавление**: диалог с тремя размещениями (файловая/серверная/веб)
  и drag&drop каталога файловой базы с автозаполнением имени и строки соединения.
- **Свойства**: типизированные поля + остальные ключи секции; секретные значения
  маскируются. `PPasswd` добавляется в `security.secrets.is_secret_key` —
  обязательство 2 ревью плана 3, становится достижимым с показом свойств.
  Сюда же переносится обязательство из §4 (4a): предложение выбрать
  установленную версию для записи с подсвеченной проблемой (`NOT_INSTALLED`/
  `INVALID_REQUEST`) — сам выбор это правка `Version`/`DefaultVersion` записи,
  в 4a есть только подсветка и подсказка без возможности исправить.
- **Удаление записи**: подтверждение с явным «файлы базы не трогаются».
- **Группы**: создать, переименовать, переместить (каскад `Folder` уже
  в `services`), удалить. Диалог удаления обязан перечислять содержимое или его
  количество и предлагает выбор: «удалить с содержимым» (`RECURSIVE`) или
  «поднять содержимое к родителю» (`PROMOTE`). Платформа каскадит молча
  ([Ф] T-05.9) — быть не хуже недостаточно, надо лучше (обязательство 3 блока Б).
- Пустой `Connect=` правится как группа; при редактировании предупреждаем,
  что платформа при перезаписи вычистит её `Version` ([Ф] T-05.6).
- Перемещение по группам drag&drop; изменение порядка — `OrderInList` дробный,
  вставка между соседями без пересчёта нумерации; точная механика — в плане 4b.
- **Ярлык `.lnk`**: запуск через OneCStarter или напрямую клиентом — решить
  в плане 4b (перенос открытого вопроса дизайна v1, §2).
- Материализация неявной группы отдельным действием не нужна: «создать группу»
  с тем же путём закрепляет её штатно.
- **Значок вида размещения** и **панель свойств выделенной записи** — замечания
  заказчика по итогам ручного smoke 4a, см. §9 (пп. 2 и 3).

## 7. Тестирование

- Всё, что можно, — без Qt: `build_tree` с неявными узлами, `resolve_version`,
  логика фильтрации (чистая функция в `services` или вспомогательном модуле) —
  таблично.
- UI — smoke offscreen (`QT_QPA_PLATFORM=offscreen`): создание окна, наполнение
  модели дерева, фильтр. Процессы 1С в тестах не запускаются никогда;
  `spawn`/`open_url` — инжектированные фейки.
- Мутационная проверка обязательна для защитных тестов: read-only общих списков,
  подтверждение удаления группы, маскировка секретов.
- `mypy --strict` (кроме `ui`), `ruff`, весь существующий набор тестов зелёный.

## 9. Замечания заказчика по ручному smoke 4a (07.08.2026)

Первый запуск собранного 4a на рабочей машине: 7 установленных версий платформы,
64 записи, 6 групп. Приложение стартует, дерево, поиск и контекстное меню работают.
Четыре замечания, все — по показу, не по механике запуска.

### 1. Контекстное меню базы отрисовано скомканно — дефект 4a

**[Ф] наблюдение заказчика, Windows 11, 07.08.2026** (скриншот): в контекстном
меню подсказка сочетания клавиш налезает на название пункта — «Тонкий клиенCtrl+1»,
«КонфигураторCtrl+3». Меню на скриншоте шириной ~151 px.

**[Ф] измерение 07.08.2026:** offscreen дефект **не воспроизводится ни в одном
из четырёх доступных стилей Qt** — ширина `sizeHint` меню с теми же пунктами:

| стиль | без QSS | тема проекта | тема + `padding` у `QMenu::item` |
| --- | --- | --- | --- |
| windows11 | 267 | 282 | 316 |
| windowsvista | 298 | 313 | 316 |
| Windows | 297 | 315 | 318 |
| Fusion | 363 | 391 | 316 |

То есть ширины хватает везде, и «добавить `padding`» — **не подтверждённое
лекарство, а догадка**. Причину надо снять на реальном экране, а не подбирать
вслепую. Кандидаты для проверки, ни один не подтверждён:

- разделение подсказки табуляцией в тексте пункта (`"Тонкий клиент\tCtrl+1"`)
  вместо штатного `QAction.setShortcut()` — Qt рисует колонку сочетания сам
  только во втором случае;
- стилизация `QMenu::item:selected` в теме без явного `padding`: известно,
  что стилизация `QMenu::item` переводит меню на раскладку по QSS;
- масштабирование экрана заказчика, если оно не 100 %.

Диагностика — первым шагом задачи, до любой правки. Дефект показа, механику
запуска не затрагивает.

### 2. Не видно, файловая база или серверная — нужен значок (4b)

> Решено в [дизайне плана 4b](2026-08-08-v1-plan4b-ui-edit-design.md), §1.3:
> значки рисуются кодом из палитры и ставятся в колонку имени, отдельной колонки нет.

В дереве видно только имя. `ConnectKind` уже различает `FILE`, `SERVER`, `WEB`
и `UNKNOWN` — данные есть, показа нет. Веб-база узнаётся косвенно, по слову «веб»
в колонке версии; файловая от серверной не отличается никак.

Требование: вид размещения виден в строке — значок в колонке имени либо отдельная
узкая колонка. `UNKNOWN` обязан отличаться от трёх известных: это не «прочее»,
а «строку соединения не разобрали». Расчёт — в `services/display.py`
(чистая функция, табличные тесты), рисование — в `ui`.

### 3. Панель свойств выделенной записи со строкой соединения (4b)

> Решено в [дизайне плана 4b](2026-08-08-v1-plan4b-ui-edit-design.md), §1.2 и §1.4:
> вырезание `user:pass@` через `urlsplit` с fail-closed возвратом `None`;
> очищенный адрес и показывается, и копируется (решение заказчика 08.08.2026).

Образец — штатный стартер (скриншот заказчика): под списком показывается
`Srvr="localhost";Ref="INITKZ-802-1870"`, по правой кнопке — «Открыть каталог»
(`Shift+F12`), «Изменить каталог» (`Shift+F11`), «Копировать путь», «Копировать
строку соединения».

Наш объём:

- панель под деревом со строкой соединения выделенной записи;
- контекстное меню панели: «Копировать строку соединения», «Копировать путь»
  (для файловой — каталог базы), «Открыть каталог» — только для `FILE`;
- «Изменить каталог» — это правка `Connect`, идёт в диалог свойств (§6),
  отдельным пунктом панели не дублируется.

**Решено заказчиком 07.08.2026:** панель показывает **только путь подключения,
без дополнительных параметров**. Как штатный стартер на образце —
`Srvr="localhost";Ref="INITKZ-802-1870"`, и ничего сверх.

Что это значит технически: из `Connect` берутся только фрагменты размещения —
`File` для файловой, `Srvr` + `Ref` для серверной, `ws` для веб-базы. Всё
остальное (`Usr`, `Pwd`, `LocaleCode`, `wsp*`, `PPasswd`, неизвестные ключи)
в панель не попадает вовсе. `parse_connect`/`find_fragment` для этого уже есть;
расчёт — чистая функция в `services/display.py` с табличными тестами.

Решение снимает вопрос маскировки для `FILE` и `SERVER`: секретов в этих
фрагментах нет по построению, маскировать нечего.

**Остаётся один краевой случай — веб-база.** Значение `ws` может нести учётные
данные прямо в URL (`ws="http://user:pass@host/"`); это уже учтено
в `services/launch.py`, где URL не попадает в сообщение об ошибке ровно
по этой причине. Значит для `WEB` путь подключения обязан показываться
с вырезанной частью `user:pass@` — иначе решение «без дополнительных
параметров» даст утечку там, где её не ждут. Правило проверяется тестом.

**Следствие для меню панели.** Раз дополнительных параметров нет нигде,
пункты штатного стартера «Копировать путь» и «Копировать строку соединения»
для нас сливаются в один — «Копировать». Полная строка `Connect` со всеми
параметрами в 4b не показывается и не копируется; если она понадобится,
это отдельное решение с отдельным вопросом о секретах.

### 4. Диагностика старта: `gui-scripts` проглатывает ошибку (T-04.6)

Всплыло при этом же smoke: `uv run onecstarter` из каталога без UI-кода
завершился молча — на Windows entry point из `[project.gui-scripts]` собирается
поверх `pythonw.exe`, у которого нет консоли, и `ModuleNotFoundError` ушёл в никуда.
Обработка `OSError` в `main()` (задача 12 плана 4a) спасает только то, что дошло
до `main()`; отказ на импорте или падение до создания `QApplication` дадут
пользователю ту же тишину.

К поставке (T-04.6): лог в `%APPDATA%\OneCStarter\`, либо `faulthandler` в файл,
либо отдельный консольный entry point для диагностики. Выбор — в плане поставки.

## 10. Светлая тема и переключение (4b)

> Четыре вопроса ниже **закрыты** в [дизайне плана 4b](2026-08-08-v1-plan4b-ui-edit-design.md),
> §2: палитра (§2.2), переключатель — раздел «Настройки» и пункт трея (§2.5),
> хранение — отдельный `settings.json` (§2.3), системная тема — «Авто»
> по умолчанию (§2.4). Утверждение «в `bases.json` места нет» уточнено: место есть,
> но настройка уехала бы вместе с файлом в `.bad` при порче — см. §2.3.

Требование заказчика 07.08.2026: возможность переключиться на светлую тему.
В 4a тема одна — тёмная, зашитая константами `ui/theme.py`.

### Что придётся тронуть — не только палитру

`theme.*` читается в трёх местах, и два из них **запекают цвет в объект**,
а не берут его при отрисовке:

| Место | Что берёт | Почему это важно для переключения |
| --- | --- | --- |
| `ui/app.py` | `STYLESHEET` целиком | применяется один раз при старте; повторный `setStyleSheet` — дёшево |
| `ui/bases/tree_model.py` | `TEXT_DIM`, `PROBLEM` | цвета кладутся в `QBrush` элементов при сборке модели — после смены темы модель обязана быть пересобрана (`view.rebuild()`), иначе строки останутся в старых цветах |
| `ui/tray.py` | `SURFACE`, `ACCENT` | иконка трея рисуется в `QPixmap` один раз — после смены темы её нужно перерисовать и переустановить |

То есть смена темы на лету — это три действия, а не одно: новый stylesheet,
`view.rebuild()`, новая иконка трея. Плохая альтернатива — «применится после
перезапуска» — допустима как первый шаг, но должна быть осознанным решением,
а не следствием того, что про две запечённые точки забыли.

### Что решить в плане 4b

1. **Палитра.** Тёмная снята со скриншотов `temp/style/`; светлой эталона нет.
   Брать ли инверсию тех же ролей или отдельный набор — решить с заказчиком,
   иначе получится «тёмная с белым фоном» с нечитаемым жёлтым акцентом
   (`ACCENT = #f2d54c` на белом даёт недостаточный контраст).
2. **Где переключатель.** Раздела «Настройки» в v1 нет (§1: одна секция «Базы»).
   Кандидаты: пункт меню трея, кнопка в панели навигации, пункт в меню окна.
3. **Где хранится выбор.** `bases.json` — это `dict[ключ базы → BaseUserData]`,
   места под настройки приложения в нём нет. Нужен либо отдельный файл
   (`%APPDATA%\OneCStarter\settings.json`), либо изменение формата `bases.json`
   с миграцией. Формат наших данных — наш, но менять его задним числом
   на машине, где уже есть история запусков, нельзя без миграции.
4. **Следовать ли системной теме.** Windows отдаёт предпочтение через
   `AppsUseLightTheme`; вариант «Авто / Светлая / Тёмная» дороже двух состояний,
   но избавляет от вопроса «почему не как везде». Решить, а не сделать молча.

Структурная правка `ui/theme.py`: константы модуля становятся палитрой-объектом
(`Palette` с теми же полями) и функцией `stylesheet(palette) -> str`. Тёмная
палитра остаётся значением по умолчанию, чтобы 4a не менял поведение.
