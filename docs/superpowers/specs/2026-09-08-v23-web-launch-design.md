# Запуск веб- и серверных баз: клиент, браузер и чья версия — дизайн v2.3

Решения заказчика 08.09.2026, брейншторминг с замерами на живой машине.
Базовая точка — `master@56ac93f` (v2.2 закрыта, 1897 тестов зелёные).
Версия поднимается до `2.3.0` в конце вехи.

Повод — жалоба: веб-база, опубликованная на веб-сервере, не запускается тонким
клиентом, хотя в свойствах записи стоит `App=ThinClient`. Разбор показал, что это
не дефект в одном месте, а нереализованная ветка плюс более широкая ошибка выбора
версии, задевающая и серверные базы.

## §1. Корень дефекта

[`services/launch.py:79-80`](../../../src/onecstarter/services/launch.py#L79) ветвится
по **виду строки соединения**:

```python
if item.kind is ConnectKind.WEB:
    return _launch_web(item, open_url)
```

Штатный стартер ветвится по **`App`**. Из подмены следует всё остальное:
`App=ThinClient` игнорируется молча; `Ctrl+1` на веб-базе — намеренное бездействие
([`view.py:915-931`](../../../src/onecstarter/ui/bases/view.py#L915)); в контекстном
меню вместо четырёх пунктов один; учётные данные v2.2 до веб-базы не доходят
по построению, потому что `_launch_web` командной строки не собирает вовсе.

Требование [requirements.md, сценарий 2](../../requirements.md) («веб-базу — в браузере»)
коду точно соответствует. Меняется требование, а не только код.

## §2. Цель запуска: `LaunchTarget` вместо `ClientKind`

Канал `forced` по всей цепочке
[`view.launch_key`](../../../src/onecstarter/ui/bases/view.py#L746) →
[`Workspace.launch`](../../../src/onecstarter/services/workspace.py#L437) →
[`launch_infobase`](../../../src/onecstarter/services/launch.py#L65) типизирован
`ClientKind`, у которого браузера нет. Пока это так, пункт «Открыть в браузере»
после снятия короткого замыкания станет ложью: без `forced` запуск уйдёт в настройку,
а её дефолт — тонкий клиент.

Вводится `LaunchTarget` в `domain/launch.py`:

```python
class LaunchTarget(Enum):
    THIN = "thin"
    THICK = "thick"
    DESIGNER = "designer"
    BROWSER = "browser"

    @property
    def client(self) -> ClientKind | None: ...   # None только у BROWSER
```

`ClientKind` не трогается: он про исполняемый файл и живёт в
`ClientConvention.executables`. Дублирование трёх членов — сознательная цена
за то, что «браузер» перестаёт быть невыразимым состоянием.

Тип параметра `forced` меняется на `LaunchTarget | None` во всех трёх слоях.

## §3. Правила выбора цели — чистая функция

Единственное место, где принимается решение, — новая чистая функция в `domain/launch.py`
(инвариант 2: ни ФС, ни процессов, всё окружение аргументами):

```python
def choose_launch_plan(
    kind: ConnectKind,
    app: str | None,
    default_app: str | None,
    *,
    web_default_is_browser: bool,
    forced: LaunchTarget | None,
) -> LaunchPlan | LaunchRefusal
```

Результат размечен двумя вариантами, оба объявлены в `domain/launch.py`.

`LaunchPlan` несёт три поля: `client: ClientKind | None` (`None` — браузер),
`auto_check_mode: bool`, `auto_check_version: bool`.

`LaunchRefusal` несёт одно поле — `reason: RefusalReason`, enum по числу клеток
«отказ» в таблице: `THICK_TO_WEB` (принудительный толстый или Конфигуратор к `ws=`),
`WEB_APP_THICK` (`App=ThickClient` у веб-базы), `BROWSER_FOR_SERVER`,
`BROWSER_FOR_FILE`, `BROWSER_FOR_UNKNOWN`.

Домен текста сообщения не строит: `LaunchRefusal` несёт только причину, а
пользовательскую формулировку собирает `services` по паре `reason` + `item.name`
и поднимает как `LaunchError` — тем же приёмом, каким `_choose_client` сегодня строит
текст по `is_web_client_app` ([`launch.py:133-151`](../../../src/onecstarter/services/launch.py#L133)).
Отличие от действующего прецедента (домен бросает `ValueError`,
[`domain/launch.py:138`](../../../src/onecstarter/domain/launch.py#L138)) сознательное:
причин пять, они различимы только типизированно, и при `mypy --strict` возвращённый
Union заставляет вызывающего разобрать оба варианта, тогда как необъявленное
исключение проверке типов невидимо.

Настройка приходит булевым значением, а не своим enum: домен не импортирует
`services` — тот же приём, что у `DefaultClient.default_app`
([`settings.py:71-83`](../../../src/onecstarter/services/settings.py#L71)).

### Таблица решений

| `kind` | `forced` | `App` | Клиент | `/AppAutoCheckMode` | `/AppAutoCheckVersion` |
| --- | --- | --- | --- | --- | --- |
| WEB | `BROWSER` | любой | браузер | — | — |
| WEB | `THIN` | любой | тонкий | нет | **да** |
| WEB | `THICK` / `DESIGNER` | любой | **отказ** | — | — |
| WEB | нет | `WebClient` | браузер | — | — |
| WEB | нет | `ThinClient` | тонкий | нет | **да** |
| WEB | нет | `ThickClient` | **отказ** | — | — |
| WEB | нет | пусто / `Auto` | настройка: тонкий **или** браузер | **да**, если тонкий | **да** |
| WEB | нет | иное значение `App` | как пусто / `Auto`: канал выбирает настройка | **да**, если тонкий | **да** |
| SERVER | `BROWSER` | любой | **отказ** | — | — |
| SERVER | иначе | как сегодня | как сегодня | как сегодня | **да** |
| FILE | `BROWSER` | любой | **отказ** | — | — |
| FILE | иначе | как сегодня | как сегодня | как сегодня | нет — пиним |
| UNKNOWN | `BROWSER` | любой | **отказ** | — | — |
| UNKNOWN | иначе | как сегодня | как сегодня | как сегодня | нет — пиним, как FILE |

**Строки `UNKNOWN`.** У `ConnectKind` есть четвёртый член
([`connect.py:89`](../../../src/onecstarter/domain/connect.py#L89)); `classify_connect`
возвращает его для строки, где не нашлось ни `File`, ни `Srvr`, ни `ws`, — включая
испорченный ключ с пробелом (`Srvr ="s";`). Сегодня такая запись идёт файловым путём:
[`launch.py:79`](../../../src/onecstarter/services/launch.py#L79) ветвится только по WEB.
Таблица это поведение **сохраняет** — веха про испорченные строки соединения ничего
не измеряла, менять их маршрут без замера нельзя. Побочная выгода: `match kind`
становится исчерпывающим для `mypy --strict`.

**Клетки `forced=BROWSER` у SERVER, FILE и UNKNOWN — защитные и из UI недостижимы:**
пункт «Открыть в браузере» (§6) даётся только записям с `kind is WEB`, хоткея
`BROWSER` нет ([`view.py:475-482`](../../../src/onecstarter/ui/bases/view.py#L475)).
Сценария для них искать не нужно — они закрывают сигнатуру, а не поведение.

Два правила, которые в черновике отсутствовали и без которых реализация — лотерея:

**`/AppAutoCheckMode` снимается тогда, и только тогда, когда пользователь выбрал
клиента.** `forced` и **распознанный** `App` в записи (`ThinClient`, `ThickClient`,
`WebClient`) — это выбор клиента, флаг снимается (**[Ф]** T-02.6, решение заказчика
23.08.2026). Нераспознанное значение `App` клиента не даёт
([`_client_from_app`](../../../src/onecstarter/domain/launch.py#L139) возвращает `None`)
и потому выбором не считается — оно ведёт себя как `Auto`. Настройка веб-баз выбирает **канал**
(браузер против тонкого), а не клиента, поэтому её значение «тонкий» флаг сохраняет —
и командная строка совпадает с эталоном **[Ф]** T-05.16 № 8.

**`default_client` («Клиент по умолчанию») в решении для `kind is WEB` не участвует.**
Так и сегодня — короткое замыкание стоит раньше `_choose_client`, — и после правки
это должно остаться: у веб-базы «толстый по умолчанию» означал бы запрет запуска.
Подсказку [`settings_view.py:225-228`](../../../src/onecstarter/ui/settings_view.py#L225)
сузить: настройка не про веб-базы.

## §4. Версию пиним только у файловых баз

`auto_check_version` определяется видом базы, а не пожеланием:

- **FILE** — как сегодня: `resolve_version`, `/AppAutoCheckVersion-`, exe выбранной версии;
- **WEB и SERVER** — положительный `/AppAutoCheckVersion`, exe максимальной установленной
  версии, платформу не переигрываем;
- **UNKNOWN** — как FILE, без изменений: маршрут испорченной строки соединения замером
  не покрыт, и веха его не трогает. Условие реализации —
  `kind is ConnectKind.FILE or kind is ConnectKind.UNKNOWN`, а **не**
  `kind is not ConnectKind.FILE`: второе молча сменило бы полярность флага
  у достижимого входа.

Это исправляет молчаливый повис (**[Ф]** T-05.16 № 3, 6) и приводит нас к поведению
штатного стартера.

### Цена, которую нельзя замолчать

«Запуск с контролем версии платформы» — заявленная функция v1 — применима только
к файловым базам. У заказчика 11 серверных и 1 веб-база: для них наш выбор версии
либо не действовал, либо, сработав, вешал клиента. Это не регресс новой вехи,
а то, что замер вскрыл в уже поставленном коде.

### Что делаем с UI (решение заказчика 08.09.2026: «показывать, но честно пометить»)

Выбор версии **остаётся** и продолжает писать `Version` в `.v8i` — ключ читает
не только наша программа, но и штатный стартер, и «на наш запуск не влияет»
не даёт права его снимать (инвариант 3).

Механизм для честной пометки уже есть:
[`version_cell`](../../../src/onecstarter/services/display.py#L253) возвращает для веб-баз
`VersionCell("веб", False, None)`, а диалог показывает `cell.hint` под строкой «Версия»
([`infobase.py:520-524`](../../../src/onecstarter/ui/dialogs/infobase.py#L520)). Правки:

1. Симметричная ветка `SERVER` в `version_cell` — текст колонки «сервер»,
   `hint` с объяснением «версию определяет кластер, ключ `Version` на запуск
   не влияет ([Ф] 08.09.2026)».
2. `hint` для WEB — сейчас `None`, наполнить тем же по смыслу текстом про публикацию.
3. **Решение о порядке ветвей:** ветка `SERVER` ставится **до** проверки
   `discovery_pending`, как уже стоит ветка `WEB`. Обоснование: утверждение «версию
   определяет кластер» не зависит от того, завершилось ли обнаружение установленных
   версий, и показывать «…» вместо него — прятать верное за неизвестным.
   Существующий тест на «…» для серверной базы переписывается **с новым обоснованием
   в докстринге**, а не молча.

**Инвариант диалога:** `InfobaseDialog.changes()` для нетронутого диалога обязана
возвращать `{}` при **любом** виде размещения. Сегодня это держится на том, что
`findData(item.requested_version)` находит пункт ([`infobase.py:495-499`](../../../src/onecstarter/ui/dialogs/infobase.py#L495));
при `-1` индекс откатывается на нулевой пункт «как установлено» с данными `None`,
и `changes()` отдаёт `Version: None`, что **удаляет ключ** из чужого файла
([`infobase.py:1164-1166`](../../../src/onecstarter/ui/dialogs/infobase.py#L1164)).
Ветку трогать нельзя; охранный тест параметризуется по FILE/SERVER/WEB (§8).

## §5. Настройка

`services/settings.py`: поле `web_launch: WebLaunch = WebLaunch.THIN`,
значения `thin` | `browser`, ключ JSON `web_launch`.

Схема остаётся **1**: новый ключ необязателен, старый файл читается без миграции,
незнакомое значение мягко уходит в дефолт — как у остальных полей.

Дефолт `thin` совпадает со штатным стартером (**[Ф]** T-05.16 № 8). Существующие
установки после обновления начнут запускать веб-базы с `App=Auto` тонким клиентом —
изменение видимое, поэтому оно и вынесено в настройку.

UI: строка «Веб-базы открывать» с двумя вариантами, рядом с «Клиент по умолчанию».

## §6. Свойства записи, меню и хоткеи

**Свойства.** В `_APP_ITEMS` добавляется «Веб-клиент (браузер)» → `App=WebClient`,
пункт показывается только у записей с `kind is WEB`. Записи, у которой `App=WebClient`
уже стоит при не-ws строке соединения, пункт достаётся существующим механизмом
«незнакомое значение сохраняем отдельным пунктом» ([`infobase.py:505-510`](../../../src/onecstarter/ui/dialogs/infobase.py#L505)) —
поведение не меняется, запуск такой записи отказывает как и сегодня.

**Смена вида размещения внутри диалога — правка по итогам финального ревью ветки (I1).**
Правило выше говорит про вид **сохранённой** записи (`item.kind`), а размещение
меняется в том же окне отдельным комбобоксом (`_kind_box`, задача 10 вехи v2.1).
Черновик спеки эту пару не рассмотрел, и диалог давал молча собрать незапускаемую
запись: открыть веб-запись → выбрать «Веб-клиент (браузер)» → сменить размещение
на файловое; «ОК» активен, `changes()` отдаёт `Connect` с `File=` и `App=WebClient`
рядом. Такая секция при **каждом** запуске отвечает отказом «задан `App=WebClient`,
но строка соединения не ws=», связать который со сменой размещения, сделанной раньше,
пользователь не сможет, — а запись уже в файле, общем со штатным стартером.

Правило дополняется двумя пунктами:

1. **Пара «веб-клиент + не-веб размещение» запирает «ОК» с пояснением рядом с ним**
   (`_web_client_conflict`, `WEB_CLIENT_PLACEMENT_NOTE`) — тем же механизмом
   `_refresh_ok_state`, что незаполненное имя и пароль без логина, и по тому же
   решению заказчика «отказ показывается раньше, до действия» (§3.1 спеки v2.1).
   Состав комбобокса при этом не перестраивается: молча подменять выбор клиента
   при смене размещения означало бы тихо править данные пользователя, а именно
   от этого класса дефекта написан весь `infobase.py`.
2. **Сочетание, уже лежащее в файле, «ОК» не запирает.** Тот же принцип, что
   у `_placement_violation`: то, чего пользователь не трогал, — не его ввод.
   Запись с `App=WebClient` при не-ws строке соединения (абзац выше) обязано
   быть можно открыть ради правки группы или версии.

**Остающийся разрыв, записан сознательно.** Обратная сторона того же правила:
у не-веб записи, вид которой сменили на веб **внутри диалога**, пункт
«Веб-клиент (браузер)» в списке не появляется — состав считается один раз,
по `item.kind`. Браузер такой записи выбирается после сохранения и повторного
открытия свойств. Это не порча данных, а недостающее удобство, и закрывать его
перестройкой состава комбобокса по сигналу смены вида — отдельное решение,
не находка ревью.

**Контекстное меню веб-базы:** «Запустить\tF3» (`forced=None`), «Тонкий клиент\tCtrl+1»
(`THIN`), «Открыть в браузере» (`forced=BROWSER` — **сильнее** и настройки, и `App`).
Записи с `App=WebClient` нужен симметричный пункт «Тонкий клиент», иначе разового
выбора нет в обратную сторону.

**Хоткеи.** `_launch_current` перестаёт молча ничего не делать: `Ctrl+1` на веб-базе
запускает тонкого клиента, `Ctrl+2`/`F4` дают внятный отказ вместо бездействия.
Дыра, которую закрывало прежнее бездействие («выдать браузер за Конфигуратор»),
закрывается теперь отказом, и на неё нужен свой тест (§8).

## §7. Достоверность `LaunchOutcome`

При положительном `/AppAutoCheckVersion` наш процесс завершается за секунды, а клиента
поднимает платформа (**[Ф]** T-05.16 № 4, 7). Значит для WEB и SERVER:

- `version` — `None`: какая версия запустится, мы не знаем;
- `pid` и `command_line` описывают **уже завершившийся** процесс.

Эти поля помечаются как недостоверные для WEB/SERVER, а не отдаются как есть.
Что именно показывать пользователю вместо них — решает слой представления;
молча выдавать мёртвый PID за живой запрещено.

**Отменено по итогам самопроверки плана; §7 приведён в соответствие с кодом
финальным ревью ветки (M2).** Пометка `pid`/`command_line` недостоверными
не реализована и реализовываться не будет: ни одно из этих двух полей наружу,
к пользователю, не выводится вовсе. Единственный потребитель `LaunchOutcome`
в рабочем коде — `Workspace.launch`, и он читает только `outcome.client`
(запись времени запуска); `pid`, `command_line`, `version` и `url` успешного
исхода не читает никто, кроме тестов. Пользователю командная строка показывается
лишь в тексте ошибки **порождения** процесса (`services/launch.py`, ветка
`except OSError`) — там процесс не стартовал вовсе, и рассуждение об «уже
завершившемся» к ней не относится. Помечать недостоверным поле, которого никто
не видит, — цена без покупателя. Требование §7 сохраняет силу ровно в одной части: **`version` для
WEB/SERVER равен `None`** (реализовано, `_installation_for`), и если поле `pid`
или `command_line` когда-нибудь начнут показывать, пометка становится
обязательной вместе с этим показом. Документ, разошедшийся с кодом, врёт
следующему исполнителю, — поэтому отмена записана здесь, а не только в отчёте
задачи.

Побочно: пароль оказывается в argv процесса, который породили не мы. Модель угроз v2.2
от этого не меняется — процесс работает под тем же пользователем, и текст предупреждения
(«виден любой программе, работающей под вашей учётной записью, всё время работы клиента»)
остаётся истинным. Меняется только наше знание о том, какой процесс держит пароль.

## §8. Побочный эффект на файл списка

Утверждение «запуск по `/IBName` `ibases.v8i` не меняет» верно **для записей
пользовательского списка**: **[Ф]** T-05.16 № 1 (веб-запись) и **[Ф]** T-05.15,
запуски A–C (файловая запись) — это единственные замеры, где сохранность файла снята
наблюдением. Остальные восемь замеров T-05.16 её не проверяли: методика сверяла
SHA-256 **после** побайтового отката, что доказывает успешность отката, а не то, что
запуск файл не менял. Для записей из `CommonInfoBases` документировано обратное:
**[Ф]** T-05.2 — клиент материализует секцию полной канонической перезаписью.

Это **уже действующее поведение продукта**: `Workspace.launch` записи `source=COMMON`
не блокирует, и файловая либо серверная общая запись вызывает ту же перезапись сегодня.
Веха лишь распространяет его на вид `WEB`. Отдельного согласия заказчика не требуется —
иначе его надо было брать и для файловых общих записей.

Материализация именно **ws**-записи измерена отдельно: **[Ф]** T-05.16 № 12
(08.09.2026) — общий список из одной ws-записи, запуск по `/IBName`, секция
дописана в пользовательский `ibases.v8i` (18933 → 19154 байта, SHA-256 сменился).
Метка **[Д]** снята.
