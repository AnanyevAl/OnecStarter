# Дизайн плана 3 — слой `services` и наши данные

> Утверждён заказчиком 03.08.2026 в сессии brainstorming.
> Уточняет [дизайн v1](2026-07-30-v1-core-design.md) в части слоя `services`; общий контекст —
> [requirements.md](../../requirements.md), задача — `T-04.3` в [tasks.md](../../tasks.md).
> Факты о 1С не дублируются: формат `.v8i` — скил `v8i-format`, механика запуска — скил
> `platform-launch`. Уровни достоверности: **[Ф]** проверено на реальной машине
> (эксперименты T-02 или замеры, зафиксированные в скилах), **[Д]** из документации ИТС,
> **[?]** не проверено, **[Р]** наше решение.

## 1. Границы

Входит: агрегация списка баз, реакция на внешнее изменение файла, запись в `ibases.v8i`
с разрешением конфликта, запуск базы, наши данные в `%APPDATA%`.

Не входит и ждёт отдельных планов:

| Что | Почему не сейчас |
| --- | --- |
| Очистка кэша базы | Расположение и состав кэшей **[?]** — нужен эксперимент на реальной машине |
| Ярлыки `.lnk` | Не решено, запускать через OneCStarter или напрямую; поведение штатного ярлыка **[?]** |
| Триггер watcher (`QFileSystemWatcher`, таймер) | Qt — только в `ui` (инвариант 1), значит план UI |
| Настройки окна и приложения | Владелец — `ui`, свой файл, план UI |

## 2. Форма слоя

Четыре модуля с одной обязанностью и тонкий координатор, держащий состояние
(документ, снапшот, наши данные, список установок).

| Модуль | Обязанность |
| --- | --- |
| `catalog` | Сборка модели списка из `ibases.v8i`, общих списков и наших данных; дерево |
| `user_data` | `bases.json`: избранное, история, ключ привязки |
| `edit` | Операции записи как патчи; цикл повтора при внешнем изменении |
| `launch` | Сценарий запуска: команда → процесс → запись истории |

**[Р]** Отвергнут единый фасад `InfobaseService`: чтение, запись, слияние и порождение процессов
в одном модуле дают файл, который тяжело ревьюить и править точечно. Отвергнут репозиторий
с подписками: в v1 подписчик один, косвенность не окупается.

## 3. Источники и модель

### Источники

| # | Источник | Режим |
| --- | --- | --- |
| 1 | `%APPDATA%\1C\1CEStart\ibases.v8i` **[Д]** | чтение и запись |
| 2 | Общие списки: `1cestart.cfg` → `CommonInfoBases` → пути к `.v8i` **[Д]** | только чтение |
| 3 | `%APPDATA%\OneCStarter\bases.json` | чтение и запись |

Пути берутся из окружения аргументами, а не хардкодятся: иначе слой не тестируется.
Значения `CommonInfoBases` объединяются из всех уровней `1cestart.cfg` **[Д]**;
`config.cestart_cfg.common_infobase_sources` это уже делает.

Недоступный общий список не роняет приложение: ветка показывается с пометкой об ошибке.

### `InfobaseItem`

Плоская запись: ключ привязки, имя, `Folder`, признак группы, строка соединения и её вид
(`ConnectKind` из `domain.connect`), запрошенная `Version` как в файле, источник
(`USER` / `COMMON`), `OrderInList` (дробный — **[Ф]** реальные значения `60.6814814814813`,
`-1`, `311296`), избранное, дата последнего запуска, счётчик запусков, `parse_error`.

**[Р]** Разрешённой версии платформы в модели нет — это отдельная чистая функция поверх
`domain.selection.resolve_version`. Список установок и правила `DefaultVersion` — данные
окружения, а не файла; смешав их с данными записи, мы потеряем табличную тестируемость,
которой требует инвариант 2.

Битые записи (спека v1, §4) попадают в модель с заполненным `parse_error` и показываются
как «не разобрано». Их байты возвращаются при записи как были — это уже обеспечивает `RawLine`
слоя `config`.

Дерево собирается чистой функцией из плоского списка по `Folder`: **[Ф]** T-02.3 — `Folder`
секции-группы равен пути родителя, собственный путь группы = `Folder` + `/` + имя секции.
Qt получает готовую структуру.

**[Р]** База, чей `Folder` указывает на несуществующую группу, показывается в корне
и помечается в модели. Скил помечает этот случай как непроверенный: как ведёт себя штатный
стартер, неизвестно. Наш выбор — не терять запись: невидимая база хуже базы не на своём месте.

## 4. Ключ привязки наших данных

**[Ф]** скил `v8i-format`: `ID` — единственный ключ слияния; `Connect` ключом идентичности
не является, несколько секций с одинаковым `Connect` допустимы; опираться на порядок секций
между сеансами нельзя.

**[Р]** Гибридный ключ:

- `id:<uuid>` — когда у секции есть `ID` (обычный случай: записи мастера штатного стартера);
- `cs:<sha256(connect)[:16]>|<name>` — суррогат, когда `ID` нет. Нормализация перед
  хешированием: `casefold` и обрезка пробелов по краям. Префикс обязателен, иначе суррогат
  столкнётся с UUID.

**[Р]** Строка соединения в ключ целиком не идёт, только её хеш. Первоначальная редакция
этого раздела клала `connect` в ключ открытым текстом, и ревью Task 6 показало, к чему это
ведёт: `Connect` несёт `Pwd`, `DBPwd`, `SPwd`, `wsp`, `wsppwd`, ключи привязки индексируют
`bases.json` и попадают в сообщения об ошибках — то есть пароль пользователя оказывался
и в нашем файле, и в тексте ошибки. Проверено на реальном коде до исправления.
Это прямое нарушение инварианта 5 `CLAUDE.md`.

Хеш выбран вместо вырезания секретов через `security/`: вырезание надёжно ровно настолько,
насколько полон список секретных имён, а он, по признанию этого же документа, не закрыт.
Хеш не зависит от полноты списка вовсе. Имя базы в ключе остаётся открытым — оно
не секрет, это отображаемое имя из списка, и по нему запись остаётся опознаваемой.

Наши данные привязываются только к базам. У секций-групп нет ни истории, ни избранного:
группа не запускается, а «избранная группа» — это функция дерева, а не запуска, и в v1 её нет.

**[Р]** Свой `ID` дописывается в `ibases.v8i` только той записи, которую пользователь
редактирует через нас (§5). Записи, к которым он не обращался, не меняются: массовая
простановка `ID` ради удобства нашего кода нарушает требование «не сломать список
пользователя». Цена решения принята: у записей без `ID` переименование или перенос базы
теряет их историю.

После дописывания `ID` наши данные перевешиваются с суррогатного ключа на `id:` операцией
`rekey`.

### Формат `bases.json`

```json
{
  "schema": 1,
  "entries": {
    "id:11111111-1111-1111-1111-111111111111": {
      "favorite": true,
      "last_launched_at": "2026-08-03T07:12:44Z",
      "launch_count": 17,
      "last_client": "thin"
    }
  }
}
```

Время хранится в UTC, в локальное переводится только при показе. Записи баз, исчезнувших
из списка, не чистятся: файл крошечный, а база может вернуться (например, отвалившийся
общий список).

Отсутствующий файл — норма, пустые данные. Битый файл — работаем с пустыми данными,
а испорченный переименовываем в `bases.json.bad`. Молча затёртая история — потеря без следа.

**[Р]** Недоступный файл — не то же самое, что битый. Если `bases.json` есть, но не читается
(блокировка антивирусом, отвал сетевого диска, права), пустые данные возвращать нельзя:
первое же сохранение затрёт живую историю. Такой случай поднимает `UserDataUnavailableError`.
Туда же уходит неудачный перенос в `.bad` — не сумев убрать испорченный файл, продолжать
с пустыми данными значит уничтожить то, что пользователь мог бы из него достать.
Уточнение внесено по итогам ревью Task 4 плана: первоначальная формулировка ловила `OSError`
наравне с порчей содержимого и вела ровно к той потере, которую этот раздел запрещает.

## 5. Запись и разрешение конфликта

Пишутся только записи с источником `USER`. Запись в общий список — ошибка программиста,
проверяется на границе операции.

**[Р]** Единица записи — патч, а не «сохранить документ»: цель (по `ID`, по суррогату
или «новая секция»), вид (`ADD` / `UPDATE` / `REMOVE`) и словарь изменений
`ключ → значение | None`, где `None` удаляет ключ. Перемещение по группам и смена порядка —
частные случаи `UPDATE` над `Folder` и `OrderInList`; отдельных операций нет.

Цикл записи, до трёх попыток:

1. `config.atomic.read_with_snapshot` → `config.v8i.parse_v8i`;
2. наложить патч;
3. `config.atomic.atomic_write_if_unchanged`;
4. на `ExternalChangeError` — следующая итерация с нуля.

**[Ф]** Перезапись платформой каноникализирует **весь** файл, а не затронутую секцию:
`OrderInList=-1` заменяется материализованными значениями, `OrderInTree` пересчитывается,
секции смещаются, всем разом дописывается `DisableLocalSpeechToText=0`. Отсюда два следствия
для этого цикла: расхождение digest — рядовое событие, а не авария, и цель патча ищется
только по `ID` или суррогату, но никогда по позиции секции.

Патч всегда ложится на свежее состояние, поэтому чужие правки в других секциях и других
ключах переживают запись. **[Р]** Совпавший ключ получает значение пользователя: он только
что его задал. Три неудачные попытки — `ConcurrentEditError`; бесконечный цикл при живом
стартере, переписывающем файл, недопустим.

Краевые случаи:

| Случай | Поведение | Почему |
| --- | --- | --- |
| `REMOVE` секции, которой уже нет | Успех | Пользователь хотел, чтобы её не было — её нет |
| `UPDATE` секции, удалённой извне | `TargetGoneError` | Молчаливое воскрешение записи хуже ошибки |
| `ADD` с именем-дублем | Разрешён | Формат уникальности не требует, штатный стартер допускает дубли |
| `PermissionError` при замене файла | Пробрасывается без повторов | **[Ф]** T-02.4 и скил `v8i-format`: файл не блокируется ни открытым стартером, ни работающим клиентом — «ретраи по `PermissionError` на всякий случай, не по факту». Значит это настоящая проблема (права, антивирус), и ретраи её спрячут |

**Состав ключей новой записи при `ADD`:** имя секции, `Connect`, наш `ID`, `Folder` — если база
создаётся не в корне, и `OrderInList=-1`.

**[Ф]** известен состав ключей, который мастер стартера пишет для секции-**группы**:
`ID`, `OrderInList=-1`, `Folder`, `OrderInTree`, `External=0`. Для секции-**базы** этот состав
не снят, поэтому переносить его целиком нельзя. **[Р]** Пишем минимум обязательного плюс
`OrderInList=-1` по образцу единственного наблюдаемого поведения мастера; смысл значения `-1`
**[?]** — известно лишь, что платформа при канонической перезаписи заменяет его
материализованными числами. `OrderInTree` и `External` не выдумываем: необязательные ключи
платформа дошлёт сама, а неверно угаданное значение хуже отсутствующего ключа.

### Отсутствующий файл и кодировка

Отсутствующий `ibases.v8i` — норма: пустой список, а первый `ADD` создаёт файл. Технически
это `parse_v8i(b"")`, который даёт документ в UTF-8 без BOM с `\r\n` — то же, что **[Ф]**
наблюдается на реальном файле.

Существующий файл пишется в той кодировке, в которой прочитан **[Ф]** (BOM встречается
и так и так, наличие BOM не признак чужого файла).

**[Р]** `UnicodeEncodeError` при записи (документ прочитан фолбэком `latin-1`, а пользователь
добавил символы вне этой кодировки) — операция отклоняется с внятным сообщением. Слой `config`
эту политику явно оставил нам ([encoding.py](../../../src/onecstarter/config/encoding.py),
докстринг `encode`). Пересохранение всего файла в UTF-8 отвергнуто: `latin-1` декодирует любые
байты, поэтому под ним может лежать другая однобайтовая кодировка с кириллицей, и «починка»
превратит чужие данные в мусор безвозвратно. Отказ обратим, потеря — нет.

## 6. Реакция на внешнее изменение

**[Р]** `services` даёт синхронную операцию «перечитать, если digest файла разошёлся
с известным». Потоков и подписок в ядре нет — операция тестируется прямым вызовом.
Триггер (`QFileSystemWatcher` с переподпиской после подмены файла, запасной таймер) живёт
в `ui` и относится к плану UI: инвариант 1 запрещает Qt в `services`, а `watchdog` тянет
новую зависимость, свой поток и флакающие тесты на таймингах ради того же результата.

Сверка по digest сама гасит срабатывания на нашу собственную запись: после записи известный
digest обновляется, и перечитывание не запускается вхолостую.

## 7. Запуск

Координатор склеивает готовые слои, своей логики почти не добавляя:

```text
resolve_version (domain.selection)
  → choose_client (domain.launch)
  → convention_for (domain.launch)
  → build_arguments (domain.launch)
  → build_launch_command (domain.launch)
  → spawn (platform_1c.process)
  → record_launch (services.user_data)
```

Время подаётся аргументом, а не берётся внутри: иначе тест истории недетерминирован.
Функции порождения процесса и открытия браузера инжектируются — процессы 1С в тестах
не запускаются никогда (спека v1, §5).

Ошибки ловятся до порождения процесса (спека v1, §4): версия не разрешилась или разрешилась
в неустановленную — отказ с указанием запрошенного и доступного; `App=WebClient` на пути
исполняемых файлов — отказ. Сообщение об ошибке несёт фактическую командную строку,
профильтрованную через `security.secrets`: при наличии секретных ключей показываются
их имена, а не значения.

Веб-базы идут мимо `spawn`: `ConnectKind.WEB` → значение `ws` открывается браузером.
Форма URL **[?]** — берём значение `ws` как есть.

### Открытый вопрос: базы из общих списков

**[Р]** Запускаем тем же `/IBName`: платформа объединяет свой список с `CommonInfoBases`,
поэтому имя обязано разрешаться. Это **[?]**, и там же прячется неоднозначность при
одинаковых именах в пользовательском и общем списках.

Альтернатива `/IBConnectionString` не годится: её форма сама непроверена (обязательство 3
из финального ревью плана 2) и она бесполезна, когда в строке соединения есть пароль.
Проверяется одним экспериментом вместе с обязательством 3; обходной путь под гипотетическую
проблему заранее не строим.

## 8. Тестирование

- **Фикстура.** `tests/fixtures/` пуст, roundtrip-тесты плана 1 живут на инлайновых байтах.
  Нужен обезличенный `ibases.v8i` целиком с обязательным набором краевых случаев из
  `CLAUDE.md`: группа без `Connect`, вложенная группа, неполная `Version`, дробный
  `OrderInList`, неизвестный ключ, клиент-серверная и `ws`-строка соединения. Сборка дерева
  и ключей на синтетике из трёх строк не проверяется.
- **Инвариант 1.** Отдельный тест в подпроцессе импортирует `services`, `domain`, `config`,
  `platform_1c`, `security` и проверяет, что `PySide6` не оказался в `sys.modules`.
  Статический поиск `import PySide6` транзитивную протечку не поймает, а опасна именно она.
- **Конфликтная запись.** Тест подменяет файл между чтением и `atomic_write_if_unchanged`
  и проверяет, что чужая правка выжила, а патч применился.
- **Наши данные.** Отсутствующий, пустой и битый `bases.json`; переименование в `.bad`;
  `rekey` при дописывании `ID`.
- **Кодировка.** Создание отсутствующего `ibases.v8i`; запись в cp1251 и UTF-8 с BOM
  без смены кодировки; отказ по `UnicodeEncodeError` на документе из `latin-1`.
- Ядро — через TDD. `mypy --strict`, `ruff`, `pytest` — как в планах 1–2.

## 9. Состав работ

Ориентировочно девять задач: модель и ключ привязки; `user_data`; `catalog` с деревом;
патчи и их применение; цикл записи с повтором и политика кодировки; запуск; веб-запуск;
фикстура; координатор. Сопоставимо с планом 2 (восемь задач). Детальная разбивка — в плане,
через `writing-plans`.
